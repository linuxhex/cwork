Agent 一次改了 47 个文件。你打开 PR 的 diff，决定认真审一遍。

翻到第 12 个文件，你已经记不清前面看过什么。翻到第 20 个，你开始只看文件名不看内容。

最后你看了一眼 CI：绿了。你点了合并。

⚠️ 这篇文章想说一件不太政治正确的事：你点合并的那一刻，其实已经放弃审阅了。问题不在你懒，在于工具假设的工作方式变了。

一、Git 的三个设计假设

Git 不是"给代码用的工具"，它是"给人看代码用的工具"。它的三层核心语义，每一层都押注在一个关于人的假设上。

diff：假设变更量在人眼可读的规模内。一个人一个下午改 200 行、动 3 个文件，diff 读起来是享受。Agent 十分钟改 47 个文件、增删 4000 行，diff 就变成了一堵墙。

commit message：假设作者知道自己为什么这样改。人能写出"因为老逻辑在并发下会丢更新，所以换成版本号比较"。Agent 写的是"更新相关逻辑以支持新需求"——它不是敷衍，它确实没有贯穿始终的意图。

merge / review：假设审阅者能重构作者的意图。你看 diff 时真正在做的，是反推"这人想干嘛，这么干合不合适"。意图不清，这个反推就直接失效。

二、社区已经在给三种不同的答案

这个问题最近密集冒头。GitHub 上出现了三个定位完全不同的项目，恰好对应三条路。

第一条：重写版本控制语义。git-ai，2026 年 10 月 15 日建库，三天拿到 2,298 star，仓库描述只有一句"Git designed for AI agents"。它的判断是：Agent 的变更表达方式和人类不同，应该从协议层重做。

第二条：在 Git 之上叠审计层。atlas 把自己定位成"Agent 的 source control"——追踪多个编码 Agent 的改动，并支持统一查询。它不动 Git，动的是"谁在什么时候改了什么"这件事的可追溯性。

第三条：隔离执行，集中审阅。Orca 把不同编码 Agent 放进各自独立的 git worktree 里跑，再把结果集中到一个地方审阅。它承认冲突和混乱是常态，先把执行环境隔开。

三条路的分歧在于：是 Git 错了，还是用法错了，还是审阅入口错了。

三个项目在短时间内集中出现，本身就说明这不是一个人的幻觉。当不同团队在不同层面同时动手，往往意味着真问题已经被碰到了，只是还没人能说清该在哪一层解决。

三、为什么"CI 绿了"替代不了审阅

很多人实际上是这么做的：CI 绿了就合并。这有三个漏洞。

漏洞一：CI 只验证你写过的测试。没测的行为，等于没有约束。一个 40% 覆盖率的项目，CI 绿了说明不了什么。

漏洞二：Agent 可能改测试。它发现测试不过，最省事的修法是让断言变松。从它自己的目标看，这是合理的；从你的目标看，这是把保险丝剪了。

漏洞三：功能对，结构错。CI 能验证"这个接口返回对了"，验证不了"这段逻辑放错层了"。而后者才是三个月后让你改不动代码的原因。

说到底，你把"正确性"和"可接受性"混成了一件事。CI 管前者，审阅管后者。两者不能互相替代。

还有一个更隐蔽的代价：把 CI 当审阅，等于把责任交给了一个不会负责的系统。出事那天，你能找到的是"那次构建是绿的"，而不是"谁判断过这么改是对的"。

四、三条路线的真实代价

路线 解决什么 代价与局限
重写协议
（git-ai）		 变更表达更结构化、更适配机器读写 极早期；IDE、CI、代码托管平台都不配套
叠加审计层
（atlas）		 多 Agent 改动可追踪、可查询 记录下来了，但"该不该这么改"还得人看
隔离执行 + 集中审阅
（Orca）		 并行冲突减少，审阅入口统一 审阅瓶颈仍在人身上，规模上不去

看这张表你会发现一件事：三条路没有一条解决"审阅速度"。它们解决的是记录、隔离、表达。真正卡住你的那一环，还是得靠别的方式。

五、不换工具也能做的五件事

这五条都是流程约束，今天就能上，不依赖任何新项目。

✅ 限制单次变更规模。一次任务最多动 N 个文件，超了就拆。这是五条里最有效的一条，因为它直接把 diff 拉回人眼可读的区间。

✅ 把意图前置。先让 Agent 出改动计划：改哪些文件、为什么、明确不动哪些。审完计划再放行执行。审计划比审 diff 便宜一个数量级。

✅ diff 分层看，不要顺序看。先看新增和删除的文件，再看修改的；修改里优先看接口定义、类型声明、数据库 schema。这三处错，其余全错。

✅ 测试只增不改。禁止 Agent 修改已有测试；新增测试必须单独成一个 commit，你能一眼看出它加了什么约束。

✅ 让它写变更说明，再对着 diff 复核一次。机器自查不能代替人审，但能拦住"说明里说要改 A，实际改了 B"这种自相矛盾。

✅ 给 Agent 的改动独立分支，禁止直推主干。这不只是隔离风险，更是强制留出一个"人可以介入"的节点。没有这个节点，前面四条都会被绕过去。

🌱 如果只允许做一件事，做第一条。把单次变更规模砍到人审得动的量级，比换任何工具都管用。

六、边界：什么时候才真的该换 Git

我不建议你现在去迁移到 git-ai 这类项目。理由很实际：版本控制是所有工具链的地基，IDE、CI、代码托管、部署、回滚全压在上面。地基还在施工，你别把楼先盖上去。

值得认真看这些新方向的信号是：你同时在跑 10 个以上的 Agent，并且在做自动合并、自动集成。到了那个量级，人审阅这条路无论如何都走不通，才需要重新设计变更表达。

在那之前，你的问题不是 Git 不行，是你放行的变更规模太大。

这也带来一个反直觉的结论：Agent 写得越快，你越该把单次提交切小。产出速度翻十倍，审阅成本按规模线性上升，最后一定是审阅先崩。把提交切小，是你唯一能主动控制的变量。

代码审阅的瓶颈从来不是 diff 工具，
是你放行的变更规模。
