你把一个需求拆成五份，开了五个 Agent 并行跑。理论上五倍速度。

两个小时后，你在手动合并五个互相打架的分支：两个改了同一个配置文件，一个把另一个刚加的函数删了，还有一个"顺利完成了任务"——完成的是上个版本的需求。

单 Agent 两小时能做完的活，五 Agent 用了四个小时，其中三个小时是你在收拾。

⚠️ 多 Agent 不是"把活分出去"，是你把一个单机问题换成了分布式问题。分布式系统所有的经典难题，你一个都躲不掉。

一、三个真实的新问题

问题一：隔离。五个 Agent 共享同一个工作目录，等于五个线程共享同一块可写内存，还没有锁。改同一个文件、改同一份配置、互相覆盖对方的中间产物——这不是偶发，是必然。

问题二：交接。A 的产出是 B 的输入。人和人之间靠默契和口头对齐，Agent 之间没有默契，只有 prompt 里写死的那几句话。格式偏一点，下游就理解偏一层，误差逐级放大。

问题三：审阅。五个 Agent 产出五份 diff，而你的审阅能力一点没变。产出是并行的，审阅是串行的。并行度越高，堵在审阅口的积压越严重。

二、为什么人类的分工搬不过去

很多人搭多 Agent，是照抄人类团队：一个负责想、一个负责写、一个负责审。看起来很专业，实际是负优化。

人类分工成立，靠三个前提：职责边界稳定、能沟通意图、能协商接口。这三条 Agent 一条都不占。

Agent 实例之间没有持续记忆，不会主动对齐，接口只能由你在提示词里预先写死。你以为搭了个团队，实际搭的是几个互不通信的进程。

所以"一个想、一个写、一个审"这套结构，常常只是把同一件事拆成三次不完整的信息传递，每次损失一点，最后质量比单 Agent 还差。

这里有个容易混淆的点：共享上下文不等于共享状态。给所有 Agent 发同一份需求文档，只是让它们起点一致；它们改代码产生的中间状态，彼此依然看不见。真正致命的是后者。

三、社区在往哪个方向补

GitHub 上这半年冒出来的项目，基本都在补上面那三个洞。

Orca 补隔离：把不同编码 Agent 放进各自独立的 git worktree 里运行，结果再集中到一个地方审阅。2026 年 10 月 26 日周榜快照里，它一周新增约 9,622 star。

openrig 补协作：把多个编码 Agent 组装成带角色和共享上下文的持久团队网络，而不是每次开一堆临时会话。

ruflo 补编排：把任务拆解、分发和结果回收做成显式的编排流程，让"谁在干哪一段"这件事可观察，而不是散落在五六个终端窗口里。

注意一个共同点：它们都在做"运行时和协作层"，没有一个是靠"再换一个更强的模型"来解决的。因为这个问题不在模型层。

四、什么时候才真的值得并行

我给你一个可判定的标准，三条同时满足才并行：

① 写集不重叠：子任务改的文件完全不交集
② 产出可独立验收：每个子任务有自己的验收标准，不需要看别人的结果
③ 失败可独立重试：一个挂了不影响其他，也不需要全体重来

场景 建议 理由
同一模块的重构 串行 写集必然重叠，冲突是确定的
不同仓库的独立需求 可并行 零共享状态，合并成本低
只读的调研、检索、梳理 可并行 没有写操作，最多是信息重复
单个复杂需求的质量提升 串行 + 验证回路 加验证比加 Agent 便宜且有效

五、真要上多 Agent，先做这五件事

✅ 先把单 Agent + 验证回路跑通。多 Agent 是优化手段，不是默认架构。单个都跑不稳，并行只会放大问题。

✅ 按"写集"切任务，不按"功能模块"切。功能模块听起来边界清晰，实际改起来全往同一批公共文件里钻。

✅ 交接用结构化契约。文件、JSON、schema，而不是一段自然语言描述。能被机器校验的交接，才叫交接。

✅ 审阅入口合并。所有 Agent 的产出进同一个待审队列，按风险排序，不按提交顺序。否则你永远在审最不急的那个。

✅ 可以设汇总者，但别让它做决策。让它做冲突检测、列清单、标风险。最终"合不合"这个判断留给人。

上并行之前，先算一笔账：并行收益 = 串行耗时 − 并行耗时；并行成本 = 协调开销 + 冲突修复 + 额外审阅。任务越小、耦合越紧，成本越轻易超过收益。十分钟能做完的需求，拆五个 Agent 一定是亏的。

🌱 一个简单的自检：如果你的多 Agent 方案里，没有一个环节负责发现冲突，那冲突就会由你在合并时发现。

六、边界：并行优化的是吞吐，不是质量

这句话值得单独说：多 Agent 能让你在单位时间里产出更多，但不能让每一份产出更好。

所以当你觉得"输出不理想"时，加 Agent 是错的方向——那属于能力和流程问题，要靠上下文、工具、验证回路去解决。加 Agent 只会让你同时得到五份不理想的输出。

反过来，当你已经能稳定得到合格的单份产出、只是嫌慢，并行才真正开始值钱。

多 Agent 解决的是排队问题，
不是能力问题。
