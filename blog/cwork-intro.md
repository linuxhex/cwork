# 用 Claude Code 技能体系，把微服务开发流程焊成一条流水线

> 从需求分析到代码提交，7 个技能自动衔接，多工程并行，逻辑推演替代测试——这就是 cwork。

---

## 一、痛点：微服务开发的手工地狱

做过微服务的人都知道，一个需求往往跨 3-5 个服务：

- **需求分析**：哪个服务改什么？接口契约怎么定？
- **写代码**：主服务改完，依赖服务也要改，来回切目录
- **测试验证**：写单测、跑单测、看覆盖率……
- **提交代码**：每个服务分别 commit + push，分支要对齐，commit message 要统一

传统方式下，这些全靠人肉串联——切目录、写代码、跑测试、提交……一个需求下来，光流程操作就占 30% 时间。

**cwork 的解法：把这套流程焊成一条自动衔接的流水线。**

---

## 二、cwork 是什么

cwork 是一套基于 Claude Code 的技能体系（Skill System），专为微服务开发设计。它包含 **7 个技能**，按需自动衔接：

```
cwork-init       → 初始化工作区（可选，多服务场景才需要）
cwork-implement  → 需求分析 + 编写计划 + 执行计划 + 推演收敛
cwork-test       → 页面自动化测试（Web / 小程序自动识别）
cwork-commit     → 提交所有工程
cwork-doc        → 生成技术方案文档
cwork-bug        → 快速修复 bug
cwork-log        → 日志与链路分析（SLS + ARMS）
```

核心流程自动衔接，**不需要手动发起下一个技能**：

```
init → implement → test（条件触发）→ commit
```

---

## 三、核心技能详解

### 🔧 cwork-implement：六阶段全链路实现

这是 cwork 的核心引擎，包含六个阶段：

#### 阶段 1：需求分析（对话式）

不是一上来就写代码，而是**对话式逐步追问**，沿决策树逐层深入：

```
你：/cwork-implement

AI：这个需求涉及哪些服务？
你：订单服务 + 用户服务

AI：订单服务需要新增什么接口？
你：导出订单列表

AI：用户服务需要提供什么数据？
你：用户基本信息查询

AI：我分析了代码，发现 2 种方案——
  方案 A：订单服务调用户服务 RPC（推荐，改动小）
  方案 B：订单服务直接查用户库（快但耦合高）
你：方案 A
```

**核心原则**：
- **每次只问一个问题**，不一股脑抛出来
- **优先选择题**，附带推荐答案，你只需采纳或否决
- **先探索代码库**，能从代码推断的事实自己查，只把需要你拍板的决策提出来

#### 阶段 2：编写计划

生成完整的实现计划，精确到文件路径和行号：

```markdown
### 任务 1：新增导出接口

**文件：**
- 创建：`src/controller/ExportController.java`
- 修改：`src/service/OrderService.java:45-67`

- [ ] **步骤 1**：在 ExportController 新增 /export 端点
- [ ] **步骤 2**：在 OrderService 新增分页查询方法
- [ ] **步骤 3**：Commit
```

**禁止占位符**——不能写"待定"、"TODO"、"后续实现"。

#### 阶段 3：方案审查

审查计划合理性，业务逻辑推演——**审查通过后才执行，禁止跳过**。

#### 阶段 4：执行计划（多 agent 并行）

这是最爽的部分——**每个服务工程开一个独立 agent 并行执行**：

```
主工程：主 agent 直接处理
  ├─ agent-A 处理 user-service
  ├─ agent-B 处理 order-service
  └─ 并行执行，互不干扰
```

不用手动切目录，不用等一个服务改完再改下一个。

#### 阶段 5：推演收敛（逻辑推演替代测试）

**这是 cwork 最独特的创新**——用逻辑推演替代单元测试：

```
Round 1: 推演 → 发现问题 → 修复
Round 2: 推演 → 发现问题 → 修复
Round N: 推演 → 无问题 → 收敛 ✅
```

推演覆盖 6 个维度：

| 检查项 | 说明 |
|--------|------|
| 主路径闭环 | 正常流程是否完整执行 |
| 异常处理 | 超时、失败、重试是否处理 |
| 契约一致 | 跨工程接口字段是否匹配 |
| 边界条件 | 空数据、大数据量、特殊字符 |
| 并发防重 | 重复请求是否防重 |
| 数据一致性 | 跨工程数据是否一致 |

最多 5 轮，连续 2 轮无问题即收敛。

#### 阶段 6：编译/构建检查

推演收敛后，跑一次编译/构建确认代码能过——**通过后才进入提交**。

---

### 🧪 cwork-test：自动识别项目类型的页面测试

启动时自动检测项目类型，走对应链路：

| 项目类型 | 识别条件 | 驱动引擎 |
|---------|---------|---------|
| 微信小程序 | 存在 `project.config.json` 且含 appid | miniprogram-automator |
| Web 应用 | 存在 `package.json` | ego-browser / page-agent |

流程：环境准备 → 测试规划 → 测试执行 → 结果报告

测试失败时自动诊断并重试，P0 场景全通过才进入提交。

---

### 📤 cwork-commit：不确认，直接提交

推演收敛后自动提交所有服务工程，**不问"确认提交吗"**——因为该验证的都验证过了。

多服务场景下，每个服务独立生成 commit message，独立 commit + push：

```
user-service:
  → git commit -m "【用户导出】<add> 新增用户数据查询接口"
  → git push ✓

order-service:
  → git commit -m "【用户导出】<add> 新增订单查询接口"
  → git push ✓
```

**HARD GATE**：分支不一致禁止提交，任一工程有未完成任务禁止提交。

---

### 📝 cwork-doc：自动生成技术方案文档

两种模式：
- **模式一**：已有需求文档 → 读取 + 分析代码改动 → 生成技术方案
- **模式二**：对话式需求分析 → 从代码出发聊需求 → 生成技术方案

输出标准技术方案：需求说明 → 详细设计 → 改动影响范围 → 稳定性设计（灰度降级 + 监控告警 + 防资损）→ checkList

**核心原则：不改动代码，只生成文档。**

---

### 🐛 cwork-bug：5 阶段快速修复

```
阶段 1/5：代码分析 → 理解上下文
阶段 2/5：问题咨询 → 对话式了解问题现象和期望
阶段 3/5：问题定位 → 定位根因
阶段 4/5：修复代码 → 修复 + 同步写注释
阶段 5/5：推演验证 → 逻辑推演 + 编译检查
```

流程简短高效，对话式逐步深入，实际代码优先。

---

### 🔍 cwork-log：从代码出发的日志与链路分析

这是最硬核的技能——**直接查阿里云 SLS 日志 + ARMS 链路**，从代码出发排查线上问题。

#### 3 步走

```
阶段 1：探查代码
  → 读服务地图定位工程目录
  → 读代码提取接口/类名/日志关键字
  → 能自己定的直接做，不问

阶段 2：搜日志 + 链路
  → 用提取的关键字查 SLS
  → 命中取 traceId → 拉链路 span 树
  → 代码 ↔ 日志 ↔ span 对应

阶段 3：结论输出
  → 汇总上下游、P99、耗时点、根因建议
  → 带文件:行号 + 证据，不猜
```

#### 内置脚本（直接 curl 阿里云 API）

| 脚本 | 用途 |
|------|------|
| `sls_query.sh` | 查 SLS 日志（list/logs/count） |
| `arms_apps.sh` | 列 ARMS 应用拿 pid |
| `arms_traces.sh` | 接口性能（QPS/平均耗时/错误率/P99） |
| `arms_trace.sh` | 单条链路 span 树（上下游/耗时点） |

#### 实战示例

```
你：/cwork-log 查 order-prod 最近15分钟 /xxx 接口耗时

AI：（自动读代码 → 提取关键字 → 查 ARMS → 拉链路）

═══════════════════════════════════════════════════════
【日志与链路分析完成】
═══════════════════════════════════════════════════════

目标服务：order-prod (prod)
时间范围：最近 15 分钟

接口性能：
- /open/charging/updateOrder：QPS 32418，平均 25ms，错误率 0%
- 整体调用链 P99 = 186ms

链路与耗时点：
- 上下游：gateway → order-prod → user-prod → MySQL
- 耗时点：MySQL 查询 142ms（占 76%）

根因假设：订单表缺少复合索引，建议加 (user_id, status) 索引
═══════════════════════════════════════════════════════
```

#### logstore 索引（固化，不每次遍历）

prod 有 212 个日志库、uat 143 个，但命名规律明确。cwork-log 内置完整分类索引：

- **`all`** = 聚合库，默认入口，绝大多数业务日志都在这
- **`device-*`** = 充电桩协议日志（盛弘/施恩/华为/鲁能）
- **`ctp-*`** = 车队日志（⚠️ 不在 all，未接入 ARMS）
- **`emp-*`/`ems-*`** = 能源管理
- **`<服务>3-out`** = 对外接口出入站

不用每次 `list` 212 个库再挑——查索引表，秒级定位。

## 四、与传统方式对比

| 维度 | 传统方式 | cwork |
|------|---------|-------|
| 需求分析 | 无结构，口头沟通 | 对话式决策树，逐步深入 |
| 编写计划 | 无 | 精确到文件:行号，禁止占位符 |
| 多工程处理 | 手动切目录，串行 | 多 agent 并行 |
| 测试验证 | 写单测、跑单测 | 逻辑推演替代（6 维覆盖） |
| 提交代码 | 每个服务手动 commit + push | 自动提交，分支一致性校验 |
| 日志排查 | 登阿里云控制台，手动查 | 从代码出发，脚本直查 API |
| 流程衔接 | 人肉串联 | 自动衔接，无需手动发起 |

## 五、核心设计理念

### 1. 能力调度纪律

**在做任何事之前，先检查是否有适用的能力/流程。哪怕只有 1% 的可能性适用，也必须先调用。**

这不是建议，是铁律。"加个功能"不意味着跳过需求分析，"修个 bug"不意味着跳过根因调查。

### 2. 探索先于提问

在问用户任何问题之前，先自己查代码、查 commit、查文档。能从代码推断的事实自己查清楚，只把**需要用户拍板的决策**提出来。

### 3. 多服务独立视角

每个服务的文档站在**本服务的定位角度**记录，禁止在主服务文档中记录依赖服务的改动。

### 4. 全中文交互

所有对话、分析、结论使用中文。仅在命令、路径、参数名、代码处保留英文。

## 六、使用方式

```bash
# 安装
cp -r cwork/skills/* ~/.claude/skills/

# 使用（在 Claude Code 中）
/cwork-init        # 多服务场景初始化
/cwork-implement   # 开始实现需求
/cwork-test        # 跑页面测试
/cwork-commit      # 提交代码
/cwork-doc         # 生成技术方案
/cwork-bug         # 修 bug
/cwork-log         # 查日志/链路
```

## 七、适合谁用

- **微服务开发者**：多工程并行、接口契约校验、自动提交——省掉 30% 流程操作
- **线上问题排查者**：从代码出发，一键查日志+链路，不用登控制台
- **技术方案写作者**：自动提取接口定义+数据模型，生成标准技术方案
- **Bug 修复者**：5 阶段快速定位修复，推演验证保证质量
