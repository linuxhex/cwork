# cwork 自改进机制规范

## 概述

cwork 自改进系统从 Hermes Agent 的学习循环理念吸收，适配 cwork 的技能内容层架构。核心思想：**高门槛自动改进，改动必须验证，验证通过自动同步**。

**设计原则**：
1. **高门槛** — 只有绝对确定的改进才执行，宁可漏改不可错改
2. **全自动** — 不需要人工介入，满足条件即执行
3. **必验证** — 改动后必须验证（分发 + 检查），验证失败即回滚
4. **必同步** — 验证通过后自动同步到所有 agent 目录
5. **可追溯** — 技能变更有 CHANGELOG，版本可查

## 学习触发层（When to Learn）

### 触发时机

| 触发点 | 触发条件 | 学习类型 |
|--------|---------|---------|
| 任务完成 | implement/bug/do 收敛后 | 技能改进提议 |
| 踩坑时刻 | 遇到 known-pits 未记录的问题 | 模式库更新 |
| 重复动作 | 同一件事做了 ≥3 次 | 抽象建议 |
| 用户纠正 | 用户说「不对」「错了」 | 行为修正 |
| 每日首次 | `.last_analysis_date` ≠ 今天 | 跨会话扫描 |

### 任务完成自检清单（implement/bug/do 结束时必做）

回顾本次任务，执行以下检查：

**第一层：门槛检查（必须全部满足才进入改进）**

1. **确定性检查**
   - 改进点是否有明确证据（代码报错/文档与实际不符/模式库缺失导致重复踩坑）？
   - 是否属于推测性改进（「可能更好」「也许可以」）？→ 推测性改进一律跳过

2. **影响范围检查**
   - 改动是否只影响单个技能文件？→ 可以自动改
   - 改动是否影响多个技能或公共规范？→ 需要更谨慎，必须有明确证据

3. **可逆性检查**
   - 改动是否容易回滚（只是加一段文字/一个模式）？→ 可以自动改
   - 改动是否难以回滚（删除大段内容/重构结构）？→ 跳过，记入 USAGE_NOTES 待人工处理

**第二层：执行改进（门槛通过后自动执行）**

4. **已知坑命中**
   - 本次踩到 known-pits 没记录的问题 → 补充到 pattern-library.md
   - 补充后验证：分发 + 检查无语法错误

5. **重复动作检测**
   - 本次重复做某件事 ≥3 次 → 提取为可复用模式 MXXX
   - 提取后验证：分发 + 检查无语法错误

6. **文档偏差修正**
   - 技能文档与实际明显不符 → 修正文档
   - 修正后验证：分发 + 检查无语法错误

7. **新反模式发现**
   - 本次发现明确错误做法 → 加入反模式 PXXX
   - 加入后验证：分发 + 检查无语法错误

**第三层：同步与记录**

8. **自动同步**
   - 验证通过后，执行 `node bin/cwork.js --tool auto` 同步到所有 agent
   - 同步后检查输出无错误

9. **记录变更**
   - 更新对应技能的 CHANGELOG.md
   - 更新技能 frontmatter 的 version 字段为最新 commit hash
   - 提交代码（commit message 格式：`【cwork 自改进】<类型> 改动简述`）

**无改进时**：不输出任何内容，静默跳过。

## 改进门槛细则（HARD GATE）

### 允许自动改进的情况

1. **模式库补充**
   - 本次踩到的坑在 pattern-library.md 中确实不存在
   - 坑的现象、根因、解法都明确
   - 补充后不影响现有模式

2. **文档明显错误**
   - 文档描述与实际代码/行为明显不符
   - 有明确证据（如代码截图/日志/实测结果）
   - 修正后不会引入歧义

3. **HARD GATE 补充**
   - 本次发现的错误做法具有普遍性（其他 技能也可能遇到）
   - 错误做法的后果明确（导致失败/浪费时间/产生错误结果）
   - 补充的 HARD GATE 条目清晰可执行

### 禁止自动改进的情况

1. **推测性改进**
   - 「可能更好」「也许可以」「建议考虑」→ 一律跳过
   - 记录到 USAGE_NOTES 待人工评估

2. **大范围重构**
   - 涉及多个技能文件的结构调整
   - 涉及核心流程的改动
   - 记录到 USAGE_NOTES 待人工评估

3. **删除内容**
   - 删除现有 HARD GATE 条目
   - 删除现有模式
   - 删除大段文档内容
   - 记录到 USAGE_NOTES 待人工评估

4. **新增技能/脚本**
   - 创建新的技能文件
   - 创建新的脚本文件
   - 记录到 USAGE_NOTES 待人工评估

## 验证流程（改动后必做）

### 验证步骤

```markdown
1. 语法检查
   - 改动的 Markdown 文件无语法错误
   - 改动的脚本文件可执行（如有）

2. 分发检查
   - 执行 `node bin/cwork.js --tool auto`
   - 检查输出无错误
   - 检查所有 agent 目录已更新

3. 引用检查
   - 改动的文件被其他文件引用时，引用路径正确
   - 新增的模式/反模式编号不重复

4. 提交检查
   - git status 确认改动文件
   - git commit 格式正确
   - version 字段更新为最新 commit hash
```

### 验证失败处理

- 分发失败 → 回滚改动（`git checkout -- <file>`）
- 引用错误 → 修正引用后重新验证
- 提交失败 → 记录到 USAGE_NOTES 待人工处理

## 知识提取层（What to Capture）

### 知识类型

| 类型 | 来源 | 存储位置 | 格式 |
|------|------|---------|------|
| 踩坑记录 | 任务中遇到的问题 | `pattern-library.md` | 问题 + 根因 + 解法 |
| 重复动作 | 做了 ≥3 次的事 | `pattern-library.md` | 动作 + 抽象建议 |
| 用户偏好 | 用户的纠正/选择 | `memory/user-preferences.md` | 偏好维度 + 值 |
| 技能偏差 | 文档与实际不符 | `pattern-library.md` | 技能 + 偏差描述 |
| 新反模式 | 错误做法 | `pattern-library.md` | 反模式 + 正确做法 |

### 踩坑记录格式

```markdown
### [YYYY-MM-DD] [skill-name] 问题简述

**现象**：具体表现
**根因**：为什么会这样
**解法**：怎么解决的
**可借鉴**：一句话总结教训
**关联模式**：[[模式名]]（如果有）
```

### 重复动作检测规则

当发现同一类动作在本次任务中出现 ≥3 次时：
1. 记录动作模式
2. 提取为可复用模式 MXXX
3. 验证 + 同步 + 记录

### 用户偏好提取规则

当用户纠正 agent 行为时：
1. 记录纠正内容
2. 判断是否为偏好（vs 一次性要求）
3. 如果是偏好，更新 `memory/user-preferences.md`

## 模式识别层（Pattern Recognition）

### 模式库位置

`skills/common/pattern-library.md` — 从实战中提取的可复用模式/反模式。

### 模式匹配规则

遇到新问题时：
1. 提取关键字（技能名 + 现象词）
2. 在本文件中搜索相似模式
3. 如果命中：
   - 检查解法是否适用
   - 适用 → 直接应用，记入本次任务日志
   - 不适用 → 创建新模式或修正现有模式
4. 如果未命中：
   - 解决问题后提取新模式
   - 验证门槛 → 通过则自动加入模式库

## 记忆检索层（Memory & Retrieval）

### 会话索引位置

`skills/common/session-index.md` — 历史任务的结构化索引。

### 检索触发条件

遇到以下情况时自动检索会话索引：
1. 踩到 known-pits 未记录的问题
2. 同一类问题第二次出现
3. 用户说「之前遇到过」
4. 任务结束自检时发现新模式 → 先检索是否已有类似记录

### 检索输出格式

```
[历史参考] YYYY-MM-DD 遇到过类似任务：
- 任务类型：xxx
- 关键决策：yyy
- 踩坑：zzz
- 会话详情：session-index.md#日期-任务名
```

### 检索后动作

- 命中且解法适用 → 直接参考，避免重复踩坑
- 命中但解法不适用 → 记录本次新解法，提议更新索引
- 未命中 → 完成任务后提议新增索引条目

## 与现有机制的整合

| 现有机制 | 整合方式 |
|---------|---------|
| USAGE_NOTES.md | 保留，作为「待分析」暂存区；不符合自动改进门槛的记入这里 |
| feedback-loop.md | 保留，每日分析时扫描模式库更新需求 |
| known-pits | 迁入模式库的反模式区，保持引用兼容 |
| memory/ | 保留，扩展用户偏好维度 |

## 技能演化追踪

### 变更日志

每个技能维护 `CHANGELOG.md`（自动追加），格式：

```markdown
# [skill-name] 变更日志

## [YYYY-MM-DD] 变更简述

**触发**：为什么改
**改动**：改了什么
**影响**：有什么效果
```

### 版本号规则

版本 = 最后一次实质性改动的 commit hash 前 7 位。

技能文件头部加版本标记：
```yaml
---
name: cwork-implement
version: ade2911
---
```
