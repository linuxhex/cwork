## 内部阶段一：需求分析（brainstorming）

<HARD-GATE>
在你展示设计方案、与用户达成一致理解（shared understanding）并获得用户批准之前，不要编写任何代码或采取任何实现行动。
</HARD-GATE>

### 检查清单（按顺序执行）

1. **探索项目上下文** — 检查文件、文档、最近的 commit
2. **提供视觉伴侣**（如果主题涉及视觉问题）— Read 同目录 `visual-companion.md`，这是一条独立的消息
3. **提出澄清问题** — 每次一个，了解目的/约束/成功标准
4. **提出 2-3 种方案** — 附带权衡分析和你的推荐
5. **展示设计** — 按复杂度分节展示，每节展示后获得用户批准
6. **多服务需求拆分** — 站在每个服务视角分析需求（见上方详细流程）
7. **记录分析结果** — 写入各服务的 analysis.md

### 核心原则

- **区分事实与决策** — 能从代码、commit、现有文档自查的事实，自己查清楚，不要拿去问用户；只有需要用户拍板的决策才提出来
- **每题给推荐答案** — 每个澄清问题都附上基于代码的推荐答案，用户只需采纳、否决或微调
- **按依赖顺序提问** — 识别决策之间的依赖关系，按依赖顺序逐个解决；前置决策未定时，不问依赖它的后续决策
- **每次一个问题** — 不要同时抛出多个问题
- **优先选择题** — 在可能的情况下比开放式问题更容易回答
- **严格遵循 YAGNI** — 从所有设计中移除不必要的功能
- **探索替代方案** — 在做决定之前始终提出 2-3 种方案
- **增量验证** — 展示设计，获得批准后再继续
- **保持灵活** — 有不明确的地方就回头澄清
- **多服务独立视角** — 每个服务从自己的职责定位理解需求
- **方案质询 + 决策树遍历** — 见「核心操作系统·编码思维方法论」，在需求分析中同样适用

### 反模式："这个太简单了，不需要设计"

每个项目都要经过这个流程。设计可以很简短（对于真正简单的项目几句话就够了），但你必须展示出来并获得批准。

### 流程详述

#### 探索项目上下文

首先查看当前项目状态：
- 文件结构
- **实际运行的代码**（最重要，注释和文档是次要的，代码才是最真实的）
- 文档（仅供参考，以实际代码为准）
- 最近的 commit
- 现有代码模式
- **代码图谱（必须先探测）**：进入探索后，第一步跑 `codegraph status`（在 `/Users/caomunian/Work/code-projects` 下执行）。有符号数（已索引）→ **必须用** `codegraph explore "<要理解的流程>"` / `codegraph query <符号>` 摸现状，比散乱 grep+Read 更省 context、更准确；无符号（未索引）→ 回退 grep/Read，不阻塞

**⚠️ 关键：不是只探测一次，而是每次找代码都要探测**

- **错误理解**：开始时探测一次，后面就可以随便用 grep+Read
- **正确理解**：需求分析、编写计划、执行实现过程中，**每次**查代码结构、查调用链、查接口实现，都要先探测 codegraph，已索引就必须用
- **持续监督**：每一步输出都必须有 `[codegraph]` 标签，没有就是偷懒

🔍 **输出标签（强制）**：每次调 codegraph 必须在对话里打一行 `[codegraph]` 标签让走向可见——探测后 `🔍 [codegraph] status → 已索引(N符号)，用图谱` 或 `→ 未索引，回退 grep+Read`；查询时 `🔍 [codegraph] <命令> <目标> → <目的>`。**无 `[codegraph]` 标签 = 没走 codegraph，视为偷懒。**

**重要原则**：
- 注释和文档可能过时或不准确，实际运行的代码才是最真实的
- 分析需求时，优先阅读和理解实际代码逻辑
- 文档和注释仅作为辅助参考，不能替代代码分析
- 如果文档描述与代码实现不一致，以代码为准

在提出详细问题之前，先评估范围：如果需求描述了多个独立子系统，立即指出这一点。

如果项目规模过大，帮助用户分解为子项目：
- 有哪些独立的部分
- 它们之间有什么关系
- 应该按什么顺序构建

#### 提出澄清问题

先自查再提问——能从代码、commit、现有文档推断出来的，自己查清楚，不要问用户；只把推断不出来、需要用户拍板的决策提出来。

每次提一个问题来完善想法：
- **每题附推荐答案** — 基于代码给出你的推荐，用户只需采纳、否决或微调
- 尽量使用选择题，开放式问题也可以
- 每条消息只提一个问题
- 重点理解：目的、约束、成功标准

#### 深度追问（需求分析质询）

在用户回答了澄清问题后，不要直接跳到方案探索。沿着决策树的每个分支逐层追问，直到双方对每个决策点达成共识：

**追问规则：**
1. **逐层追问**：沿决策树每个分支往下走，理清各项决策之间的依赖关系，有些选择必须等前一个问题确定了才能回答，按先后顺序逐个问清楚
2. **每个问题带推荐答案**：不要抛空问题，每次追问都要给出你的推荐及理由
3. **一次只问一个**：等用户回答了再问下一个，一次抛出多个问题会让人不知所措
4. **事实自己查，决策归用户**：能通过查看代码、文件系统、工具等找到的事实，直接去查，不用问用户；但决策是用户的，每个决策都要等用户拍板
5. **确认前不动手**：确认双方理解一致之前，不进入方案探索

**示例：**
```
用户："导出格式用 CSV"
追问："为什么选 CSV？我建议先看下现有导出逻辑。"
  →（查代码发现已有 Excel 导出模块）
追问："现有代码已有 Excel 导出模块，建议复用。选 CSV 还是复用 Excel？我推荐复用 Excel。"
用户："复用 Excel 吧"
追问："数据量方面，现有导出最大支持多少行？我查一下。"
  →（查数据库发现最大表 50 万行）
追问："最大表 50 万行，Excel 单 sheet 上限 104 万行，够用。是否需要分页导出？建议暂不加，先满足基本需求。"
用户："好，先不加"
```

**追问原则：**
- 只追问关键决策点，不追问琐碎细节
- 追问是为了暴露风险和遗漏，不是为了否定用户
- 沿决策树追问，每层得出明确结论后再进入下一层
- 追问中发现的约束和风险，记录到 analysis.md

#### 探索方案

提出 2-3 种不同的方案及其权衡：
- 以对话的方式展示选项，附上你的推荐和理由
- 先展示你推荐的方案并解释原因

#### 展示设计

一旦你认为理解了要构建的内容，就展示设计：
- 每个部分的篇幅与其复杂度匹配
- 每个部分展示后询问是否正确
- 涵盖：架构、组件、数据流、错误处理
- 随时准备回头澄清不明确的地方

**面向隔离和清晰的设计**：
- 将系统拆分为更小的单元，每个单元有一个明确的职责
- 通过定义良好的接口通信
- 对于每个单元，你应该能回答：它做什么，如何使用，它依赖什么？

**在现有代码库中工作**：
- 在提出更改之前先探索现有结构。遵循现有模式。
- 如果现有代码存在影响当前工作的问题，在设计中包含有针对性的改进
- 不要提议无关的重构

#### 前端设计感知（条件触发）

如果需求涉及前端新工程或新页面，在展示设计时额外完成：

1. **确认设计方向**：通过设计面试（见「前端设计辅助」章节）逐步确认产品类型、用户、风格
2. **检测技术栈**：检查 `package.json` 或向用户确认前端框架
3. **输出设计简报**：写入 `DESIGN-BRIEF.md`
4. **展示给用户确认**：将色彩、字体、间距方案展示给用户

**注意**：此步骤仅在触发前端设计辅助时执行，纯后端需求跳过。

#### 多服务需求拆分

当需求涉及多个服务时：

1. **主服务分析**
   - 从主服务视角理解需求
   - 确定需要调用哪些依赖服务
   - 定义调用契约（请求/响应结构）
   - 写入主服务的 analysis.md

2. **依赖服务分析**（每个依赖服务独立分析）
   - 从本服务视角理解需求
   - 确定需要提供什么接口
   - 确定需要查询/修改什么数据
   - 写入本服务的 analysis.md

3. **契约对齐**
   - 检查主服务的调用契约和依赖服务的响应契约是否一致
   - 检查字段名、类型、必填性是否匹配
   - 发现不一致时协调修正
   - **代码图谱核对（必须先探测）**：先跑 `codegraph status` 确认已索引，然后用 `codegraph callers`/`callees`/`node` 验证主服务调用的符号与依赖服务提供的符号真实对得上（不只看文档契约）；未索引跳过

**配置查询联动（cwork-config）** — 需求沟通时核对配置

需求沟通时常需确认某服务某环境的配置真值（开关/阈值/地址/参数），调用 `cwork-config` 查 Nacos：

**触发条件**（任一）：
- 需确认某功能开关是否开启
- 需确认某阈值/参数的实际值
- 需确认某服务地址/依赖地址
- 需求涉及配置变更

**联动流程**：
```
需求涉及配置？
  ├─ 否 → 直接继续需求分析
  └─ 是 → 调用 cwork-config 查配置：
           1. 定 env + 服务名
           2. nacos_query.sh get/search 查配置真值
           3. 配置 ↔ 需求对应，确认实现方案
```

**联动原则**：cwork-config 管「核对 Nacos 配置真值」，拿到配置后回到需求分析继续。

## 内部阶段二：编写计划（writing-plans）

编写全面的实现计划，记录工程师需要知道的一切：每个任务要修改哪些文件、代码。将整个计划拆成小步骤任务。

**计划保存位置**：
- 主工程：`docs/requirements/{requirement_key}/plan.md`
- 依赖工程：`依赖工程/docs/requirements/{requirement_key}/plan.md`

### analysis.md 格式规范

**格式要求**：
- 使用清晰的标题层级（##、###）
- 使用表格展示结构化信息
- 使用列表展示要点
- 使用引用块（>）强调重要信息
- 适当使用分隔线分节
- **禁止包含代码片段、代码示例、接口定义代码**

**推荐格式**：

```markdown
# 需求分析（{服务名称}视角）

## 需求概述
> 一句话概括需求目标

## 业务背景
- 背景说明
- 触发条件
- 预期效果

## 本服务职责
| 职责项 | 说明 |
|--------|------|
| xxx | xxx |

## 依赖关系

### 调用方（谁调用我）
| 调用方 | 接口 | 用途 |
|--------|------|------|
| xxx服务 | /api/xxx | 获取xxx数据 |

### 被调用方（我调用谁）
| 服务 | 接口 | 用途 | 关键字段 |
|------|------|------|---------|
| xxx服务 | /api/xxx | 获取xxx | userId, type |

## 数据契约

### 请求结构
| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| userId | String | 是 | 用户ID |

### 响应结构
| 字段 | 类型 | 说明 |
|------|------|------|
| data | Object | 返回数据 |

## 改动范围
- [ ] 新增接口：/api/xxx
- [ ] 修改逻辑：xxx处理

## 风险与注意
- ⚠️ 风险点1：xxx
- 💡 注意事项：xxx
```

**格式要求**：
- 使用清晰的标题层级
- 每个任务有明确的文件列表

- 代码片段仅用于说明核心实现思路，不超过 10 行
- 复杂逻辑用文字描述 + 简短代码示意

**推荐格式**：

### 范围检查

如果规格涵盖了多个独立子系统，建议将其拆分为独立的计划——每个子系统一个。

### 文件结构

在定义任务之前，先列出将要创建或修改的文件以及每个文件的职责：

- 设计边界清晰、接口定义良好的单元
- 每个文件应有一个明确的职责
- 一起变更的文件应放在一起
- 在现有代码库中，遵循已有模式

### 小步骤任务粒度

**每步是一个操作（2-5 分钟）：**
- "实现代码" - 一步

**注意**：implement 过程中不做代码提交，提交由 commit 技能统一处理。

### 计划文档头部

```markdown
# [功能名称] 实现计划

**目标：** [一句话描述要构建什么]

**架构：** [2-3 句话描述方案]

```

### 任务结构

````markdown

**文件：**
- 创建：`exact/path/to/file.py`
- 修改：`exact/path/to/existing.py:123-145`

- [ ] **步骤 1：实现代码**

```python
def function(input):
    return expected
```
````

### 禁止占位符

每个步骤都必须包含工程师需要的实际内容。以下是**计划缺陷**——绝不要写出来：
- "待定"、"TODO"、"后续实现"、"补充细节"
- "添加适当的错误处理" / "添加验证" / "处理边界情况"
- "类似任务 N"（重复代码）
- 只描述做什么而不展示怎么做的步骤
- 引用了未在任何任务中定义的类型、函数或方法

### 多服务计划编写

为每个服务独立编写计划：

1. **主服务计划**
   - 基于主服务的 analysis.md
   - 包含主服务的所有任务
   - 写入主服务的 plan.md

2. **依赖服务计划**（每个依赖服务独立编写）
   - 基于本服务的 analysis.md
   - 包含本服务的所有任务
   - 写入本服务的 plan.md

### 前端设计任务（条件触发）

如果涉及前端新工程/新页面，plan.md 中**必须包含**以下前置任务：

| 任务 | 说明 |
|------|------|
| 设计简报确认 | 完成设计面试，输出 DESIGN-BRIEF.md |
| 基础样式实现 | 色彩变量、字体、间距 token 写入全局样式 |
| 页面布局骨架 | 基于设计简报实现页面整体布局结构 |
| 核心组件实现 | 按设计简报风格实现关键 UI 组件 |

**任务顺序**：设计系统确认 → 基础样式 → 布局骨架 → 核心组件 → 业务逻辑

## 内部阶段三：方案审查（plan-review）

**编写计划后，执行计划前，必须进行方案审查。**

### 审查目标

确保计划合理、完整、可行，避免执行过程中发现问题导致返工。

### 审查维度

**业务逻辑推演（必须）**：

| 审查项 | 说明 |
|--------|------|
| 业务流程推演 | 模拟业务主流程执行，验证流程是否闭环 |
| 业务规则推演 | 模拟业务规则判断，验证条件分支是否完整 |
| 业务状态推演 | 模拟状态流转，验证状态机是否正确 |
| 业务数据推演 | 模拟数据流转，验证数据是否完整 |
| 业务异常推演 | 模拟异常场景，验证异常处理是否完整 |
| 业务边界推演 | 模拟边界条件，验证边界处理是否正确 |

**技术方案审查（必须）**：

| 审查项 | 说明 |
|--------|------|
| 文件路径正确 | 文件路径是否存在，是否合理 |
| 依赖关系合理 | 模块依赖是否合理，是否存在循环依赖 |
| 技术方案可行 | 技术选型是否合理，是否满足需求 |
| 接口契约一致 | 前后端接口契约是否一致，字段是否匹配 |
| 配置项完整 | 配置项是否完整，默认值是否合理 |

**执行可行性审查（必须）**：

| 审查项 | 说明 |
|--------|------|
| 步骤无遗漏 | 任务步骤是否完整，是否有遗漏 |
| 步骤无冲突 | 任务之间是否有冲突，顺序是否合理 |
| 资源可获取 | 依赖资源是否可获取，权限是否足够 |
| 环境可支持 | 运行环境是否支持，版本是否兼容 |

**前端设计审查（条件触发，仅前端新工程/新页面）**：

| 审查项 | 说明 |
|--------|------|
| 设计简报应用 | 是否按 DESIGN-BRIEF.md 实现色彩/字体/间距 |
| 无障碍基线 | 对比度、键盘导航、aria 是否满足 WCAG 2.1 AA |
| 响应式 | 移动优先、断点是否一致、无横向滚动 |

### 代码质量准则（强制）

#### 代码简化原则

**保护功能**：只优化代码质量，绝不改变业务逻辑。重构后行为必须一致。

**用卫语句减少嵌套**：深层嵌套用提前返回拉平（反：3 层 if 嵌套；正：`if (user == null) return "unknown"; if (!user.isActive()) return "inactive"; return user.isPremium() ? "premium" : "basic";`）。

**聚焦范围**：只优化当前任务涉及的代码，不搞"顺手改一下"。

**避免过度工程**：不为假想的未来需求设计。三行相似代码好过一个提前抽象的通用框架。

**改进优先级**：零风险改进（变量重命名、消除冗余）→ 结构改进（减少嵌套、提取函数）→ 风格对齐（匹配项目已有编码风格）。

#### 完成验证铁律

**执行顺序**：识别验证命令 → 运行完整命令 → 阅读输出+退出码 → 判断是否证实 → 才能声称。

#### 系统化调试铁律

**未完成根因调查，禁止提出修复方案。** 四阶段：根因调查（读错误→稳定复现→检查近期改动→追踪数据流）→ 模式分析（对比正常/异常代码）→ 假设验证（一个假设+最小改动，不叠加）→ 实施修复（先复现测试+单一修复+验证）。

**三振出局**：修复尝试 ≥ 3 次 → 停下来质疑架构，和用户讨论。

**危险信号**（立即回到根因调查）："先临时修一下"、"试试改 X 看看"、"同时改几个地方"、"大概是 X"。

### 自问自答质询（推演质询）

每轮推演检查完成后，对推演结论进行自我质询。全程自问自答，不涉及用户——自己扮演质疑者，自己回答，自己决策：

**质询规则：**
1. **逐层自问**：对每个推演结论，沿决策树逐分支追问"如果这里错了呢？"
2. **每个自问带论据和自答**：提出质疑后，自己给出回答——"我怀疑这里有盲点，原因是 X，我决定去验证 Y"
3. **一次只质疑一个结论**：逐个结论质询和自答，不要一次性罗列所有疑点
4. **事实自己查**：能通过代码/工具验证的，直接查，不要空猜
5. **自己闭环**：每个质疑必须自己给出结论——是补充检查项还是确认可靠，不留给用户判断

**自问模板：**
1. "我是否因为思维惯性跳过了某些检查？"
2. "如果这个推演结论是错的，最可能错在哪里？"
3. "有没有我刻意回避的不确定点？"

**自问自答循环：**
```
for each 推演结论:

    自答：我怀疑/确认...，原因是...
    如果发现盲点：
        自己补充检查项，修复问题，不问用户
    如果确认可靠：
        记录：经自问验证，结论可靠
```

**与推演循环的关系：**
- 自问自答嵌入推演循环内，每轮推演后执行

- 工程目录下存在 `package.json`
- `package.json` 中存在 `build` 脚本
- 本次实现中有代码文件的新增或修改

### Maven 检测

```bash
if command -v mvn &> /dev/null; then
    MAVEN_CMD="mvn"
elif [ -x "/Applications/IntelliJ IDEA.app/Contents/plugins/maven/lib/maven3/bin/mvn" ]; then
    MAVEN_CMD="/Applications/IntelliJ IDEA.app/Contents/plugins/maven/lib/maven3/bin/mvn"
else
    MAVEN_CMD=""
fi
```

### 执行流程

```
对于每个有改动的工程：
    1. 进入工程目录
    2. 判断工程类型：
       - Java 工程（存在 pom.xml）：
         - 检测 Maven 是否可用
         - 执行 mvn compile -DskipTests
         - 编译成功 → 记录到 changes.md
         - 编译失败 → 输出错误，修复，重新编译
       - 前端工程（存在 package.json 且有 build 脚本）：
         - 检测包管理器（npm/yarn/pnpm）
         - 执行构建命令（npm run build / yarn build / pnpm build）
         - 构建成功 → 记录到 changes.md
         - 构建失败 → 输出错误，修复，重新构建
       - 其他工程：
         - 输出提示：非 Java/前端工程，跳过编译/构建检查
    3. 继续下一个工程
```

### 编译/构建失败处理

**如果任一工程编译/构建失败：**

1. 输出错误信息
2. 记录到 changes.md：
   ```markdown
   ## 编译/构建错误
   - 工程：{工程名称}
   - 类型：{Java/前端}
   - 错误：{错误信息}
   ```
3. 修复问题
4. 重新执行编译/构建
5. 通过后才算完成

### 多服务场景

**每个有代码改动的工程都要单独执行编译/构建检查：**

```
═══════════════════════════════════════════════════════════════
【编译/构建检查】开始执行
═══════════════════════════════════════════════════════════════

main-service (Java):
  → mvn compile -DskipTests
  → 编译通过 ✓

user-service (Java):
  → mvn compile -DskipTests
  → 编译通过 ✓

web-frontend (前端):
  → npm run build
  → 构建通过 ✓

admin-frontend (前端):
  → yarn build
  → 构建通过 ✓

other-service (非 Java/前端):
  → 跳过

═══════════════════════════════════════════════════════════════
【编译/构建检查】全部通过
═══════════════════════════════════════════════════════════════
```
