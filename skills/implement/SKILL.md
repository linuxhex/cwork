# 实现

## 概述

`implement` 包含三个子步骤：
1. **需求分析**：对话式，逐步提问（来自 superpowers-zh brainstorming）
2. **执行实现**：多 agent 并行，一把梭哈
3. **推演收敛**：自动循环，一把梭哈

## 语言约束
- 对话、分析、结论、提示默认使用中文
- 仅在必要处保留英文：命令、路径、参数名、状态码、字段名

## HARD GATE
- workflow-state 不是 init 或 implement，禁止执行
- 未完成需求分析，禁止执行实现
- 推演未收敛，禁止进入 commit

## 第一步：需求分析（对话式，逐步提问）

<HARD-GATE>
在你展示设计方案并获得用户批准之前，不要编写任何代码或采取任何实现行动。
</HARD-GATE>

### 检查清单（按顺序执行）

1. **探索项目上下文** — 检查文件、文档、最近的 commit
2. **提供视觉伴侣**（如果主题涉及视觉问题）— 这是一条独立的消息
3. **提出澄清问题** — 每次一个，了解目的/约束/成功标准
4. **提出 2-3 种方案** — 附带权衡分析和你的推荐
5. **展示设计** — 按复杂度分节展示，每节展示后获得用户批准
6. **记录分析结果** — 更新 workflow-state.json

### 核心原则

- **每次一个问题** — 不要同时抛出多个问题
- **优先选择题** — 在可能的情况下比开放式问题更容易回答
- **严格遵循 YAGNI** — 从所有设计中移除不必要的功能
- **探索替代方案** — 在做决定之前始终提出 2-3 种方案
- **增量验证** — 展示设计，获得批准后再继续
- **保持灵活** — 有不明确的地方就回头澄清

### 反模式："这个太简单了，不需要设计"

每个项目都要经过这个流程。一个待办事项列表、一个单函数工具、一个配置变更——全都需要。"简单"的项目恰恰是未经检验的假设造成最多浪费的地方。设计可以很简短（对于真正简单的项目几句话就够了），但你必须展示出来并获得批准。

### 流程详述

#### 探索项目上下文

首先查看当前项目状态：
- 文件结构
- 文档
- 最近的 commit
- 现有代码模式

在提出详细问题之前，先评估范围：如果需求描述了多个独立子系统，立即指出这一点。不要花时间用问题去细化一个需要先拆分的项目。

如果项目规模过大，帮助用户分解为子项目：
- 有哪些独立的部分
- 它们之间有什么关系
- 应该按什么顺序构建

#### 提出澄清问题

每次提一个问题来完善想法：
- 尽量使用选择题，开放式问题也可以
- 每条消息只提一个问题——如果一个主题需要更多探索，拆分成多个问题
- 重点理解：目的、约束、成功标准

#### 探索方案

提出 2-3 种不同的方案及其权衡：
- 以对话的方式展示选项，附上你的推荐和理由
- 先展示你推荐的方案并解释原因

#### 展示设计

一旦你认为理解了要构建的内容，就展示设计：
- 每个部分的篇幅与其复杂度匹配：简单的几句话，复杂的最多 200-300 字
- 每个部分展示后询问是否正确
- 涵盖：架构、组件、数据流、错误处理、测试
- 随时准备回头澄清不明确的地方

**面向隔离和清晰的设计**：
- 将系统拆分为更小的单元，每个单元有一个明确的职责
- 通过定义良好的接口通信，可以独立理解和测试
- 对于每个单元，你应该能回答：它做什么，如何使用，它依赖什么？

**在现有代码库中工作**：
- 在提出更改之前先探索现有结构。遵循现有模式。
- 如果现有代码存在影响当前工作的问题，在设计中包含有针对性的改进
- 不要提议无关的重构。专注于服务当前目标的事情。

### 视觉伴侣

当你预计后续问题会涉及视觉内容（原型、布局、图表）时，提供一次以获得同意：

> "我们接下来讨论的一些内容，如果能在浏览器中展示给你看可能会更直观。我可以在讨论过程中为你制作原型、图表、对比图和其他视觉材料。要试试吗？"

**此提议必须是一条独立的消息。** 等待用户回复后再继续。

详细指南见：`skills/implement/visual-companion.md`

## 第二步：执行实现（一把梭哈，多 agent 并行）

### 分析结果汇总
根据对话结果，汇总：
- 核心问题列表
- 改动范围
- 契约影响
- 风险点

### 分派任务（每个工程独立记录）

```
主工程：主 agent 直接处理
- 从主工程视角记录分析和改动
- 写入主工程的 workflow-state.json

依赖工程：每个依赖工程开一个独立 agent
- agent-A 处理 user-service
  → 从 user-service 视角记录分析和改动
  → 写入 user-service 的 workflow-state.json
- agent-B 处理 order-service
  → 从 order-service 视角记录分析和改动
  → 写入 order-service 的 workflow-state.json
- 并行执行，互不干扰
```

### 每个工程的记录视角

每个工程从自己的视角记录：

```json
// 主工程 workflow-state.json
{
  "phase": "implement",
  "perspective": "main",
  "analysis": {
    "本工程改动": ["新增导出接口", "修改查询逻辑"],
    "对依赖工程的调用": ["调用 user-service 的 xxx 接口"],
    "契约变更": ["新增字段 xxx"]
  }
}

// user-service workflow-state.json
{
  "phase": "implement",
  "perspective": "dependency",
  "analysis": {
    "本工程改动": ["新增 xxx 接口实现"],
    "被主工程调用": ["主工程调用 xxx 接口"],
    "契约变更": ["响应新增字段 xxx"]
  }
}
```

**好处**：
- 不需要来回切换目录
- 并行执行，速度快
- 每个 agent 只关注一个工程
- 每个工程有独立的视角记录

## 第三步：推演收敛（一把梭哈，自动循环）

主 agent 统一推演（跨工程）：

```
round = 1
while round <= 5:
    推演：
    - 主路径闭环？
    - 异常处理？
    - 契约一致？（跨工程）
    - 边界条件？
    - 并发防重？
    
    if 有问题:
        修复
        round += 1
    elif 上轮也无问题:
        break
    else:
        round += 1
```

## 输出

每个工程生成 3 个文件：

### workflow-state.json（内部状态，不提交）

```json
{
  "phase": "implement",
  "requirement_key": "用户导出",
  "feature_branch": "feature_userExport",
  "updated_at": "2026-05-17 12:00:00"
}
```

**加入 .gitignore**：`docs/requirements/*/workflow-state.json`
