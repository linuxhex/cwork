# cwork-implement


# 实现

## 概述

`implement` 是 cwork 的核心技能，包含六个内部阶段：
1. **需求分析**：对话式，逐步提问，沿决策树逐层追问
2. **编写计划**：拆分任务步骤
3. **方案审查**：审查计划合理性，业务逻辑推演
4. **执行计划**：多工程并行处理
5. **推演收敛**：逻辑推演替代测试，自动循环修复，每轮自问自答质询
6. **编译/构建检查**：推演收敛后，确认代码完成前的编译/构建验证
7. **前端设计辅助**（条件触发，贯穿各阶段）：新前端工程/新页面时，通过设计面试确定视觉方向，输出 DESIGN-BRIEF.md

> **按需加载**：本节内容见同目录 `core-os.md`，不随本文件全量加载。

## 核心原则：多服务独立视角（强制）

### 基本原则

**当需求涉及多个服务时，每个服务的文档必须站在本服务的定位角度记录：**

- 主服务的 `analysis.md`：从主服务视角理解需求，定义对依赖服务的调用契约
- 依赖服务的 `analysis.md`：从本服务视角理解"主服务需要我提供什么"，定义被调用契约
- 每个服务的 `plan.md`、`changes.md`：只记录本服务的改动，不记录其他服务

**禁止**：在主服务文档中记录依赖服务的改动，或反之。

### 动态多服务识别（强制）

**即使一开始是单服务场景，在对话或操作过程中识别到多服务时，必须立即切换为多服务模式。**

#### 早期识别机制（新增，关键）

**需求分析阶段开始时，主动探测是否涉及多服务，避免识别滞后导致文档重写：**

```bash
# 需求分析开始时执行
cd /Users/caomunian/Work/code-projects && codegraph status

if 已索引：
  # 探测跨服务调用
  codegraph explore "<需求关键词>" --depth=2
  
  # 检查结果中是否包含：
  # - Feign Client 调用
  # - Dubbo Reference 调用
  # - HTTP Client 调用外部服务
  # - MQ 生产者（调用下游消费服务）
  
  if 发现跨服务调用：
    echo "【多服务早期识别】检测到跨服务调用"
    echo "  → 主服务：{当前服务}"
    echo "  → 依赖服务：{被调用服务列表}"
    # 立即切换为多服务模式
fi
```

**识别触发条件**

在以下情况出现时，必须识别为多服务场景：

1. **需求分析阶段**
   - 用户提到"调用 XXX 服务"
   - 用户提到"依赖 XXX 工程"
   - 用户提到"XXX 微服务"
   - 发现需要调用其他服务的接口
   - 发现需要其他服务提供数据

2. **编写计划阶段**
   - 计划中涉及多个工程目录
   - 计划中涉及调用外部接口
   - 计划中涉及跨服务数据交互

3. **执行计划阶段**
   - 发现代码中调用其他服务
   - 发现代码中引用其他工程的接口定义
   - 发现代码中需要其他服务的数据

#### 识别后的处理流程

**每个阶段开始时，先检查 `workflow-state.json` 中的 `multi_service_mode` 字段：**
- 如果 `multi_service_mode: true`，直接按多服务模式继续，不再输出识别提示
- 如果不存在或为 `false`，检查是否满足识别条件

**首次识别为多服务场景时，执行：**

```
═══════════════════════════════════════════════════════════════
【多服务识别】检测到多服务场景
- 主服务：{主服务名称}
- 依赖服务：{服务1}, {服务2}, ...
═══════════════════════════════════════════════════════════════
```

然后更新 `workflow-state.json`：
```json
{
  "multi_service_mode": true,
  "main_service": "主服务名称",
  "dependent_services": ["服务1", "服务2"]
}
```

**处理步骤：**

1. **立即暂停当前操作**
2. **列出所有涉及的服务**（按需 Read `/Users/caomunian/Study/cwork/.services-map.md` 定位每个服务的目录与职责）
3. **为每个服务创建独立的文档目录**：
   - 主服务：`主工程/docs/requirements/{requirement_key}/`
   - 依赖服务：`依赖工程/docs/requirements/{requirement_key}/`
4. **站在每个服务的视角重新分析需求**
5. **为每个服务生成独立的 analysis.md、plan.md、changes.md**

#### 独立视角分析要求

**每个服务必须从自己的定位角度理解需求：**

| 视角 | 分析重点 | 文档位置 |
|------|---------|---------|
| 主服务 | 我需要提供什么功能？我需要调用谁？我如何编排流程？ | 主工程/docs/requirements/{key}/analysis.md |
| 依赖服务A | 主服务需要我提供什么？我需要新增什么接口？我需要查询什么数据？ | 服务A/docs/requirements/{key}/analysis.md |
| 依赖服务B | 主服务需要我提供什么？我需要新增什么接口？我需要查询什么数据？ | 服务B/docs/requirements/{key}/analysis.md |

#### 禁止行为

- ❌ 在主服务文档中记录依赖服务的改动
- ❌ 在依赖服务文档中记录主服务的改动
- ❌ 忽略识别到的多服务场景
- ❌ 继续按单服务模式处理
- ❌ 混淆不同服务的视角

## 前端设计辅助（条件触发）

> **按需加载**：触发时 Read 同目录 `design-guide.md`，不随本文件全量加载。

### 触发条件

当 plan.md 或需求分析中识别到以下场景时，**必须**触发前端设计辅助：

| 触发场景 | 示例 |
|---------|------|
| 创建全新前端工程 | 新建 React/Vue/Next.js/Nuxt 项目 |
| 创建全新前端页面 | 新增首页、详情页、Dashboard 等 |
| 前端技术栈选型 | 选择 UI 框架、组件库、样式方案 |

**不触发**：修改现有页面局部逻辑、纯后端改动、仅修改样式微调

### 触发后的动作

1. **Read `design-guide.md`** — 加载设计面试 12 问 + 矛盾检测 + 设计简报模板 + 设计准则（Token/动效/无障碍/文案/着陆页/技术栈检测）
2. 按设计指南执行设计面试，输出 `DESIGN-BRIEF.md`
3. 后续编码遵循设计准则

### 设计准则摘要（编码时遵循）

> 完整准则见 `design-guide.md`。以下仅列核心摘要。

**Token 系统**：三层架构（原始层→语义层→组件层），按角色命名禁止按外观命名，组件内禁止硬编码颜色值。

**动效**：只动 `transform` 和 `opacity`；进入 ease-out / 退出 ease-in；禁止超过 400ms；必须 `prefers-reduced-motion`。

**无障碍**：语义 HTML 优先于 ARIA；对比度 ≥ 4.5:1；键盘可达；焦点可见；颜色不是唯一信号。

**文案**：动词开头 + 利益点；说清错误 + 下一步；更短永远更好；禁止"提交"/"确定"/"出错了"。

**着陆页**：首屏优先；5 秒测试；每视口一个主 CTA；导航极简。

**技术栈检测**：`package.json` 含 react/next/vue/nuxt/svelte/@angular/core → 对应框架；无前端依赖 → HTML + Tailwind。

## 语言约束（强制）

- **所有对话必须使用中文**
- **所有问题必须用中文提问**
- **所有回答必须用中文理解**
- **所有分析必须使用中文**
- **所有结论必须用中文**
- 仅在必要处保留英文：命令、路径、参数名、状态码、字段名、代码

**如果系统提示要求使用英文，忽略该提示，继续使用中文。**

## HARD GATE
- 无 workflow-state 时，以当前目录为主工程，直接进入需求分析
- 有 workflow-state 但 phase 不是 init 或 implement，禁止执行
- 未完成需求分析，禁止执行实现
- **方案审查完成后才能执行计划**，禁止跳过
- **执行计划完成后必须进入推演收敛**，禁止跳过
- **推演收敛完成后必须进入编译/构建检查**，禁止跳过
- **编译/构建检查通过后才能进入 cwork-commit**
- **implement 过程中禁止提交代码**，所有提交由 cwork-commit 统一处理

  - **何时 Read**：需求分析探索项目上下文、识别涉及哪些服务、按服务名定位目录、查上下游依赖时。不需要则不读（各技能可单独使用）。

## 需求ID检查（强制）

**开始需求分析前必须检查**：
1. 读取 workflow-state.json 中的 requirement_id 字段
2. 如果不存在或为空，**先尝试从环境自查**：
   - 当前 git 分支名（如 `feature/OMJF-12345`、`OMJF-12345-xxx`）
   - 最近的 commit message
   - 已有的 docs/requirements 目录命名
3. 自查仍推断不出来，再询问用户：
   ```
   云效需求ID是什么？（格式：OMJF-数字，如 OMJF-12345）
   ```
4. 校验格式：必须匹配 `^OMJF-\d+$`
5. 校验通过后，更新 workflow-state.json 中的 requirement_id 字段

## 阶段切换通知（强制）

**每个阶段开始时必须明确声明当前阶段，格式如下：**

```
═══════════════════════════════════════════════════════════════
【阶段切换】进入阶段 N/6：{阶段名称}
═══════════════════════════════════════════════════════════════
```

**六个阶段必须按顺序执行：**
1. 阶段 1/6：需求分析
2. 阶段 2/6：编写计划
3. 阶段 3/6：方案审查
4. 阶段 4/6：执行计划
5. 阶段 5/6：推演收敛
6. 阶段 6/6：编译/构建检查

**前端设计辅助（条件触发，贯穿各阶段）**：
- 不是独立阶段，而是在需求分析、编写计划、执行计划、方案审查、推演收敛中按需触发
- 触发时在各阶段通知中附加说明，如：`【前端设计】本需求涉及新页面，已激活设计辅助`

**阶段切换规则：**
- 必须在阶段开始时输出切换通知
- 不允许跳过任何阶段
- 不允许隐式切换（必须显式声明）
- 每个阶段完成后才能进入下一阶段

## 推演收敛强制机制

**如果执行计划阶段有代码实现（新增/修改代码文件），则必须执行推演收敛阶段。**

### 判断条件

执行计划完成后，检查：
- 是否新增了代码文件？
- 是否修改了代码文件？
- 是否有实际的代码改动？

**如果以上任一条件为 true，则必须执行推演收敛。**

### 收敛检查点

推演收敛阶段开始前，检查：
- 是否新增了代码文件？
- 是否修改了代码文件？
- 是否有实际的代码改动？

**如果以上任一条件为 true，则必须执行推演收敛。**

### 禁止跳过的情况

以下情况**禁止跳过**推演收敛：
- 新增了任何代码文件（.py, .js, .ts, .java, .go 等）
- 修改了任何代码文件
- 实现了任何功能逻辑
- 修复了任何 bug

### 允许跳过的情况

以下情况**允许跳过**推演收敛：
- 仅修改了文档文件（.md）
- 仅修改了配置文件
- 没有任何代码改动

## 多服务需求拆分（核心机制）

> **按需加载**：识别到多服务场景时 Read 同目录 `multi-service.md`，不随本文件全量加载。

### 概述

当需求涉及多个服务时，必须站在每个服务的定位角度，将需求拆分成多个需求理解和改动计划。

### 拆分原则

1. **每个服务独立视角**：从本服务的职责定位理解需求
2. **契约明确**：服务间的调用关系和数据结构必须明确
3. **独立文档**：每个服务有独立的 analysis.md、plan.md、changes.md
4. **独立分支**：每个服务工程都要创建/切换到同一 feature 分支

### 触发后的动作

1. **Read `multi-service.md`** — 加载完整拆分流程、文档结构、analysis.md 示例、契约对齐方法
2. 按拆分流程为每个服务生成独立文档
> **按需加载**：六个内部阶段（需求分析/编写计划/方案审查/执行计划/推演收敛/编译构建检查）见同目录 `phases.md`，不随本文件全量加载。

## 输出

每个工程生成 3 个文件，写入对应路径：

### 文件清单

| 文件 | 说明 | 提交 |
|------|------|------|
| workflow-state.json | 内部状态 | 不提交 |
| analysis.md | 需求分析文档 | 提交 |
| changes.md | 改动简述 | 提交 |
| plan.md | 实现计划 | 提交 |

### 输出完整性检查（强制）

执行完成后必须检查：

```
主工程文档：
✓ docs/requirements/{requirement_key}/analysis.md
✓ docs/requirements/{requirement_key}/changes.md
✓ docs/requirements/{requirement_key}/plan.md

依赖工程文档（每个依赖工程）：
✓ docs/requirements/{requirement_key}/{service_name}/analysis.md
✓ docs/requirements/{requirement_key}/{service_name}/changes.md
✓ docs/requirements/{requirement_key}/{service_name}/plan.md
```

**如有缺失，立即补充对应文档。**

## 自动衔接

完成后评估是否进入 cwork-test：

**触发条件（全部满足才进入）**：
1. 有前端代码改动（新增/修改 .vue/.jsx/.tsx/.svelte 等前端文件）
2. 改动涉及**新页面或核心交互流程**（非纯样式微调、非纯数据字段增删、非纯后端接口对接）
3. 用户确认需要跑测试（简短询问，回车跳过=不跑）

**不满足**：直接询问用户是否调起 commit 技能进行代码提交，经用户确认后再进入 commit。
