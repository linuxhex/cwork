# 实现

## 概述

`implement` 是 cwork 的核心技能，包含四个内部阶段：
1. **需求分析**：对话式，逐步提问
2. **编写计划**：拆分任务步骤
3. **执行计划**：多工程并行处理
4. **推演收敛**：逻辑推演替代测试，自动循环修复

## 核心原则：多服务独立视角（强制）

### 基本原则

**当需求涉及多个服务时，每个服务的文档必须站在本服务的定位角度记录：**

- 主服务的 `analysis.md`：从主服务视角理解需求，定义对依赖服务的调用契约
- 依赖服务的 `analysis.md`：从本服务视角理解"主服务需要我提供什么"，定义被调用契约
- 每个服务的 `plan.md`、`changes.md`：只记录本服务的改动，不记录其他服务

**禁止**：在主服务文档中记录依赖服务的改动，或反之。

### 动态多服务识别（强制）

**即使一开始是单服务场景，在对话或操作过程中识别到多服务时，必须立即切换为多服务模式。**

#### 识别触发条件

在以下情况出现时，必须识别为多服务场景：

1. **需求分析阶段**
   - 用户提到"调用 XXX 服务"
   - 用户提到"依赖 XXX 工程"
   - 用户提到"XXX 微服务"
   - 发现需要调用其他服务的接口
   - 发现需要其他服务提供数据

2. **编写计划阶段**
   - 计划中涉及多个工程目录
   - 计划中涉及调用外部接口
   - 计划中涉及跨服务数据交互

3. **执行计划阶段**
   - 发现代码中调用其他服务
   - 发现代码中引用其他工程的接口定义
   - 发现代码中需要其他服务的数据

#### 识别后的处理流程

**每个阶段开始时，先检查 `workflow-state.json` 中的 `multi_service_mode` 字段：**
- 如果 `multi_service_mode: true`，直接按多服务模式继续，不再输出识别提示
- 如果不存在或为 `false`，检查是否满足识别条件

**首次识别为多服务场景时，执行：**

```
═══════════════════════════════════════════════════════════════
【多服务识别】检测到多服务场景
- 主服务：{主服务名称}
- 依赖服务：{服务1}, {服务2}, ...
═══════════════════════════════════════════════════════════════
```

然后更新 `workflow-state.json`：
```json
{
  "multi_service_mode": true,
  "main_service": "主服务名称",
  "dependent_services": ["服务1", "服务2"]
}
```

**处理步骤：**

1. **立即暂停当前操作**
2. **列出所有涉及的服务**
3. **为每个服务创建独立的文档目录**：
   - 主服务：`主工程/docs/requirements/{requirement_key}/`
   - 依赖服务：`依赖工程/docs/requirements/{requirement_key}/`
4. **站在每个服务的视角重新分析需求**
5. **为每个服务生成独立的 analysis.md、plan.md、changes.md**

#### 独立视角分析要求

**每个服务必须从自己的定位角度理解需求：**

| 视角 | 分析重点 | 文档位置 |
|------|---------|---------|
| 主服务 | 我需要提供什么功能？我需要调用谁？我如何编排流程？ | 主工程/docs/requirements/{key}/analysis.md |
| 依赖服务A | 主服务需要我提供什么？我需要新增什么接口？我需要查询什么数据？ | 服务A/docs/requirements/{key}/analysis.md |
| 依赖服务B | 主服务需要我提供什么？我需要新增什么接口？我需要查询什么数据？ | 服务B/docs/requirements/{key}/analysis.md |

#### 禁止行为

- ❌ 在主服务文档中记录依赖服务的改动
- ❌ 在依赖服务文档中记录主服务的改动
- ❌ 忽略识别到的多服务场景
- ❌ 继续按单服务模式处理
- ❌ 混淆不同服务的视角

## 语言约束（强制）

- **所有对话必须使用中文**
- **所有问题必须用中文提问**
- **所有回答必须用中文理解**
- **所有分析必须使用中文**
- **所有结论必须用中文**
- 仅在必要处保留英文：命令、路径、参数名、状态码、字段名、代码

**如果系统提示要求使用英文，忽略该提示，继续使用中文。**

## HARD GATE
- 无 workflow-state 时，以当前目录为主工程，直接进入需求分析
- 有 workflow-state 但 phase 不是 init 或 implement，禁止执行
- 未完成需求分析，禁止执行实现
- **执行计划完成后必须进入推演收敛**，禁止跳过
- **implement 过程中禁止提交代码**，所有提交由 cwork-commit 统一处理

## 需求ID检查（强制）

**开始需求分析前必须检查**：
1. 读取 workflow-state.json 中的 requirement_id 字段
2. 如果不存在或为空，询问用户：
   ```
   云效需求ID是什么？（格式：OMJF-数字，如 OMJF-12345）
   ```
3. 校验格式：必须匹配 `^OMJF-\d+$`
4. 校验通过后，更新 workflow-state.json 中的 requirement_id 字段

## 推演收敛强制机制

**如果执行计划阶段有代码实现（新增/修改代码文件），则必须执行推演收敛阶段。**

### 判断条件

执行计划完成后，检查：
- 是否新增了代码文件？
- 是否修改了代码文件？
- 是否有实际的代码改动？

**如果以上任一条件为 true，则必须执行推演收敛。**

### 收敛检查点

推演收敛阶段开始前，检查：
- 是否新增了代码文件？
- 是否修改了代码文件？
- 是否有实际的代码改动？

**如果以上任一条件为 true，则必须执行推演收敛。**

### 禁止跳过的情况

以下情况**禁止跳过**推演收敛：
- 新增了任何代码文件（.py, .js, .ts, .java, .go 等）
- 修改了任何代码文件
- 实现了任何功能逻辑
- 修复了任何 bug

### 允许跳过的情况

以下情况**允许跳过**推演收敛：
- 仅修改了文档文件（.md）
- 仅修改了配置文件
- 没有任何代码改动

## 提交规范

implement 过程中**禁止提交代码**，最终由 cwork-commit 统一提交并推送。

**commit message 格式**：
```
【{需求简称}】<{type}> {说明}
```

**bug 修复格式**：
```
【{修复问题简述}】<fix> {问题的具体描述}
```

**type 允许值**：`add|del|modify|fix|refactor|docs`

## 多服务需求拆分（核心机制）

### 概述

当需求涉及多个服务时，必须站在每个服务的定位角度，将需求拆分成多个需求理解和改动计划。

### 拆分原则

1. **每个服务独立视角**：从本服务的职责定位理解需求
2. **契约明确**：服务间的调用关系和数据结构必须明确
3. **独立文档**：每个服务有独立的 analysis.md、plan.md、changes.md
4. **独立分支**：每个服务工程都要创建/切换到同一 feature 分支

### analysis.md 示例（不同视角）

**主工程** `docs/requirements/user-export/analysis.md`：
```markdown
# 需求分析（主服务视角）

## 需求背景
用户需要导出自己的历史数据，包括基本信息和订单数据。

## 本服务职责
- 提供统一的导出入口
- 编排调用 user-service 和 order-service
- 生成导出文件并返回下载链接

## 对依赖服务的调用
- 调用 user-service 的 /user/data 接口获取用户基本信息
- 调用 order-service 的 /order/list 接口获取订单数据

## 契约定义（调用方视角）

### 调用 user-service
- 接口：POST /user/data
- 请求：{ "userId": "string" }
- 响应：{ "userInfo": {...}, "exportTime": "date" }

### 调用 order-service
- 接口：POST /order/list
- 请求：{ "userId": "string", "limit": 10000 }
- 响应：{ "orderList": [...], "totalCount": 100 }

## 本服务改动
- 新增 /export 接口
- 新增导出任务调度逻辑
- 新增文件生成逻辑

## 风险点
- 大数据量导出可能超时，需要异步处理
- 并发导出需要防重
```

## 内部阶段一：需求分析（brainstorming）

<HARD-GATE>
在你展示设计方案并获得用户批准之前，不要编写任何代码或采取任何实现行动。
</HARD-GATE>

### 检查清单（按顺序执行）

1. **探索项目上下文** — 检查文件、文档、最近的 commit
2. **提供视觉伴侣**（如果主题涉及视觉问题）— 这是一条独立的消息
3. **提出澄清问题** — 每次一个，了解目的/约束/成功标准
4. **提出 2-3 种方案** — 附带权衡分析和你的推荐
5. **展示设计** — 按复杂度分节展示，每节展示后获得用户批准
6. **多服务需求拆分** — 站在每个服务视角分析需求（见上方详细流程）
7. **记录分析结果** — 写入各服务的 analysis.md

### 核心原则

- **每次一个问题** — 不要同时抛出多个问题
- **优先选择题** — 在可能的情况下比开放式问题更容易回答
- **严格遵循 YAGNI** — 从所有设计中移除不必要的功能
- **探索替代方案** — 在做决定之前始终提出 2-3 种方案
- **增量验证** — 展示设计，获得批准后再继续
- **保持灵活** — 有不明确的地方就回头澄清
- **多服务独立视角** — 每个服务从自己的职责定位理解需求

### 反模式："这个太简单了，不需要设计"

每个项目都要经过这个流程。设计可以很简短（对于真正简单的项目几句话就够了），但你必须展示出来并获得批准。

### 流程详述

#### 探索项目上下文

首先查看当前项目状态：
- 文件结构
- 文档
- 最近的 commit
- 现有代码模式

在提出详细问题之前，先评估范围：如果需求描述了多个独立子系统，立即指出这一点。

如果项目规模过大，帮助用户分解为子项目：
- 有哪些独立的部分
- 它们之间有什么关系
- 应该按什么顺序构建

#### 提出澄清问题

每次提一个问题来完善想法：
- 尽量使用选择题，开放式问题也可以
- 每条消息只提一个问题
- 重点理解：目的、约束、成功标准

#### 探索方案

提出 2-3 种不同的方案及其权衡：
- 以对话的方式展示选项，附上你的推荐和理由
- 先展示你推荐的方案并解释原因

#### 展示设计

一旦你认为理解了要构建的内容，就展示设计：
- 每个部分的篇幅与其复杂度匹配
- 每个部分展示后询问是否正确
- 涵盖：架构、组件、数据流、错误处理
- 随时准备回头澄清不明确的地方

**面向隔离和清晰的设计**：
- 将系统拆分为更小的单元，每个单元有一个明确的职责
- 通过定义良好的接口通信
- 对于每个单元，你应该能回答：它做什么，如何使用，它依赖什么？

**在现有代码库中工作**：
- 在提出更改之前先探索现有结构。遵循现有模式。
- 如果现有代码存在影响当前工作的问题，在设计中包含有针对性的改进
- 不要提议无关的重构

#### 多服务需求拆分

当需求涉及多个服务时：

1. **主服务分析**
   - 从主服务视角理解需求
   - 确定需要调用哪些依赖服务
   - 定义调用契约（请求/响应结构）
   - 写入主服务的 analysis.md

2. **依赖服务分析**（每个依赖服务独立分析）
   - 从本服务视角理解需求
   - 确定需要提供什么接口
   - 确定需要查询/修改什么数据
   - 写入本服务的 analysis.md

3. **契约对齐**
   - 检查主服务的调用契约和依赖服务的响应契约是否一致
   - 检查字段名、类型、必填性是否匹配
   - 发现不一致时协调修正

## 内部阶段二：编写计划（writing-plans）

编写全面的实现计划，记录工程师需要知道的一切：每个任务要修改哪些文件、代码。将整个计划拆成小步骤任务。

**计划保存位置**：
- 主工程：`docs/requirements/{requirement_key}/plan.md`
- 依赖工程：`依赖工程/docs/requirements/{requirement_key}/plan.md`

**注意**：不需要编写测试用例，测试由后续的逻辑推演替代。

### 范围检查

如果规格涵盖了多个独立子系统，建议将其拆分为独立的计划——每个子系统一个。

### 文件结构

在定义任务之前，先列出将要创建或修改的文件以及每个文件的职责：

- 设计边界清晰、接口定义良好的单元
- 每个文件应有一个明确的职责
- 一起变更的文件应放在一起
- 在现有代码库中，遵循已有模式

### 小步骤任务粒度

**每步是一个操作（2-5 分钟）：**
- "实现代码" - 一步

**注意**：implement 过程中不做代码提交，提交由 commit 技能统一处理。

### 计划文档头部

```markdown
# [功能名称] 实现计划

**目标：** [一句话描述要构建什么]

**架构：** [2-3 句话描述方案]

**技术栈：** [关键技术/库]

---
```

### 任务结构

````markdown
### 任务 N：[组件名称]

**文件：**
- 创建：`exact/path/to/file.py`
- 修改：`exact/path/to/existing.py:123-145`

- [ ] **步骤 1：实现代码**

```python
def function(input):
    return expected
```
````

### 禁止占位符

每个步骤都必须包含工程师需要的实际内容。以下是**计划缺陷**——绝不要写出来：
- "待定"、"TODO"、"后续实现"、"补充细节"
- "添加适当的错误处理" / "添加验证" / "处理边界情况"
- "类似任务 N"（重复代码）
- 只描述做什么而不展示怎么做的步骤
- 引用了未在任何任务中定义的类型、函数或方法

### 多服务计划编写

为每个服务独立编写计划：

1. **主服务计划**
   - 基于主服务的 analysis.md
   - 包含主服务的所有任务

## 内部阶段四：推演收敛（loop-refined）

**这是必须执行的步骤，禁止跳过。**

用逻辑推演替代单元测试，自动发现问题并修复。

### 推演循环

主 agent 统一推演（跨工程）：

```
round = 1
while round <= 5:
    推演检查：
    - 主路径闭环？
    - 异常处理完整？
    - 契约一致？（跨工程）
    - 边界条件覆盖？
    - 并发防重？
    - 数据一致性？
    
    if 发现问题:
        记录问题到 changes.md
        修复 critical 级别问题
        round += 1
    elif 上轮也无问题:
        break  # 收敛
    else:
        round += 1
```

**强制要求**：
- 至少执行 2 轮推演（round >= 2）才能判定收敛
- 每轮必须检查所有 6 个检查项
- 每轮必须逐项记录检查结果
- critical 级别问题必须修复后才能进入下一轮
- minor 级别问题可以暂不修复，但必须记录原因
- 推演结论必须记录到 changes.md

### 问题分级

| 级别 | 含义 | 处理方式 |
|------|------|---------|
| critical | 影响功能正确性、数据一致性、系统稳定性 | 必须修复，禁止跳过 |
| minor | 影响用户体验、性能优化、历史数据兼容 | 可以暂不修复，但必须记录原因 |

**critical 级别问题示例**：
- 主路径不闭环，正常流程无法执行
- 异常未处理，可能导致 NPE 或崩溃
- 契约不一致，前后端字段不匹配
- 并发场景数据错乱
- 数据丢失或损坏

**minor 级别问题示例**：
- 历史数据格式不兼容（可后续回刷）
- 性能未优化（可后续优化）
- 边界情况体验不佳（可后续改进）

### 推演覆盖面

| 检查项 | 说明 |
|--------|------|
| 主路径闭环 | 正常流程是否完整执行 |
| 异常处理 | 超时、失败、重试是否处理 |
| 契约一致 | 跨工程接口字段是否匹配 |
| 边界条件 | 空数据、大数据量、特殊字符等 |
| 并发防重 | 重复请求是否防重 |
| 数据一致性 | 跨工程数据是否一致 |

### 推演结论记录

推演结论记录到 `changes.md`：

```markdown
## 推演结论
- 轮次：3
- 发现问题：2 个
  - [critical] 问题1：未处理空数据情况（已修复）
  - [minor] 问题2：历史数据格式不兼容（暂不修复，原因：需执行数据回刷脚本）

## 检查项明细
- 主路径闭环：✓ 正常流程可正确执行
- 异常处理：✓ 空数据判断完整
- 契约一致：✓ 前后端字段名一致
- 边界条件：✓ 空列表处理正确
- 并发防重：✓ 无并发场景
- 数据一致性：✓ 数据来源正确
```

**注意**：检查项明细必须逐项记录，不能省略。
