# 实现

## 概述

`implement` 是 cwork 的核心技能，包含六个内部阶段：
1. **需求分析**：对话式，逐步提问，沿决策树逐层追问
2. **编写计划**：拆分任务步骤
3. **方案审查**：审查计划合理性，业务逻辑推演
4. **执行计划**：多工程并行处理
5. **推演收敛**：逻辑推演替代测试，自动循环修复，每轮自问自答质询
6. **编译/构建检查**：推演收敛后，确认代码完成前的编译/构建验证
7. **前端设计辅助**（条件触发，贯穿各阶段）：新前端工程/新页面时，通过设计面试确定视觉方向，输出 DESIGN-BRIEF.md

## 核心操作系统

以下两条原则是 implement 的操作系统，贯穿所有阶段，优先级高于一切具体流程。

### 一、能力调度纪律

**在做任何事之前，先检查是否有适用的能力/流程。哪怕只有 1% 的可能性适用，也必须先调用。**

这不是建议，是铁律。如果你正在做的事有对应的方法论，你没有选择——必须用它。

#### 调度流程

```
收到任务
  → 是否有适用的流程/能力？（哪怕 1%）
    → 是：先调用它，再响应
    → 否：正常响应
```

**流程类能力优先于实现类能力**：
- "我们要构建 X" → 先做需求分析，再进入实现
- "修这个 bug" → 先做根因调查，再动手修
- "加个功能" → 先澄清需求，再写代码

#### 危险信号——你在合理化跳过

以下想法出现时，**立即停下来**——你正在逃避纪律：

| 想法 | 现实 |
|------|------|
| "这只是个简单问题" | 简单问题会变复杂。检查流程。 |
| "我先了解一下上下文" | 流程告诉你怎么了解。先检查流程。 |
| "我先快速看一下代码" | 代码缺少对话上下文。先检查流程。 |
| "这不需要正式流程" | 如果有适用的流程，就用它。 |
| "流程太重了" | 简单的事会变复杂。用它。 |
| "我先做这一件事" | 做事之前先检查。 |
| "我记得流程是什么" | 流程会演进。读当前版本。 |
| "这个不算任务" | 任何行动都是任务。检查流程。 |

#### 指令优先级

1. **用户明确指令**（agents.md、直接请求）— 最高优先级
2. **本操作系统中的流程纪律** — 覆盖默认行为
3. **默认行为** — 最低优先级

用户说 WHAT，流程决定 HOW。"加个功能" 不意味着跳过需求分析。

### 二、编码思维方法论

**先探索代码库，再提方案。先解决前置决策，再推进后续决策。对每个假设追问到底。**

#### 探索先于提问

在问用户任何问题之前，先自己查：
- 读代码、读 commit、读现有文档
- 能从代码推断的事实，自己查清楚
- 只把**需要用户拍板的决策**提出来
- 每个问题都附上基于代码的推荐答案

#### 决策树遍历

把方案拆成决策树，按依赖顺序逐个解决：

```
方案
  ├─ 决策 A（前置）
  │   ├─ 选项 1：权衡...
  │   └─ 选项 2：权衡...
  ├─ 决策 B（依赖 A）
  │   ├─ 选项 1：权衡...
  │   └─ 选项 2：权衡...
  └─ 决策 C（依赖 A、B）
```

**规则**：
- 每个决策点列出选项和权衡，解决后再进入下一个
- **不要跳步**——前置决策未定时，后续决策可能全部作废
- 按依赖顺序排列，不按方便程度

#### 方案质询

对每个方案决策，追问其隐含假设和潜在风险：

- 用户说"简单做就行" → 追问"简单到什么程度？哪些边界可以不管？"
- 用户给了方向 → 先检查代码库是否已有相关实现，有则复用，无则再讨论新建
- 方案看起来合理 → 追问"什么情况下这个方案会失败？"

#### 每次一个决策

- 不要同时抛出多个问题
- 优先选择题，开放式问题次之
- 每题给推荐答案，用户只需采纳、否决或微调
- 区分事实与决策：能从代码自查的事实自己查，只有需要拍板的决策才提出来

### 三、两者的协同

```
任务进入
  │
  ├─ 能力调度：有适用的流程吗？→ 有则先调用
  │
  ├─ 探索代码库：先自己查，再提问
  │
  ├─ 决策树遍历：拆解决策，按依赖顺序逐个解决
  │     │
  │     ├─ 每个决策：方案质询（追问假设和风险）
  │     ├─ 每个决策：给推荐答案 + 选项权衡
  │     └─ 每次一个，不跳步
  │
  ├─ 执行实现：严格按决策结果执行
  │
  └─ 验证完成：证据先于声称
```

**这套操作系统贯穿所有六个阶段**，不是独立阶段，是每个阶段内的行为准则。

## 核心原则：多服务独立视角（强制）

### 基本原则

**当需求涉及多个服务时，每个服务的文档必须站在本服务的定位角度记录：**

- 主服务的 `analysis.md`：从主服务视角理解需求，定义对依赖服务的调用契约
- 依赖服务的 `analysis.md`：从本服务视角理解"主服务需要我提供什么"，定义被调用契约
- 每个服务的 `plan.md`、`changes.md`：只记录本服务的改动，不记录其他服务

**禁止**：在主服务文档中记录依赖服务的改动，或反之。

### 动态多服务识别（强制）

**即使一开始是单服务场景，在对话或操作过程中识别到多服务时，必须立即切换为多服务模式。**

#### 识别触发条件

在以下情况出现时，必须识别为多服务场景：

1. **需求分析阶段**
   - 用户提到"调用 XXX 服务"
   - 用户提到"依赖 XXX 工程"
   - 用户提到"XXX 微服务"
   - 发现需要调用其他服务的接口
   - 发现需要其他服务提供数据

2. **编写计划阶段**
   - 计划中涉及多个工程目录
   - 计划中涉及调用外部接口
   - 计划中涉及跨服务数据交互

3. **执行计划阶段**
   - 发现代码中调用其他服务
   - 发现代码中引用其他工程的接口定义
   - 发现代码中需要其他服务的数据

#### 识别后的处理流程

**每个阶段开始时，先检查 `workflow-state.json` 中的 `multi_service_mode` 字段：**
- 如果 `multi_service_mode: true`，直接按多服务模式继续，不再输出识别提示
- 如果不存在或为 `false`，检查是否满足识别条件

**首次识别为多服务场景时，执行：**

```
═══════════════════════════════════════════════════════════════
【多服务识别】检测到多服务场景
- 主服务：{主服务名称}
- 依赖服务：{服务1}, {服务2}, ...
═══════════════════════════════════════════════════════════════
```

然后更新 `workflow-state.json`：
```json
{
  "multi_service_mode": true,
  "main_service": "主服务名称",
  "dependent_services": ["服务1", "服务2"]
}
```

**处理步骤：**

1. **立即暂停当前操作**
2. **列出所有涉及的服务**（按需 Read `/Users/caomunian/Study/cwork/.services-map.md` 定位每个服务的目录与职责）
3. **为每个服务创建独立的文档目录**：
   - 主服务：`主工程/docs/requirements/{requirement_key}/`
   - 依赖服务：`依赖工程/docs/requirements/{requirement_key}/`
4. **站在每个服务的视角重新分析需求**
5. **为每个服务生成独立的 analysis.md、plan.md、changes.md**

#### 独立视角分析要求

**每个服务必须从自己的定位角度理解需求：**

| 视角 | 分析重点 | 文档位置 |
|------|---------|---------|
| 主服务 | 我需要提供什么功能？我需要调用谁？我如何编排流程？ | 主工程/docs/requirements/{key}/analysis.md |
| 依赖服务A | 主服务需要我提供什么？我需要新增什么接口？我需要查询什么数据？ | 服务A/docs/requirements/{key}/analysis.md |
| 依赖服务B | 主服务需要我提供什么？我需要新增什么接口？我需要查询什么数据？ | 服务B/docs/requirements/{key}/analysis.md |

#### 禁止行为

- ❌ 在主服务文档中记录依赖服务的改动
- ❌ 在依赖服务文档中记录主服务的改动
- ❌ 忽略识别到的多服务场景
- ❌ 继续按单服务模式处理
- ❌ 混淆不同服务的视角

## 前端设计辅助（条件触发）

> **按需加载**：触发时 Read 同目录 `design-guide.md`，不随本文件全量加载。

### 触发条件

当 plan.md 或需求分析中识别到以下场景时，**必须**触发前端设计辅助：

| 触发场景 | 示例 |
|---------|------|
| 创建全新前端工程 | 新建 React/Vue/Next.js/Nuxt 项目 |
| 创建全新前端页面 | 新增首页、详情页、Dashboard 等 |
| 前端技术栈选型 | 选择 UI 框架、组件库、样式方案 |

**不触发**：修改现有页面局部逻辑、纯后端改动、仅修改样式微调

### 触发后的动作

1. **Read `design-guide.md`** — 加载设计面试 12 问 + 矛盾检测 + 设计简报模板 + 设计准则（Token/动效/无障碍/文案/着陆页/技术栈检测）
2. 按设计指南执行设计面试，输出 `DESIGN-BRIEF.md`
3. 后续编码遵循设计准则

### 设计准则摘要（编码时遵循）

> 完整准则见 `design-guide.md`。以下仅列核心摘要。

**Token 系统**：三层架构（原始层→语义层→组件层），按角色命名禁止按外观命名，组件内禁止硬编码颜色值。

**动效**：只动 `transform` 和 `opacity`；进入 ease-out / 退出 ease-in；禁止超过 400ms；必须 `prefers-reduced-motion`。

**无障碍**：语义 HTML 优先于 ARIA；对比度 ≥ 4.5:1；键盘可达；焦点可见；颜色不是唯一信号。

**文案**：动词开头 + 利益点；说清错误 + 下一步；更短永远更好；禁止"提交"/"确定"/"出错了"。

**着陆页**：首屏优先；5 秒测试；每视口一个主 CTA；导航极简。

**技术栈检测**：`package.json` 含 react/next/vue/nuxt/svelte/@angular/core → 对应框架；无前端依赖 → HTML + Tailwind。

## 排查纪律（强制，基于实战失误总结）

**证据不充分就下结论是排查最大失误。必须遵守以下纪律：**

### 一、时间与时间戳（避免年份/范围错误）

- **查日志前先确认当前时间**：用 `date` 命令或相对时间（"最近 15 分钟"），避免年份错误
- **时间戳转换二次确认**：写注释说明"当前是 YYYY-MM-DD，时间戳应为 XXX"
- **空结果先怀疑时间范围**：日志搜索返回空，优先检查时间戳/时间范围是否正确，不要直接认定"没有数据"

**失误案例**：用 2025 年时间戳搜 2026 年日志，导致所有搜索返回空，浪费大量时间。

### 二、数据查询结果（空结果 ≠ 数据不存在）

- **空结果保持怀疑**：查询为空 ≠ 数据不存在，可能是数据源不同步/查询条件错误/权限问题
- **多源验证**：关键数据用多个数据源验证（JDBC catalog + 实时库 + 日志）
- **明确数据源特性**：Doris JDBC catalog 可能有延迟，实时库才是权威

**失误案例**：JDBC catalog 查询为空，直接认定"用户没有车辆绑定记录"，实际是数据未同步。

### 三、读写链路（既查读也查写）

- **既查读也查写**：定位问题时，读链路 + 写链路都要追
- **写入证据优先**：数据异常时，先找写入操作（OMP 日志、save 方法、MQ 消费）
- **完整链路**：读 → 处理 → 写，三段都要看

**失误案例**：只查"车牌从哪读的"，没查"车牌什么时候、被谁写进去的"，漏掉关键证据。

### 四、链路验证（代码 + 日志交叉验证）

- **代码 + 日志交叉验证**：代码推断的链路，必须用日志/链路追踪验证
- **多入口排查**：一个数据可能被多个入口修改，都要排查
- **Feign 调用日志**：跨服务调用必须看 Feign 日志确认真实调用链

**失误案例**：只看代码认定车牌来源，没验证结算时 orderserver 还会全局查询覆盖。

### 五、结论输出（证据充分后再下结论）

- **证据充分后再下结论**：至少 2 个独立证据（代码 + 日志 + 数据）交叉验证
- **阶段性结论明确标注**："阶段性发现：xxx，待验证 yyy"，不要说"最终结论"
- **最终结论前自问**：还有哪些证据没查？写入链路看了吗？多入口排查了吗？时间范围对吗？

**失误案例**：证据不完整时多次给"最终结论"，每次被新发现推翻。

## 推演收敛强制机制

**如果执行计划阶段有代码实现（新增/修改代码文件），则必须执行推演收敛阶段。**

### 判断条件

执行计划完成后，检查：
- 是否新增了代码文件？
- 是否修改了代码文件？
- 是否有实际的代码改动？

**如果以上任一条件为 true，则必须执行推演收敛。**

### 收敛检查点

推演收敛阶段开始前，检查：
- 是否新增了代码文件？
- 是否修改了代码文件？
- 是否有实际的代码改动？

**如果以上任一条件为 true，则必须执行推演收敛。**

### 禁止跳过的情况

以下情况**禁止跳过**推演收敛：

## 内部阶段一：需求分析（brainstorming）

<HARD-GATE>
在你展示设计方案、与用户达成一致理解（shared understanding）并获得用户批准之前，不要编写任何代码或采取任何实现行动。
</HARD-GATE>

### 检查清单（按顺序执行）

1. **探索项目上下文** — 检查文件、文档、最近的 commit
2. **提供视觉伴侣**（如果主题涉及视觉问题）— Read 同目录 `visual-companion.md`，这是一条独立的消息
3. **提出澄清问题** — 每次一个，了解目的/约束/成功标准
4. **提出 2-3 种方案** — 附带权衡分析和你的推荐
5. **展示设计** — 按复杂度分节展示，每节展示后获得用户批准
6. **多服务需求拆分** — 站在每个服务视角分析需求（见上方详细流程）
7. **记录分析结果** — 写入各服务的 analysis.md

### 核心原则

- **区分事实与决策** — 能从代码、commit、现有文档自查的事实，自己查清楚，不要拿去问用户；只有需要用户拍板的决策才提出来
- **每题给推荐答案** — 每个澄清问题都附上基于代码的推荐答案，用户只需采纳、否决或微调
- **按依赖顺序提问** — 识别决策之间的依赖关系，按依赖顺序逐个解决；前置决策未定时，不问依赖它的后续决策
- **每次一个问题** — 不要同时抛出多个问题
- **优先选择题** — 在可能的情况下比开放式问题更容易回答
- **严格遵循 YAGNI** — 从所有设计中移除不必要的功能
- **探索替代方案** — 在做决定之前始终提出 2-3 种方案
- **增量验证** — 展示设计，获得批准后再继续
- **保持灵活** — 有不明确的地方就回头澄清
- **多服务独立视角** — 每个服务从自己的职责定位理解需求
- **方案质询 + 决策树遍历** — 见「核心操作系统·编码思维方法论」，在需求分析中同样适用

### 反模式："这个太简单了，不需要设计"

每个项目都要经过这个流程。设计可以很简短（对于真正简单的项目几句话就够了），但你必须展示出来并获得批准。

### 流程详述

#### 探索项目上下文

首先查看当前项目状态：
- 文件结构
- **实际运行的代码**（最重要，注释和文档是次要的，代码才是最真实的）
- 文档（仅供参考，以实际代码为准）
- 最近的 commit
- 现有代码模式
- **代码图谱（必须先探测）**：进入探索后，第一步跑 `codegraph status`（在 `/Users/caomunian/Work/code-projects` 下执行）。有符号数（已索引）→ **必须用** `codegraph explore "<要理解的流程>"` / `codegraph query <符号>` 摸现状，比散乱 grep+Read 更省 context、更准确；无符号（未索引）→ 回退 grep/Read，不阻塞

**⚠️ 关键：不是只探测一次，而是每次找代码都要探测**

- **错误理解**：开始时探测一次，后面就可以随便用 grep+Read
- **正确理解**：需求分析、编写计划、执行实现过程中，**每次**查代码结构、查调用链、查接口实现，都要先探测 codegraph，已索引就必须用
- **持续监督**：每一步输出都必须有 `[codegraph]` 标签，没有就是偷懒

🔍 **输出标签（强制）**：每次调 codegraph 必须在对话里打一行 `[codegraph]` 标签让走向可见——探测后 `🔍 [codegraph] status → 已索引(N符号)，用图谱` 或 `→ 未索引，回退 grep+Read`；查询时 `🔍 [codegraph] <命令> <目标> → <目的>`。**无 `[codegraph]` 标签 = 没走 codegraph，视为偷懒。**

**重要原则**：
- 注释和文档可能过时或不准确，实际运行的代码才是最真实的
- 分析需求时，优先阅读和理解实际代码逻辑
- 文档和注释仅作为辅助参考，不能替代代码分析
- 如果文档描述与代码实现不一致，以代码为准

在提出详细问题之前，先评估范围：如果需求描述了多个独立子系统，立即指出这一点。

如果项目规模过大，帮助用户分解为子项目：
- 有哪些独立的部分
- 它们之间有什么关系
- 应该按什么顺序构建

#### 提出澄清问题

先自查再提问——能从代码、commit、现有文档推断出来的，自己查清楚，不要问用户；只把推断不出来、需要用户拍板的决策提出来。

每次提一个问题来完善想法：
- **每题附推荐答案** — 基于代码给出你的推荐，用户只需采纳、否决或微调
- 尽量使用选择题，开放式问题也可以
- 每条消息只提一个问题
- 重点理解：目的、约束、成功标准

#### 深度追问（需求分析质询）

在用户回答了澄清问题后，不要直接跳到方案探索。沿着决策树的每个分支逐层追问，直到双方对每个决策点达成共识：

**追问规则：**
1. **逐层追问**：沿决策树每个分支往下走，理清各项决策之间的依赖关系，有些选择必须等前一个问题确定了才能回答，按先后顺序逐个问清楚
2. **每个问题带推荐答案**：不要抛空问题，每次追问都要给出你的推荐及理由
3. **一次只问一个**：等用户回答了再问下一个，一次抛出多个问题会让人不知所措
4. **事实自己查，决策归用户**：能通过查看代码、文件系统、工具等找到的事实，直接去查，不用问用户；但决策是用户的，每个决策都要等用户拍板
5. **确认前不动手**：确认双方理解一致之前，不进入方案探索

**示例：**
```
用户："导出格式用 CSV"
追问："为什么选 CSV？我建议先看下现有导出逻辑。"
  →（查代码发现已有 Excel 导出模块）
追问："现有代码已有 Excel 导出模块，建议复用。选 CSV 还是复用 Excel？我推荐复用 Excel。"
用户："复用 Excel 吧"
追问："数据量方面，现有导出最大支持多少行？我查一下。"
  →（查数据库发现最大表 50 万行）
追问："最大表 50 万行，Excel 单 sheet 上限 104 万行，够用。是否需要分页导出？建议暂不加，先满足基本需求。"
用户："好，先不加"
```

**追问原则：**
- 只追问关键决策点，不追问琐碎细节
- 追问是为了暴露风险和遗漏，不是为了否定用户
- 沿决策树追问，每层得出明确结论后再进入下一层
- 追问中发现的约束和风险，记录到 analysis.md

#### 探索方案

提出 2-3 种不同的方案及其权衡：
- 以对话的方式展示选项，附上你的推荐和理由
- 先展示你推荐的方案并解释原因

#### 展示设计

一旦你认为理解了要构建的内容，就展示设计：
- 每个部分的篇幅与其复杂度匹配
- 每个部分展示后询问是否正确
- 涵盖：架构、组件、数据流、错误处理
- 随时准备回头澄清不明确的地方

**面向隔离和清晰的设计**：
- 将系统拆分为更小的单元，每个单元有一个明确的职责
- 通过定义良好的接口通信
- 对于每个单元，你应该能回答：它做什么，如何使用，它依赖什么？

**在现有代码库中工作**：
- 在提出更改之前先探索现有结构。遵循现有模式。
- 如果现有代码存在影响当前工作的问题，在设计中包含有针对性的改进
- 不要提议无关的重构

#### 前端设计感知（条件触发）

如果需求涉及前端新工程或新页面，在展示设计时额外完成：

1. **确认设计方向**：通过设计面试（见「前端设计辅助」章节）逐步确认产品类型、用户、风格
2. **检测技术栈**：检查 `package.json` 或向用户确认前端框架
3. **输出设计简报**：写入 `DESIGN-BRIEF.md`
4. **展示给用户确认**：将色彩、字体、间距方案展示给用户

**注意**：此步骤仅在触发前端设计辅助时执行，纯后端需求跳过。

#### 多服务需求拆分

当需求涉及多个服务时：

1. **主服务分析**
   - 从主服务视角理解需求
   - 确定需要调用哪些依赖服务
   - 定义调用契约（请求/响应结构）
   - 写入主服务的 analysis.md

2. **依赖服务分析**（每个依赖服务独立分析）
   - 从本服务视角理解需求
   - 确定需要提供什么接口
   - 确定需要查询/修改什么数据
   - 写入本服务的 analysis.md

3. **契约对齐**
   - 检查主服务的调用契约和依赖服务的响应契约是否一致
   - 检查字段名、类型、必填性是否匹配
   - 发现不一致时协调修正
   - **代码图谱核对（必须先探测）**：先跑 `codegraph status` 确认已索引，然后用 `codegraph callers`/`callees`/`node` 验证主服务调用的符号与依赖服务提供的符号真实对得上（不只看文档契约）；未索引跳过

## 内部阶段三：方案审查（plan-review）

**编写计划后，执行计划前，必须进行方案审查。**

### 审查目标

确保计划合理、完整、可行，避免执行过程中发现问题导致返工。

### 审查维度

**业务逻辑推演（必须）**：

| 审查项 | 说明 |
|--------|------|
| 业务流程推演 | 模拟业务主流程执行，验证流程是否闭环 |
| 业务规则推演 | 模拟业务规则判断，验证条件分支是否完整 |
| 业务状态推演 | 模拟状态流转，验证状态机是否正确 |
| 业务数据推演 | 模拟数据流转，验证数据是否完整 |
| 业务异常推演 | 模拟异常场景，验证异常处理是否完整 |
| 业务边界推演 | 模拟边界条件，验证边界处理是否正确 |

**技术方案审查（必须）**：

| 审查项 | 说明 |
|--------|------|
| 文件路径正确 | 文件路径是否存在，是否合理 |
| 依赖关系合理 | 模块依赖是否合理，是否存在循环依赖 |
| 技术方案可行 | 技术选型是否合理，是否满足需求 |

#### 代码简化原则

**保护功能**：只优化代码质量，绝不改变业务逻辑。重构后行为必须一致。

**用卫语句减少嵌套**：深层嵌套用提前返回拉平（反：3 层 if 嵌套；正：`if (user == null) return "unknown"; if (!user.isActive()) return "inactive"; return user.isPremium() ? "premium" : "basic";`）。

**避免过度工程**：不为假想的未来需求设计。三行相似代码好过一个提前抽象的通用框架。

**改进优先级**：零风险改进（变量重命名、消除冗余）→ 结构改进（减少嵌套、提取函数）→ 风格对齐（匹配项目已有编码风格）。

#### 完成验证铁律

**执行顺序**：识别验证命令 → 运行完整命令 → 阅读输出+退出码 → 判断是否证实 → 才能声称。

**子 agent 报告不可信**：子 agent 报告"成功"，必须独立验证——检查 git diff、运行验证命令、确认改动。

#### 系统化调试铁律

**未完成根因调查，禁止提出修复方案。** 四阶段：根因调查（读错误→稳定复现→检查近期改动→追踪数据流）→ 模式分析（对比正常/异常代码）→ 假设验证（一个假设+最小改动，不叠加）→ 实施修复（先复现测试+单一修复+验证）。

**三振出局**：修复尝试 ≥ 3 次 → 停下来质疑架构，和用户讨论。

**危险信号**（立即回到根因调查）："先临时修一下"、"试试改 X 看看"、"同时改几个地方"、"大概是 X"。

### 自问自答质询（推演质询）

每轮推演检查完成后，对推演结论进行自我质询。全程自问自答，不涉及用户——自己扮演质疑者，自己回答，自己决策：

**质询规则：**
1. **逐层自问**：对每个推演结论，沿决策树逐分支追问"如果这里错了呢？"
2. **每个自问带论据和自答**：提出质疑后，自己给出回答——"我怀疑这里有盲点，原因是 X，我决定去验证 Y"
3. **一次只质疑一个结论**：逐个结论质询和自答，不要一次性罗列所有疑点
4. **事实自己查**：能通过代码/工具验证的，直接查，不要空猜
5. **自己闭环**：每个质疑必须自己给出结论——是补充检查项还是确认可靠，不留给用户判断

**自问模板：**
1. "我是否因为思维惯性跳过了某些检查？"
2. "如果这个推演结论是错的，最可能错在哪里？"
3. "有没有我刻意回避的不确定点？"

**自问自答循环：**
```
for each 推演结论:
    自问：这个结论经得起挑战吗？如果错了，最可能错在哪？
    自答：我怀疑/确认...，原因是...
    如果发现盲点：
        自己补充检查项，修复问题，不问用户
    如果确认可靠：
        记录：经自问验证，结论可靠
```

**与推演循环的关系：**
- 自问自答嵌入推演循环内，每轮推演后执行
- 自问发现的问题纳入推演修复流程

```
    1. 进入工程目录
    2. 判断工程类型：
       - Java 工程（存在 pom.xml）：
         - 检测 Maven 是否可用
         - 执行 mvn compile -DskipTests
         - 编译成功 → 记录到 changes.md
         - 编译失败 → 输出错误，修复，重新编译
       - 前端工程（存在 package.json 且有 build 脚本）：
         - 检测包管理器（npm/yarn/pnpm）
         - 执行构建命令（npm run build / yarn build / pnpm build）
         - 构建成功 → 记录到 changes.md
         - 构建失败 → 输出错误，修复，重新构建
       - 其他工程：
         - 输出提示：非 Java/前端工程，跳过编译/构建检查
    3. 继续下一个工程
```

### 编译/构建失败处理

**如果任一工程编译/构建失败：**

1. 输出错误信息
2. 记录到 changes.md：
   ```markdown
   ## 编译/构建错误
   - 工程：{工程名称}
   - 类型：{Java/前端}
   - 错误：{错误信息}
   ```
3. 修复问题
4. 重新执行编译/构建
5. 通过后才算完成

### 多服务场景

**每个有代码改动的工程都要单独执行编译/构建检查：**

## 自动衔接

完成后评估是否进入 cwork-test：

**触发条件（全部满足才进入）**：
1. 有前端代码改动（新增/修改 .vue/.jsx/.tsx/.svelte 等前端文件）
2. 改动涉及**新页面或核心交互流程**（非纯样式微调、非纯数据字段增删、非纯后端接口对接）
3. 用户确认需要跑测试（简短询问，回车跳过=不跑）

**不满足**：直接询问用户是否调起 commit 技能进行代码提交，经用户确认后再进入 commit。
