# 日志与链路分析

## 概述

`log` 通过阿里云 **SLS 日志** + **ARMS 链路** 排查线上问题。3 步走（**日志先行 + 首轮并行**）：

1. **首轮并行查询**（阶段0）：有单号 → 同一轮并行发出时间戳计算 + 单号搜 SLS + count 试探 → 一轮定位到相关服务和关键参数
2. **深入日志 + 代码验证**（阶段1）：用首轮提取的参数继续搜 → 锁定异常点 → 只读最相关的 1-2 个代码文件验证原因
3. **结论输出**（阶段2）：代码 ↔ 日志 ↔ span 对应，给出 文件:行号 + 证据

**核心原则**：
- **日志先行，代码验证**：先拿到数据证据，再用代码解释原因。**有单号时第一轮就搜日志，不读代码、不查需求。**
- **首轮并行**：第一轮同时发出多个查询（时间戳 + 单号搜 + count），不串行等待
- **单号优先**：用户给了业务单号，第一轮就用单号搜（最精确，零噪音）
- **时间戳命令驱动**：禁止心算时间戳，所有时间戳必须来自 shell 命令
- **不臆造数据**：查询无结果就如实说，换条件再查

**合理默认**（没特殊说明就用，别问）：环境=prod、时间范围=最近 15 分钟、日志库=`all`。

## logstore 索引（固化，关键）

**不要每次 `sls_query.sh list` 再挑日志库。** prod 有 212 个库、uat 143 个，但命名规律明确。完整分类索引（按域/厂商/接口分类 + 高频服务→库速查 + pid 速查）见同目录 **`LOGSTORE_INDEX.md`**，定位库时先查它。核心规则：

- **`all` = 聚合库，默认入口**：绝大多数业务服务的**结构化**运行日志都在这（含 `trace`/`logger`/`level`/`message`）。先查 `all`，用工程的 **spring.name 作关键字**精确锁定（如 `DeviceBusinessServer`、`orderserver`，含连字符的 `payment-server` 也行，**不带引号**）。实测 `__tag__:_container_name_:` / `__path__:` 等 tag 语法 SLS 会报错、不能用；容器名当关键字也搜不到——只有 spring.name（在每条日志 `__path__` 里）全文搜可靠。device 协议日志常不在 all（查 `device-*` 专属库）。**CTP 车队日志也不在 all**（查 `ctp-*` 专属库，CTP 未接入 ARMS 链路追踪）。日志里的 `trace` 字段 = traceId，可直接喂 `arms_trace.sh`。
- **专属库按域分**：对外接口出入站 `<服务>3-out`；充电桩 `device-<厂商>`（`device-shenghong`盛弘/`device-shenrui`施恩/`device-huawei`华为/`device-luneng`鲁能/`device-wm`/`device-ykc1`）；运维桩 `device-ykcoms`；车队 `ctp-*`（⚠️ 不在 all，未接入 ARMS）；能源 `emp-*`/`ems-*`；运维 `xuzhu-omp-*`/`omp-*`/`feomp-*`；开放 `osp-*`；ZDL `zdl-*`；系统 `k8s-event`/`gc_log`/`sentinel-*`。
- **命名换算**：ARMS 应用名去掉 `-prod/-uat` ≈ logstore 前缀。`all` 查不到再试 `<前缀>-server` / `<前缀>3-out`；uat 业务专属库很少，查 uat 业务日志基本只查 `all`。
- **不确定库是否存在** → `count` 试探（比 `list` 省事），不要一上来就 `list` 全部。

## 脚本调用说明（关键）

本 skill 的脚本位于 `scripts/` 子目录（与本 SKILL.md 同级）。调用时用 skill 根目录的相对路径，或解析出绝对路径。**所有脚本已内置阿里云签名，直接 `bash` 调用即可，无需额外鉴权。**

| 脚本 | 用途 | 用法 |
|---|---|---|
| `sls_query.sh` | 查 SLS 日志 | `<env> list` / `<env> logs <logstore> [query] [line] [from_s] [to_s]` / `<env> count <logstore> [query] [from_s] [to_s]` |

| `arms_traces.sh` | 接口性能（次数/平均/QPS/错误率/整体P99） | `<pid> [分钟] [接口关键字]` |
| `arms_trace.sh` | 单条链路 span 树（上下游/耗时点） | `<pid> <traceId> [ts_ms]` |

参数说明：`env`=test/uat/prod；时间戳为秒级（SLS）或毫秒级（ts_ms）；`pid` 从 `arms_apps.sh` 输出获取；`logstore` 默认 `all`（见上表）。

## 阶段 0：首轮并行查询（最关键，决定排查速度）

**核心原则：有单号就直接搜日志，不读代码、不查需求。** 第一轮必须并行发出多个查询，一轮定位到相关服务和日志。

### 0.1 有业务单号时（最常见，必须快）

**第一轮并行查询（同一轮发出，不串行等待）**：

```bash
# ① 确认当前时间 + 计算时间戳（从单号推断日期）
date
# 单号前缀 260807 → 2026-08-07
date -j -f "%Y-%m-%d %H:%M:%S" "2026-08-07 00:00:00" +%s
date -j -f "%Y-%m-%d %H:%M:%S" "2026-08-08 00:00:00" +%s

# ② 用单号直接搜 SLS（零噪音，最精确）
bash scripts/sls_query.sh prod logs all "<单号>" 50 <from> <to>

# ③ 如果单号搜不到，用单号里的 gunId/recordId 搜
# （从 ② 的结果中提取）
```

**从日志结果提取关键信息**：
- 哪个服务在处理这个订单（看 `__tag__:_container_name_` 或 `__path__`）
- 订单的关键参数（tradeSeq、uid、gunId、payType、金额等）
- 订单状态和停充原因

**⚠️ 禁止**：先读代码再查日志 / 先查最近需求再查日志 / 先定位工程目录再查日志 / 串行（查一个等结果再查下一个）

### 0.2 无单号时（按现象搜）

```bash
# 第一轮并行：时间戳 + 多关键字搜索
date
bash scripts/sls_query.sh prod logs all "<关键字1>" 20 <from> <to>
bash scripts/sls_query.sh prod count all "<关键字2>" <from> <to>
```

### 0.3 业务关键字 → 实际服务映射（避免搜错服务）

**⚠️ 业务概念和实际处理服务经常不一致，搜错服务会浪费大量时间。**

| 业务关键字 | 实际处理服务（spring.name） | 常见误搜 |
|---|---|---|
| 余额校验/余额停充/预付/停充 | **charge-server** (DeviceBusinessServer) | ~~orderserver~~ |
| 充电启停/实时帧/桩通信 | **charge-server** (DeviceBusinessServer) | ~~charge-business-server~~ |
| 订单创建/结算/退款/占位费 | **order-server** (orderserver) + **order-foundation** | ~~charge-server~~ |
| 充电过程监控/BMS数据 | **charge-business-server** | ~~charge-server~~ |
| 支付/钱包/账户余额 | **payment-server** / **finance-server** | ~~order-server~~ |
| 电站/桩/枪基础数据 | **base_server** | ~~charge-server~~ |
| 车队/CTP | **ctp-*** 专属库（不在 all） | ~~orderserver~~ |
| 用户端渲染/小程序 | **guan-zhong** | ~~order-server~~ |

**使用方式**：用户说了业务关键字 → 查上表确定实际服务 → 用 spring.name 搜日志。

### 0.4 从首轮日志提取线索后的下一步

```
首轮日志结果
  │
  ├─ 找到异常/ERROR → 提取 traceId → 查链路 → 读代码验证
  │
  ├─ 找到关键参数（uid/gunId/tradeSeq）→ 用参数搜下一轮日志
  │     └─ 搜相关服务的业务日志（如：搜 "BalanceCheck and <uid>"）
  │
  ├─ 找到订单状态/停充原因 → 对比用户描述 → 判断是否一致
  │     └─ 不一致 → 搜为什么状态与预期不同
  │
  └─ 首轮无结果 → 空结果怀疑链（时间戳 → 库选择 → 服务定位）
```

### 0.5 前置需求关联（可选，不阻塞主流程）

**仅在以下条件全部满足时才执行**：用户没给具体单号 + 首轮日志搜索无明确结果 + 问题可能与最近上线功能相关。否则**跳过**，直接进入日志分析。

## 阶段 1：深入日志 + 代码验证

**前提**：阶段 0 已拿到首轮日志结果，知道了相关服务和关键参数。

### 1.1 深入日志（用首轮提取的参数继续搜，2-3 轮内锁定）

**关键字构造（一次搜到位，别试关键字）**：
- **关联 ID 优先**：用首轮提取的 recordId/gunId/tradeSeq/uid 作主关键字（零噪音），spring.name 作过滤
- **业务关键字从用户现象直接映射，不要自己发明**：不停充→`BalanceCheck/停充/余额校验`；金额异常→`chargedAmount/amount`；状态异常→`status/状态`
- **一条查询同时带 spring.name + 关联 ID + 业务关键字**，一次搜到位：`<spring.name> and <关联ID> and <业务关键字>`

```bash
# 深入搜：spring.name + 关联ID + 业务关键字 一次带齐
bash scripts/sls_query.sh prod logs all "<spring.name> and <关联ID> and <业务关键字>" 30 <from> <to>
# 统计某类日志数量（判断是整体异常还是个例）
bash scripts/sls_query.sh prod count all "<spring.name> and <业务关键字>" <from> <to>
```

**轮次目标**：阶段 1 最多 2-3 轮日志。超过 3 轮还没锁定 → 停下来问自己"是不是方向错了"（触发「不确定时探讨」），不要在日志里无限深挖。

### 1.2 搜日志 → 读代码的转换判据（什么时候停搜日志）

**满足任一即可转读代码**：
- 已拿到异常值的具体字段 + 该字段来自哪个服务/方法（异常值 + 来源 + 时间三要素齐全）
- 已拿到 traceId 且链路异常点定位到具体 span
- 连续 2 轮日志无新信息（没新异常、没新关联 ID、没新字段值）

**继续搜日志的信号**：日志里出现新的关联 ID / 新的异常字段 / 链路指向上游服务还没查 → 还有线索，继续搜。

**没判据时不要硬转**：不确定证据够不够 → 按「不确定时探讨」问用户，或再搜一轮确认，不要在"搜日志还是读代码"之间反复横跳。

### 1.3 代码验证（已拿到数据证据，读代码解释原因）

**⚠️ 只在已有日志证据后才读代码，且只读相关代码**：

1. 先 `codegraph status` 探测（已索引必须用图谱）
2. 用日志里发现的类名/方法名 → `codegraph node <类名>` 精准定位
3. 只读与日志证据直接相关的代码段，**不要通读整个文件**
4. 代码 ↔ 日志对应，解释为什么出现异常值

**禁止**：没有日志证据就大量读代码"找线索" / 一次读 5+ 个文件（只读最相关的 1-2 个）/ 通读整个 Service 的所有方法

## 阶段 2：链路与性能分析（按需）

> 阶段 0/1 已定位到异常点后，如需进一步分析链路耗时或性能，进入本阶段。

### 2.1 ARMS 链路分析

**拿 traceId + 时间戳后查链路**：

```bash

### 2.2 空结果怀疑链

查询返回空时，逐层排查：
1. **时间戳对吗？** → `date` 确认，重新计算
2. **库选对吗？** → 查 LOGSTORE_INDEX.md，或参考阶段0的"业务关键字→服务"映射
3. **pid 失效吗？** → `arms_traces.sh` 验证，失效则重跑 `arms_apps.sh`
4. **数据在专属库吗？** → CTP/运维桩/device 协议日志不在 all
5. **确实没数据** → 如实说，建议调整时间范围

> 阶段0的"业务关键字→服务"映射覆盖了常见场景。以下为完整 logstore 路由参考：

- **pid 索引**：查 `ARMS_PID_CACHE.md`（应用 → pid → 专属库）

## 不确定时停下来探讨（grill-me）

**自己能定的直接做**：环境/时间/日志库默认值、代码线索、工程定位、发查询——不问。
**不确定时立即停下来跟用户探讨**，不要闷头跑。

**何时停**（任一即停）：
1. 日志关键字搜不到 → 可能关键字/库/时间范围错了 → 问用户确认现象和时间
2. 日志现象跟用户描述不一致 → 可能理解偏差 → 问用户核对现象细节
3. 链路上下游不符合预期 → 可能调用链理解错了 → 问用户确认业务流程
4. 多个候选根因无法确定 → 不要猜 → 问用户哪个更符合现象
5. **阶段 1 超过 3 轮还没锁定** → 方向可能错了，停下来核对，不要在日志里无限深挖

**怎么问**（grill-me 四原则）：
- **问具体，不问泛**：问"报错信息是什么"，不问"有什么问题"
- **问验证，不问猜测**：问"这个现象你见过吗"，不问"可能是 xxx 吗"
- **问排除，不问选择**：问"哪个可以排除"，不问"选哪个"
- **一次问透，不挤牙膏**：把相关问题一次问完，不要反复问

**现象核对示例**（最常用）：
```
我查到的现象是 xxx，跟你描述的 yyy 不太一致，能再确认下：
- 问题具体表现是什么？（报错信息/页面行为/数据异常）
- 发生时间大概是什么时候？
- 影响范围是全部用户还是部分用户？

**跑飞预防**：每查到一个关键线索，先问自己"这个线索合理吗？跟用户描述的现象一致吗？"——不确定就问，不要硬推。

## 排查纪律（基于实战失误，执行时参考）

### 一、日志先行（时间戳 + 关键字 + 代码顺序）

- **时间戳命令驱动，禁止心算**：LLM 做大数算术不可靠。查日志前先 `date` 确认当前时间，再用 shell 命令转时间戳（macOS：`date -j -f "%Y-%m-%d %H:%M:%S" "2026-08-10 00:00:00" +%s` / `date -v-15M +%s`；Linux：`date -d "..." +%s`），填入查询 from/to。空结果优先怀疑时间范围。
- **单号优先搜索**：用户给了业务单号/充电单号/订单号/枪码，第一轮就用单号搜（零噪音）。关键字优先级：P0 业务单号/traceId > P1 recordId/gunId > P2 服务名+业务关键字 > P3 泛化关键字。**禁止在已有单号的情况下用泛化关键字搜索**。
- **日志先行，代码验证**：先拿到数据证据（用单号搜 SLS → 提取关联 ID → 2-3 轮锁定异常点），再读代码解释原因。禁止"读代码→搜日志→没找到→再读代码"的交替循环。
- **工程路径验证**：定位工程后先 `ls` 验证路径存在再读代码。常见混淆：`order_server`（下划线）vs `order-server`（连字符）、`charge_server` vs `DeviceBusinessServer`（spring.name）。以 services-map 为准，但每次验证。

**失误案例**：心算 2026-08-07 的时间戳算成了 2025 年的值（差 31536000 秒），导致所有 SLS 查询返回空，反复排查多轮才发现。

### 二、读写链路（既查读也查写 + 交叉验证 + 值异常层定位）

- **既查读也查写**：定位问题时读链路 + 写链路都要追，数据异常先找写入操作（OMP 日志、save 方法、MQ 消费）。完整链路 读 → 处理 → 写 三段都看。
- **代码 + 日志交叉验证**：代码推断的链路必须用日志/链路追踪验证；跨服务调用必须看 Feign 日志确认真实调用链。
- **多入口排查**：一个数据可能被多个入口修改，都要排查（用 `codegraph callers` 找全调用方）。
- **值异常先定位变化起点**：发现某字段值异常（始终为 0 / 不递增 / 与预期不符），先确认"这个值从哪一层开始变的"，不要假设中间层出问题就一路追下去：
  - **先看最上游**：直接查数据进来的原始日志（Feign 入参 / 实时帧原始数据 / 接口入参），看字段在源头是什么值
  - **对比正常字段 vs 异常字段**：同一来源找一个正常递增的字段 vs 异常字段（如 chargedPowerOri 正常递增 vs chargedAmountOri 始终为 0），一对比就能判断是"源头就不报"还是"中间层丢的"
  - **确认变化起点后再追链路**：源头就异常 → 根因在上游（如设备不上报），不用追中间层；中间层才变异常 → 再按"既查读也查写"追写入链路

**失误案例**：排查余额不停充，发现 chargedAmountOri 始终为 0，直接假设"Redis 没写入"，追 dealCarRealTimeData 调用链、order-foundation vs order-server 职责分工，多轮后发现根因是桩本身不上报金额字段。如果一开始就查实时帧原始数据（updateOrderOfCharging 的 Feign 入参），把 chargedAmountOri 和 chargedPowerOri 一起提出来对比，一步就能定位是源头问题，省掉整个中间层追踪。

### 三、根因到底（证据充分 + 三要素 + 禁假设）

- **证据充分后再下结论**：至少 2 个独立证据（代码 + 日志 + 数据）交叉验证。阶段性结论明确标注"阶段性发现：xxx，待验证 yyy"，不要说"最终结论"。
- **根因三要素**：根因是什么（一句话）+ 证据是什么（日志/span/数据）+ 怎么验证（复现路径或验证命令）。
- **排查必须到底**：不能停在"可能是 xxx"、"怀疑是 xxx"——必须追到具体代码行/具体配置项/具体数据异常。证据不足就继续查，明确告知用户"尚未定位到根因，还需排查 xxx"。
- **禁止输出"根因假设"**：结论区只写"根因"，不写"根因假设"或"可能原因"。没查到就说"排查中，待查 xxx"，不要编假设充数。

**失误案例**：证据不完整时多次给"最终结论"，每次被新发现推翻。

### 四、空结果怀疑链（空结果 ≠ 数据不存在）

- **空结果保持怀疑**：查询为空 ≠ 数据不存在，可能是数据源不同步/查询条件错误/权限问题。
- **多源验证**：关键数据用多个数据源验证（JDBC catalog + 实时库 + 日志）。Doris JDBC catalog 可能有延迟，实时库才是权威。
- **怀疑顺序**：时间戳 → 库选择 → pid 失效 → 数据在专属库 → 确实没数据。

## 联动：查业务数据 / 查 Nacos 配置（cwork-data / cwork-config）

排查中常需用数据或配置佐证根因。**触发条件命中即调起**（主 agent 用 Skill 工具触发），写法对齐 cwork-bug 的「后端日志联动」。

**① 数据查询联动（cwork-data）** — 用数仓数据佐证
- 触发条件（任一）：需核对业务数据（订单状态/金额/库存/某用户数据）、查某时段数据量、数据一致性存疑、日志看到数据异常需数仓佐证。
- 流程：从链路/日志拿到线索（订单号/用户号/时段）→ 调 cwork-data 查对应数仓表（DWD 宽表优先）→ 数据 ↔ 日志/链路对应。
- 调用示例：
  ```bash
  cd skills/data/scripts/mcp-client
  python3 mcp_client.py query --sql "SELECT * FROM internal.dwd.dwd_order_settle_model WHERE dt='<日期>' AND order_no='<订单号>' LIMIT 10"
  ```
- 联动原则：cwork-log 管「链路/日志根因」，cwork-data 管「业务数据佐证」；拿到数据证据后回到链路分析下结论。

**② 配置查询联动（cwork-config）** — 核对 Nacos 配置真值
- 触发条件（任一）：需确认某服务某环境实际配置（开关/阈值/地址/参数）、怀疑配置变更引发问题、日志显示参数与预期不符要核对 Nacos 真值。
- 流程：定 env + 服务名 → 调 cwork-config 查配置（不知 dataId 先 `search`）→ 配置真值 ↔ 现象对应。
- 调用示例：
  ```bash
  cd skills/config/scripts
  bash nacos_query.sh test search <服务名>                  # 定位 dataId
  bash nacos_query.sh test get <dataId> DEFAULT_GROUP       # 取配置
  bash nacos_query.sh diff <dataId> DEFAULT_GROUP uat prod  # 多环境对比
  ```
- 联动原则：cwork-log 管「现象与链路」，cwork-config 管「核对 Nacos 配置真值」；确认配置后回到链路分析。

> **凭证注意**：cwork-data 需 `skills/data/scripts/mcp-client/.mcp_config.json` 已配置；cwork-config 需 `skills/config/scripts/.config.local.sh` 已配置对应集群。未配置时跳过对应联动，仅基于日志/链路分析。

## 反模式

**高代价反模式（实战踩坑，必须避免）**：

- **❌ 不日志先行**：有单号时第一轮就该搜日志，不是读代码、不是先查最近需求、不是先定位工程目录。读 5 个 Service 文件再搜日志 = 浪费 10+ 轮。日志定位到后只读最相关的 1-2 个代码文件，不通读。
- **❌ 搜错服务**：业务概念 ≠ 实际服务。"余额校验"在 charge-server 不在 orderserver。查阶段0.3 的"业务关键字→实际服务"映射表，别凭直觉搜。
- **❌ 串行查询**：第一轮只发一个查询等结果 → 再发下一个。正确：第一轮并行发 3-4 个查询（时间戳 + 单号搜 + count 试探）。
- **❌ 值异常就假设中间层出问题、一路追写入链路**：发现某字段始终为 0，直接假设"Redis 没写入 / 中间层丢了"并追调用链——多轮后才发现根因是源头（设备/上游接口）根本没报这个字段。正确：先查最上游的原始日志（Feign 入参/实时帧），找一个同来源的正常字段做对比，一步判断是源头问题还是中间层问题，再决定追哪段。
- **❌ 臆造数据 / 只看一个指标下结论**：查询无结果就如实说，让用户调整条件；流量正常不代表链路正常，要交叉看。耗时点/异常点必须显式指出，不能藏在原始输出里。
- **❌ 排查停在假设层面就输出结论**："可能是 xxx"、"怀疑是 xxx"、"根因假设"都不能作为最终结论——必须追到根因，证据不足就说"待查"。
- **❌ 已索引却散乱 grep+Read、不用 codegraph**：代码验证阶段先 `codegraph status`，已索引必须用 node/callees/callers/explore 抠线索。代码排查时不读实际代码、只凭日志猜也要对应到具体文件:行号。

**一般反模式**：
- 不分情况地反复确认（自己能定的直接做；只在服务歧义/方向不明等决策点问）
- 该问时不问、自己瞎猜（需要用户拍板的地方不对话，容易查错方向）
- 每次都 `sls_query.sh list` 让用户挑日志库（用 logstore 映射，默认 `all`）

## 完成定义

- 能自己定的已直接做（读代码、发查询），决策点已与用户简短确认
- 目标应用 pid 已获取（唯一命中直接用，多命中已确认）
- 按目标调用脚本拿到数据（流量/链路/日志）
- 耗时点与异常点已显式指出（带 span/日志证据）
- **根因已定位**：根因 + 证据 + 验证方式三要素齐全；如未定位到，明确告知用户待查方向
- 结论已汇总输出（上下游、P99、耗时点、日志证据、根因）
