# 日志与链路分析

## 概述

`log` 是日志与链路分析的技能，通过阿里云 **SLS 日志** + **ARMS 链路** 排查线上问题。

**主动排查 + 不确定时及时探讨（grill-me）**：

- **自己能定的直接做**：环境/时间/日志库默认值、代码线索、工程定位、发查询——不问
- **不确定时及时探讨**：排查方向不明、线索矛盾、现象异常、理解存疑——**立即停下来跟用户探讨**，用 grill-me 方式验证理解，不要闷头跑
- **跑飞预防机制**：每查到一个关键线索，先问自己"这个线索合理吗？跟用户描述的现象一致吗？"——不确定就问，不要硬推

**⚠️ 跑飞高发场景（必须停下来探讨）**：
1. 日志关键字搜不到 → 可能关键字错了/库选错了/时间范围错了 → 问用户确认现象和时间
2. 日志现象跟用户描述不一致 → 可能理解偏差了 → 问用户核对现象细节
3. 链路上下游不符合预期 → 可能调用链理解错了 → 问用户确认业务流程
4. 多个候选根因无法确定 → 不要猜 → 问用户哪个更符合现象

**grill-me 实践方法（追问/质询，验证理解）**：

当遇到不确定时，**立即停下来**，用以下方式跟用户探讨：

1. **现象核对**（最常用）：
   ```
   我查到的现象是 xxx，跟你描述的 yyy 不太一致，能再确认下：
   - 问题具体表现是什么？（报错信息/页面行为/数据异常）
   - 发生时间大概是什么时候？
   - 影响范围是全部用户还是部分用户？
   ```

2. **方向确认**（排查方向不明时）：
   ```
   我现在有两个排查方向：
   A. xxx（可能性更高，因为...）
   B. yyy（可能性较低，因为...）
   
   你觉得应该先查哪个？或者有其他线索？
   ```

3. **线索质询**（线索矛盾时）：
   ```
   我发现一个矛盾点：
   - 日志显示 xxx
   - 但代码逻辑应该是 yyy
   
   这里有几种可能：
   1. 代码最近改过
   2. 日志关键字理解错了
   3. 有其他入口
   
   你知道最近有相关改动吗？或者有其他入口吗？
   ```

4. **根因排除**（多个候选根因时）：
   ```
   我找到几个可能的根因，但无法确定是哪个：
   1. xxx（证据：...）
   2. yyy（证据：...）
   3. zzz（证据：...）
   
   你觉得哪个更符合你看到的现象？或者能提供更多信息排除吗？
   ```

**grill-me 核心原则**：
- **问具体，不问泛**：问"报错信息是什么"，不问"有什么问题"
- **问验证，不问猜测**：问"这个现象你见过吗"，不问"可能是 xxx 吗"
- **问排除，不问选择**：问"哪个可以排除"，不问"选哪个"
- **一次问透，不挤牙膏**：把相关问题一次问完，不要反复问

3 步走（**日志先行 + 首轮并行**，不确定时停下来探讨）：
1. **首轮并行查询**（阶段0）：有单号 → 同一轮并行发出：时间戳计算 + 单号搜 SLS + count 试探 → 一轮定位到相关服务和关键参数
2. **深入日志 + 代码验证**（阶段1）：用首轮提取的参数继续搜 → 锁定异常点 → 只读最相关的 1-2 个代码文件验证原因
3. **结论输出**（阶段2）：代码 ↔ 日志 ↔ span 对应，给出 文件:行号 + 证据

**核心原则**：
- **日志先行，代码验证**：先拿到数据证据，再用代码解释原因。**有单号时第一轮就搜日志，不读代码、不查需求。**
- **首轮并行**：第一轮必须同时发出多个查询（时间戳 + 单号搜 + count），不串行等待
- **业务关键字→实际服务**：搜日志前查映射表，避免搜错服务（如"余额校验"在 charge-server 不在 orderserver）
- **单号优先搜索**：用户给了业务单号，第一轮就用单号搜（最精确，零噪音）
- **时间戳命令驱动**：禁止心算时间戳，所有时间戳必须来自 shell 命令
- **少读代码**：代码只在有日志证据后读，且只读最相关的 1-2 个文件，不通读
- **自己能定的直接做**：环境/时间/日志库默认值、发查询——不问
- **不确定时及时探讨**：排查方向不明、线索矛盾、现象异常——立即停下来跟用户探讨
- **跑飞预防**：每查到一个关键线索，先验证合理性，不确定就问
- 不臆造数据：查询无结果就如实说，换条件再查

## 排查纪律（强制，基于实战失误总结）

**证据不充分就下结论是排查最大失误。必须遵守以下纪律：**

### 一、时间与时间戳（强制命令驱动，禁止心算）

**⚠️ 禁止心算时间戳**：LLM 做大数算术不可靠，所有时间戳必须来自 shell 命令。

**查日志前必须执行**：
```bash
# ① 确认当前时间（强制）
date
# 输出示例：2026-08-10 15:30:00，据此计算时间戳

# ② macOS 日期转时间戳
date -j -f "%Y-%m-%d %H:%M:%S" "2026-08-10 00:00:00" +%s

# ③ macOS 计算 N 分钟前的时间戳
date -v-15M +%s  # 15分钟前

# ④ Linux 日期转时间戳
date -d "2026-08-10 00:00:00" +%s
```

**时间戳获取流程**：
1. 先跑 `date` 确认当前时间
2. 根据当前时间计算目标时间（如"最近15分钟"）
3. 用 shell 命令转换时间戳，**不许心算**
4. 在查询命令里填入 from/to 时间戳

**空结果先怀疑时间范围**：日志搜索返回空，优先检查时间戳/时间范围是否正确，不要直接认定"没有数据"。

**失误案例**：心算 2026-08-07 的时间戳，算成了 2025 年的值（差 31536000 秒），导致所有 SLS 查询返回空，反复排查多轮才发现。

### 二、搜索关键字优先级（强制，避免发散）

**用户给了业务单号/充电单号/订单号/枪码时，单号是第一优先关键字**：

| 优先级 | 关键字类型 | 示例 | 噪音 |
|---|---|---|---|
| **P0** | 业务单号/traceId | `2608072130337098` | 零噪音 |
| **P1** | 单号关联的 recordId/gunId | `recordId=xxx` | 低噪音 |
| **P2** | 服务名 + 业务关键字 | `orderserver and 余额校验` | 中噪音 |
| **P3** | 泛化关键字 | `余额校验`、`停充` | 高噪音 |

**搜索策略**：
1. 用户给了单号 → **第一轮就用单号搜**（最精确，零噪音）
2. 从日志里提取关联 ID（recordId/gunId/tradeSeq）→ 用关联 ID 搜下一轮
3. 只有在没有单号时，才用服务名 + 业务关键字搜
4. **禁止在已有单号的情况下用泛化关键字搜索**（会导致大量噪音）

**失误案例**：用户给了充电单号 2608072130337098，但第一轮搜了"余额校验"，匹配到 PMCS 运维日志等大量无关内容，浪费多轮过滤。

### 三、日志先行策略（强制，减少代码日志交替）

**核心原则：日志先行，代码验证**。先拿到数据证据，再用代码解释原因。

**排查顺序**：
```
阶段 A：快速日志定位（不读代码）
  ① 用户给单号 → 直接用单号搜 SLS
  ② 从日志提取关联 ID（recordId/gunId/traceSeq）
  ③ 用关联 ID 搜下一轮日志
  ④ 2-3 轮内锁定异常点（ERROR/异常值/耗时点）

阶段 B：代码验证（已拿到数据证据）
  ⑤ 读代码确认链路（验证而非探索）
  ⑥ 解释为什么出现异常值
```

**禁止的模式**：
```
❌ 错误：读代码 → 提取关键字 → 搜日志 → 没找到 → 再读代码 → 再搜日志
✓ 正确：用单号搜日志 → 拿到数据证据 → 读代码解释原因
```

**失误案例**：看一段代码 → 查日志 → 没找到 → 回来再看代码 → 再查，反复多轮。正确做法是先拿到充电单号直接搜日志，从日志里拿到 recordId，再搜余额校验日志，一轮就能确认 chargedAmountOri 是否为 0。

### 四、工程路径验证（强制，避免路径错误）

**定位工程后必须验证路径存在**：

```bash
# 定位到工程目录后，先验证
ls /Users/caomunian/Work/code-projects/trade/order-server
# 路径存在 → 继续读代码
```

- `charge_server` vs `DeviceBusinessServer`（spring.name）
- 以 services-map 为准，但每次验证

**失误案例**：services-map 写的是 order_server，实际目录是 order-server，直接去读导致找不到文件。

### 五、数据查询结果（空结果 ≠ 数据不存在）

- **空结果保持怀疑**：查询为空 ≠ 数据不存在，可能是数据源不同步/查询条件错误/权限问题
- **多源验证**：关键数据用多个数据源验证（JDBC catalog + 实时库 + 日志）
- **明确数据源特性**：Doris JDBC catalog 可能有延迟，实时库才是权威

**失误案例**：JDBC catalog 查询为空，直接认定"用户没有车辆绑定记录"，实际是数据未同步。

### 六、读写链路（既查读也查写）

- **既查读也查写**：定位问题时，读链路 + 写链路都要追
- **写入证据优先**：数据异常时，先找写入操作（OMP 日志、save 方法、MQ 消费）
- **完整链路**：读 → 处理 → 写，三段都要看

**失误案例**：只查"车牌从哪读的"，没查"车牌什么时候、被谁写进去的"，漏掉关键证据。

### 七、链路验证（代码 + 日志交叉验证）

- **代码 + 日志交叉验证**：代码推断的链路，必须用日志/链路追踪验证
- **多入口排查**：一个数据可能被多个入口修改，都要排查
- **Feign 调用日志**：跨服务调用必须看 Feign 日志确认真实调用链

**失误案例**：只看代码认定车牌来源，没验证结算时 orderserver 还会全局查询覆盖。

### 八、结论输出（证据充分后再下结论）

- **证据充分后再下结论**：至少 2 个独立证据（代码 + 日志 + 数据）交叉验证
- **阶段性结论明确标注**："阶段性发现：xxx，待验证 yyy"，不要说"最终结论"
- **最终结论前自问**：还有哪些证据没查？写入链路看了吗？多入口排查了吗？时间范围对吗？

**失误案例**：证据不完整时多次给"最终结论"，每次被新发现推翻。

### 九、根因定位（排查必须到底）

- **排查必须定位到根因才能结束**：不能停在"可能是 xxx"、"怀疑是 xxx"——必须追到具体代码行/具体配置项/具体数据异常，有确凿证据
- **根因三要素**：根因是什么（一句话）+ 证据是什么（日志/span/数据）+ 怎么验证（复现路径或验证命令）
- **证据不足就继续查**：如果现有证据不足以确定根因，明确告知用户"尚未定位到根因，还需排查 xxx"，不要硬下结论
- **禁止输出"根因假设"**：结论区只写"根因"，不写"根因假设"或"可能原因"。如果真没查到根因，说"排查中，待查 xxx"，不要编一个假设充数

**失误案例**：排查到一半输出"根因假设是 xxx"，用户按假设去处理，问题没解决又回来重查。

### 十、值异常的层定位（先定位变化起点，再决定追哪段）

**发现某字段值异常（始终为 0 / 不递增 / 与预期不符）时，先确认"这个值从哪一层开始变的"，不要假设中间层出问题就一路追下去。**

- **先看最上游**：直接查数据进来的原始日志（Feign 入参 / 实时帧原始数据 / 接口入参），看字段在源头是什么值
- **对比正常字段 vs 异常字段**：同一来源里找一个正常递增的字段 vs 异常字段（如 chargedPowerOri 正常递增 vs chargedAmountOri 始终为 0），一对比就能判断是"源头就不报"还是"中间层丢的"
- **确认变化起点后再追链路**：源头就异常 → 根因在上游（如设备不上报），不用追中间层；中间层才变异常 → 再按"六、读写链路"追写入链路

**失误案例**：排查余额不停充，发现 chargedAmountOri 始终为 0，直接假设"Redis 没写入"，追 dealCarRealTimeData 调用链、order-foundation vs order-server 职责分工，多轮后发现根因是桩本身不上报金额字段。如果一开始就查实时帧原始数据（updateOrderOfCharging 的 Feign 入参），把 chargedAmountOri 和 chargedPowerOri 一起提出来对比，一步就能定位是源头问题，省掉整个中间层追踪。

## logstore 索引（固化，关键）

**不要每次 `sls_query.sh list` 再挑日志库。** prod 有 212 个库、uat 143 个，但命名规律明确。完整分类索引（按域/厂商/接口分类 + 高频服务→库速查 + pid 速查）见同目录 **`LOGSTORE_INDEX.md`**，定位库时先查它。核心规则：

- **`all` = 聚合库，默认入口**：绝大多数业务服务的**结构化**运行日志都在这（含 `trace`/`logger`/`level`/`message`）。先查 `all`，用工程的 **spring.name 作关键字**精确锁定（如 `DeviceBusinessServer`、`orderserver`，含连字符的 `payment-server` 也行，**不带引号**）。实测 `__tag__:_container_name_:` / `__path__:` 等 tag 语法 SLS 会报错、不能用；容器名当关键字也搜不到——只有 spring.name（在每条日志 `__path__` 里）全文搜可靠。device 协议日志常不在 all（查 `device-*` 专属库）。**CTP 车队日志也不在 all**（查 `ctp-*` 专属库，CTP 未接入 ARMS 链路追踪）。日志里的 `trace` 字段 = traceId，可直接喂 `arms_trace.sh`。
- **专属库按域分**：对外接口出入站 `<服务>3-out`；充电桩 `device-<厂商>`（`device-shenghong`盛弘/`device-shenrui`施恩/`device-huawei`华为/`device-luneng`鲁能/`device-wm`/`device-ykc1`）；运维桩 `device-ykcoms`；车队 `ctp-*`（⚠️ 不在 all，未接入 ARMS）；能源 `emp-*`/`ems-*`；运维 `xuzhu-omp-*`/`omp-*`/`feomp-*`；开放 `osp-*`；ZDL `zdl-*`；系统 `k8s-event`/`gc_log`/`sentinel-*`。
- **命名换算**：ARMS 应用名去掉 `-prod/-uat` ≈ logstore 前缀。`all` 查不到再试 `<前缀>-server` / `<前缀>3-out`；uat 业务专属库很少，查 uat 业务日志基本只查 `all`。
- **不确定库是否存在** → `count` 试探（比 `list` 省事），不要一上来就 `list` 全部。

## 脚本调用说明（关键）

## 联动：查业务数据 / 查 Nacos 配置（cwork-data / cwork-config）

排查中常需用数据或配置佐证根因。**触发条件命中即调起**（主 agent 用 Skill 工具触发），写法对齐 cwork-bug 的「后端日志联动」。

**① 数据查询联动（cwork-data）** — 用数仓数据佐证
- 触发条件（任一）：需核对业务数据（订单状态/金额/库存/某用户数据）、查某时段数据量、数据一致性存疑、日志看到数据异常需数仓佐证。
- 流程：从链路/日志拿到线索（订单号/用户号/时段）→ 调 cwork-data 查对应数仓表（DWD 宽表优先）→ 数据 ↔ 日志/链路对应。
- 调用示例：
  ```bash
  cd skills/data/scripts/mcp-client
  python3 mcp_client.py query --sql "SELECT * FROM internal.dwd.dwd_order_settle_model WHERE dt='<日期>' AND order_no='<订单号>' LIMIT 10"
  ```
- 联动原则：cwork-log 管「链路/日志根因」，cwork-data 管「业务数据佐证」；拿到数据证据后回到链路分析下结论。

**② 配置查询联动（cwork-config）** — 核对 Nacos 配置真值
- 触发条件（任一）：需确认某服务某环境实际配置（开关/阈值/地址/参数）、怀疑配置变更引发问题、日志显示参数与预期不符要核对 Nacos 真值。
- 流程：定 env + 服务名 → 调 cwork-config 查配置（不知 dataId 先 `search`）→ 配置真值 ↔ 现象对应。
- 调用示例：
  ```bash
  cd skills/config/scripts
  bash nacos_query.sh test search <服务名>                  # 定位 dataId
  bash nacos_query.sh test get <dataId> DEFAULT_GROUP       # 取配置
  bash nacos_query.sh diff <dataId> DEFAULT_GROUP uat prod  # 多环境对比
  ```
- 联动原则：cwork-log 管「现象与链路」，cwork-config 管「核对 Nacos 配置真值」；确认配置后回到链路分析。

> **凭证注意**：cwork-data 需 `skills/data/scripts/mcp-client/.mcp_config.json` 已配置；cwork-config 需 `skills/config/scripts/.config.local.sh` 已配置对应集群。未配置时跳过对应联动，仅基于日志/链路分析。

## 反模式

**⚠️ 高代价反模式（实战踩坑，必须避免）**：

- **❌ 先读完代码再查日志**：有单号时，第一轮就该搜日志，不是读代码。读 5 个 Service 文件再搜日志 = 浪费 10+ 轮。正确：日志先行，代码验证。
- **❌ 搜错服务**：业务概念 ≠ 实际服务。"余额校验"在 charge-server 不在 orderserver。查"业务关键字→实际服务"映射表，别凭直觉搜。
- **❌ 串行查询**：第一轮只发一个查询等结果 → 再发下一个。正确：第一轮并行发 3-4 个查询（时间戳 + 单号搜 + count 试探）。
- **❌ 有单号还先查需求**：用户给了充电单号，直接搜日志，不需要先查最近 7 天上线了什么需求。
- **❌ 一次读太多代码文件**：日志已经定位到 BalanceCheckService，不需要把 CheckFlowOrderBalanceService、CheckThirdOrderBalanceService 等 5 个子类全读一遍。只读最相关的 1-2 个。
- **❌ 值异常就假设中间层出问题、一路追写入链路**：发现某字段始终为 0，直接假设"Redis 没写入 / 中间层丢了"并追调用链、服务职责分工——多轮后才发现根因是源头（设备/上游接口）根本没报这个字段。正确：先查最上游的原始日志（Feign 入参/实时帧），找一个同来源的正常字段做对比（如 chargedPowerOri 正常 vs chargedAmountOri=0），一步判断是源头问题还是中间层问题，再决定追哪段。

**一般反模式**：

- **不分情况地反复确认**（自己能定的直接做；只在服务歧义/方向不明等决策点问）
- **该问时不问、自己瞎猜**（需要用户拍板的地方不对话，容易查错方向）
- **每次都 `sls_query.sh list` 让用户挑日志库**（用 logstore 映射，默认 `all`）
- 臆造日志内容或链路数据（查询无结果就如实说，让用户调整条件）
- 只看一个指标下结论（流量正常不代表链路正常，要交叉看）
- 把耗时点/异常点藏在原始输出里不点明（必须显式指出耗时点和异常）
- 已索引却散乱 grep+Read、不用 codegraph（代码验证阶段先 `codegraph status`，已索引必须用 node/callees/callers/explore 抠线索）
- 代码排查时不读实际代码、只凭日志猜（要对应到具体文件:行号）
- 排查停在假设层面（"可能是 xxx"、"怀疑是 xxx"）就输出结论——必须追到根因，证据不足就说"待查"
- 输出"根因假设"或"可能原因"充数——结论区只写"根因"，没查到就说没查到
