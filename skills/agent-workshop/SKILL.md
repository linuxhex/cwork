# Agent 工坊

## 概述

`cwork-agent-workshop` 是一个「单主题深挖」的内容 skill：从 GitHub 与一手资料里挑出一个正在升温的 Agent 主对象（架构 / harness / skill），拆清它的能力特性，用一次可复现的案例实践去验证，最后写成一篇有观点、有证据、有场景价值的公众号软文。

**和同类的分工**：

| skill | 体裁 | 产出 |
|-------|------|------|
| `cwork-tech-express` | 三日资讯简报 | 快讯压缩 + 短评，多条并列 |
| `cwork-article` | 通用文章生产 | 按给定主题写，不负责选题与情报采集 |
| **`cwork-agent-workshop`** | **单主题深度软文** | **1 个主对象 + 2-3 个对照，情报采集 → 案例实践 → 能力/场景论证** |

**核心能力**：

1. **选题锚定** — 从「用户指定 / 近 30 天一手热度 / 上期结尾预告」三路取题，一篇文章只讲一个主对象
2. **一手情报** — GitHub 仓库/Release/源码、官方规范、论文、作者自述与社区讨论；二手媒体只当线索，不当证据
3. **案例实践（强制）** — 至少一个 L1/L2 案例；等级按代价与风险选，证据等级必须写进文章
4. **软文骨架** — 钩子 → 结论 → 拆解 → 能力特性表 → 案例 → **场景价值（三类读者）** → 冷静判断 → 最小行动
5. **不吹不黑** — 每个优势必须配一个代价或边界；不能验证的就写「未验证」
6. **排版交付** — HTML + inline CSS（模板见 [template.md](template.md)），封面走「ImageGen 无文字底图 + HTML 叠中文 + Chrome 渲染」
7. **写入草稿** — 复用科技速递已验证的浏览器注入链路与脚本，存草稿为止，发表按钮归用户

**工作流程**：

```
阶段0 选题锚定与形态确认 → 阶段1 情报采集 → 阶段2 案例实践(证据分级)
→ 阶段3 论证与写作(能力→场景价值) → 阶段4 排版+封面 → 阶段5 写入草稿 → 阶段6 汇报
```

## 语言约束（强制）

全流程对话、分析、结论一律中文；仅命令、路径、参数名、链接、项目名原文保留。

## 产物目录（全局 contentDir，强制）

所有内容产物写外置内容目录，解析规则见 `cwork-common/output-dir.md`（优先级：用户当轮指定 > `CWORK_CONTENT_DIR` > `cwork.content.json` > 兜底 `<repo>/docs/articles`，兜底必须告知）。

本期目录：**`$CONTENT_DIR/agent-workshop/<YYYYMMDD>-<slug>/`**（slug 用主对象名的小写短横线形式，如 `20261121-claude-skills`）。锚定选题后立即解析一次并回显落点；目录已存在即视为更新本期稿件，沿用同一 `appmsgid`。**期号** = 该目录下已有期次目录数 + 1（首次为 01），写进正文栏目条。

> 文中尖括号（如 `<期次>`、`<slug>`）是占位符，命令块已改用 `$ISSUE` 变量，照抄前把 `ISSUE` 换成真实目录名。

```
$CONTENT_DIR/agent-workshop/<YYYYMMDD>-<slug>/
├── research.md        # 阶段 1 情报台账
├── practice-log.md    # 阶段 2 实践记录
├── body.html          # 阶段 4 正文（inline CSS）
├── inject-fn.js       # 脚本生成，勿手改
├── inject.js          # 备用链路用
├── images/            # 封面与配图
└── draft-report.json  # 阶段 5 执行与复验结果
```

## 阶段 0：选题锚定与形态确认

### 0.1 三条取题路径

| 路径 | 触发 | 做法 |
|------|------|------|
| 用户指定 | 用户给了项目名/主题 | 直接核实对象存在且可取证，跳过候选 |
| 热度自选 | 用户只说「写一篇最近 agent 的」 | 给 3 个候选（各一行：对象 + 为什么是现在 + 可实践等级），一次一问让用户选 |
| 系列承接 | 上期结尾预告过下一期 | 先确认预告对象是否仍值得写，失温就换 |

候选必须覆盖**主题域三选一**：`架构`（编排/记忆/工具/多 Agent）、`harness`（评测脚手架与基准）、`skill`（技能包规范与生态）。

### 0.2 热度与可得性判据（事实自己查）

- 最近 release / 提交是否在 30 天内；star 周增速是否有明显跃升（记录抓取时间）
- 是否有可读的一手材料：README/架构文档/源码/论文/Release 中至少 3 类
- 是否有可实践的入口：能装、能跑 demo、许可证允许本地实验
- **排除**：单纯 star 高但停更半年、只有营销页无文档、只有二手转述找不到原始出处

### 0.3 选题卡（必须回显，等一句确认；用户不回即按默认继续）

```
选题卡
主对象：<项目/规范名> <仓库地址>
主题域：架构 / harness / skill（选一个主轴）
为什么是现在：<一句，带日期或数字>
对照对象：<A 一行差异> / <B 一行差异>
证据可得：一手 <n> 类（仓库/文档/源码/论文/Release 至少 3 类）｜二手线索 <m> 条
案例实践：目标 L1 / L2 / L3（L3 需你确认预算约 <token/时间>）
预计篇幅：CJK 1200-2000（硬上限 2000，口语化）
栏目期号：NO.<已有期次数+1>
产物目录：<解析后的实际路径>
发布形态：公众号图文文章（默认）｜是否同步头条：否
```

只问一个真正需要用户拍板的问题：**要不要跑到 L2/L3（有成本）**。其余按推荐值走。

### 0.4 发布形态

默认公众号**图文文章**。用户明确要头条时再问「文章 / 微头条」，交付细则见 `cwork-article` 的对应阶段。贴图形态不在本 skill 范围内（软文需要正文排版，不适合图片即内容）。

## 阶段 1：情报采集

工具顺序：`WebSearch`（带年份/月份）→ `WebFetch` 打开原文 → GitHub API（`gh api` 可用则用，未登录注意 60 次/小时限流）→ 需渲染才用工作台浏览器。

**开工时先做一轮三域扫描**（阶段 0 已由用户直接指定主对象时跳过）：架构、harness、skill 各取 2-3 条候选（一行：对象 + 为什么是现在 + 可实践等级），再从中定主轴。目的是不因先入为主错过当下更值得写的那一个；主对象一旦确定，只深挖它，其余降为对照或舍弃。

**执行节奏**：同一批查询并行发出，不要一条条串行。源矩阵与检索式见 [sources.md](sources.md)。

### 1.1 必须取到的字段

主对象（一项不能少）：

| 字段 | 来源 | 备注 |
|------|------|------|
| 仓库地址 / 官网 | 搜索或官方页 | 链接必须能打开 |
| Star / Fork | GitHub API 或仓库页 | 记抓取日期，数字会变 |
| 最近提交 / 最新 Release | API 或仓库页 | 判断活跃度 |
| 许可证 | 仓库页 | 影响能否本地实践与商用讨论 |
| 核心依赖与运行门槛 | README / 配置文件 | 语言版本、模型 key、GPU/浏览器/DB |
| 定位一句话 | README 首段 | 用作者自己的话，再给中文解释 |
| 关键数字 | 官方文档/论文/榜单 | 必须带口径 |

对照对象（至少 2 个）：各取「定位、差异点、代价」三行即可，不展开成第二篇。

### 1.2 证据规则（硬约束）

- **禁止编造**：仓库地址、星数、版本号、许可证、榜单分数、发布日期。查不到就写「未获取」。
- **一手优先**：README/源码/官方文档/论文 > 作者博客与发布说明 > 社区讨论 > 科技媒体。
- **二手降级**：只能拿到媒体转述时，正文写「据 <媒体> <日期> 报道」，不得写成已核实。
- **榜单数字必须带口径**：哪个榜、哪一期、什么 harness、什么模型与预算、pass@1 还是 resolve rate。**不同 harness 的分数不可横向比较**。
- **star 数是时点值**：文中写「截至 <日期> 约 x.x 万 star」，不写「全网最火」这类无判据结论。
- 同一说法出现多个版本（如两种 star 数）→ 取仓库页/API 值，并在 `research.md` 记「冲突与取舍」。

### 1.3 落盘 `research.md`

```
## 主对象
- 名称 / 地址 / 许可证 / 最新版本 / star(抓取日期) / 最近提交
- 定位（作者原话 + 中文解释）
- 核心能力清单（3-6 条，各一句机制）
## 对照对象
- A：定位 | 关键差异 | 代价
- B：定位 | 关键差异 | 代价
## 关键数字与口径
- 数字 | 口径（榜单/harness/模型/预算/日期）| 链接 | 一手/二手
## 社区声音
- 正反各 2-3 条（HN/Issues/Discussions），带链接
## 冲突与取舍
- 哪个数字有两个版本，最终采用哪个，为什么
```

## 阶段 2：案例实践（强制，等级见 [practice.md](practice.md)）

「结合案例实践」是本 skill 与普通解读文的区别，不能跳过。

### 2.1 选等级（先算代价，再问用户）

| 等级 | 含义 | 典型代价 | 默认 |
|------|------|----------|------|
| L0 | 只读文档 | 0 | 仅在完全无法运行时兜底，需说明原因 |
| L1 | 读关键源码/配置，画出调用链 | 30-60 分钟 | 保底必须做到 |
| L2 | 本地装起来跑通最小任务 | 1-2 小时 + 少量模型费用 | 有入口时优先 |
| L3 | 用固定 harness 跑小规模基准 | 半天 + 明显模型费用 | 需用户明确同意 |

- harness/基准类主题默认 **L1 + 引用他人公开实测**；要自己跑 L3 必须先报预算。
- skill 类主题天然适合 **L2**：写一个最小 skill，实测它是否会被正确触发、边界在哪。
- 架构类主题优先 **L2**：跑通官方最小 demo，记录一次真实输入输出。

### 2.2 安全边界（硬约束）

1. 在 `$CONTENT_DIR/agent-workshop/20261121-<slug>/sandbox/` 或系统临时目录里做，**不污染仓库、不提交产物**。
2. 装依赖前先读 `package.json` / `pyproject.toml` / `Makefile`，识别 `postinstall`、`curl | bash`、docker 拉取等隐式动作；能 `--ignore-scripts` 就先忽略脚本。
3. 密钥只走环境变量，**不写进任何落盘文件、不进截图、不进文章**；跑完清理。
4. 不连生产数据、不执行未知二进制、不 star/fork/开 issue 等写操作。
5. 模型调用设上限（如单次任务 ≤ 20 次请求），超出就停，如实写「预算耗尽，未完成」。

### 2.3 记录 `practice-log.md`

固定格式，正文里能直接引用的实验事实只从这里取：

```
## 环境
OS / 语言版本 / 关键依赖版本 / 模型与接口 / 硬件
## 步骤
1. <命令> → <结果摘要（截断长输出）>
## 结果
成功/失败 | 耗时 | 请求数/token 估算 | 费用估算 | 是否可复现
## 失败点与坑
（依赖冲突、权限、限流、模型不支持工具调用……失败点往往是最有价值的内容）
## 可写进文章的事实
- 【L2】…（每条一句，带数字）
```

## 阶段 3：论证与写作

### 3.1 先加载人格

撰写前读 `.cwork/refs/cwork-tech-writer/SKILL.md`（源仓库 `skills/tech-writer/SKILL.md`），提取「思维框架 + 语言风格 + 写作套路」，作为内容约束。**人格只决定怎么说，不改变 HTML 排版交付形态**。

### 3.2 文章的论证主线（固定七段，骨架见 [template.md](template.md)）

```
1 钩子：一个具体场景里的痛点（不是宏大叙事）
2 结论先行：3 条要点，读完这三条也能走
3 拆解：它怎么做到的（架构/流程/关键机制）
4 能力特性表：能力 → 机制 → 边界/代价
5 案例实践：我跑的或别人跑的，逐条标证据等级
6 场景价值：个人开发者 / 团队工程 / 业务方，三类读者的「原来 → 现在 → 价值/代价」
7 冷静判断 + 最小行动：不适用场景、隐藏成本、30 分钟能验证的第一件事
```

### 3.3 「能力特性 → 场景价值」是本 skill 的核心产出（硬约束）

每篇文章必须有一张完整映射表，且正文对每一行展开一段，**不能只列表不解释**：

| 能力特性 | 机制（一句话） | 场景价值（谁、原来怎样、现在怎样） | 代价 / 边界 |
|----------|----------------|-----------------------------------|-------------|
| 例：技能包按需加载 | 只把描述常驻上下文，命中才读全文 | 团队把 SOP 沉淀成 skill，新人不用背提示词 | 描述写得差就不触发 |

场景价值必须落到**具体的人与动作**，禁止「提升效率」「赋能业务」这类空话。三类读者里至少写透两类：

- **个人开发者**：省掉什么重复劳动、学习曲线多长、要不要花钱
- **团队工程**：协作方式/交付流程哪里变了、评测与回归怎么做、维护成本
- **业务方**：哪个环节的交付周期或质量变了、风险与合规边界

### 3.4 不吹不黑（硬约束）

- 每个优势后紧跟一个代价或适用边界；找不到代价说明还没拆透。
- 作者自述性能一律标「作者自述」；二手数据标来源；自己没跑过的写「未验证」。
- 不写「颠覆」「吊打」「必学」这类无判据判断；对比只在同口径下进行。
- 术语首次出现给一句人话解释，别假设读者懂 A2A、pass@1。

### 3.5 篇幅与结构（硬约束）

- 正文 CJK **1200-2000**，**上限 2000，不得超**。计数口径：`body.html` 去标签后的汉字数（`node -e` 统计 `[\u4e00-\u9fff]`），这是验收的唯一判据。
- 公众号编辑器右下角的「正文字数」会把英文、数字、标点、空格都算进去，通常比 CJK 高 30%-50%（20261121 实跑：CJK 1661，编辑器显示 2340）。汇报时附上编辑器值，但**不用它判超限**。
- 压字数只能砍冗余解释、过渡句和排比，**不许砍代价、边界、来源、口径**——这些是文章的骨架。
- 每 300-500 字一个小标题（2000 字内一般 6-8 个 `<h2>`）；代码/命令块每段 ≤ 10 行，只留关键行。
- 标题、核心结论先给用户过一眼（标题 3-5 选 1 + 结论 3 条），确认后才进排版。

### 3.6 口语化（硬约束）

成稿要像跟同事说话，不像念报告。按这八条落地：

- **开场给场景**：一次选型会、一次 Debug、一次帮朋友看方案，3-4 句讲清谁被什么卡住。禁止「随着……的发展」「在……背景下」起头。
- **短句 + 转折**：多用「可真跑起来」「说白了」「追到根上」「结果呢」这类口语连接，少用「因此」「基于此」「综上」。
- **用你我，不用第三人称堆砌**：别通篇「用户」「开发者」「从业者」，能说「你」就说「你」。
- **禁用 AI 腔词表**：赋能、闭环、抓手、底层逻辑、重塑、一站式、全方位、综上所述、不难看出、值得注意的是、总的来说、在某种程度上、从……角度来看。出现即改写。
- **段落 60-120 字**，一段只说一件事；不写三段排比，不堆长破折号。
- **口语不等于模糊**：数字、版本号、日期、来源一个都不能省，省掉的是形容词和过渡废话。
- **术语第一出现给人话**：harness 就是「评测这副架子」，agent 就是「会自己动手的模型」。
- **出声自检**：写完挑最像报告的三段念一遍，念着别扭、或者「不会跟同事这么说」，就按日常说法重写。

## 阶段 4：排版与封面

1. 正文 = **HTML + inline CSS**，直接复制 [template.md](template.md) 骨架填内容；公众号编辑器不吃 class。
2. 视觉元素至少 4 种：证据等级徽标、能力卡、命令块、对比卡、金句块、来源区。
3. 证据等级徽标必须与 `practice-log.md` / `research.md` 一一对应，不许升级标注。
4. **封面（强制）** 两段式：
   - a) ImageGen 出**无文字底图**（`size="2560x1080"`，prompt 见 template.md），存 `images/00-cover.png`；
   - b) 复用速递脚本叠中文大字（中文绝不让 ImageGen 直出）：

```bash
ISSUE=20261121-claude-skills   # 本期目录名，按实际替换
node skills/tech-express/scripts/make-cover-poster.cjs \
  --dir "$CONTENT_DIR/agent-workshop/$ISSUE" \
  --title "Agent 工坊" \
  --date "11月21日" \
  --sub "本期主题一句话" \
  --kicker "AGENT WORKSHOP · DEEP DIVE"
powershell -ExecutionPolicy Bypass -File skills/tech-express/scripts/make-cover.ps1 -Dir "$CONTENT_DIR/agent-workshop/$ISSUE"
```

## 反模式

- 把 skill 写成第二个 tech-express：多条快讯并列、每条一两段，没有主对象
- 只搬 README 和二手博客，没读源码也没跑案例（L0 当默认）
- 跑通一个 hello world 就写「生产可用」「开箱即用」
- 拿不同 harness / 不同模型 / 不同预算的分数横向比较
- 把作者自述性能、媒体标题里的数字当实测写
- 场景价值写成「提升效率、赋能业务、降本增效」——没有具体的人和动作
- 通篇 AI 腔（赋能 / 闭环 / 底层逻辑 / 综上所述），读着像报告不像人说话
- 为了压到 2000 字以内去砍代价、边界或来源，把文章压成安利稿
- 每个优势都不配代价，通篇安利
- star 数、版本号、许可证凭记忆写，或写「全网最火」这类无判据结论
- 证据等级在正文里私自升级（L1 写成「我实测」）
- 在文章或截图里暴露 API key、内网地址、账号信息
- 在仓库里跑实验、提交产物、留下 sandbox 目录
- 手工拼 HTML 注入正文；注入失败反复新建草稿
- 保存后重开编辑器复验（触发自动保存版本合并）
- 只交 Markdown/纯文本，或只写大字报封面建议不实际出图
- 让 ImageGen 直画中文大字（汉字必错）
- 未确认标题与核心结论就写入草稿
- 自动化点「发表」或代点「声明原创」
