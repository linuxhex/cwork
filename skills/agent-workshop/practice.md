# Agent 工坊 · 案例实践手册

「结合案例实践」不是跑个 hello world 截图，而是用一次**可复现、可交代代价**的实验，验证文章里的某个结论。本文件规定怎么选等级、怎么保安全、怎么记录。

---

## 一、先做可行性三问（决定 L1 还是 L2/L3）

| 问题 | 是 | 否 |
|------|----|----|
| 有调用模型/服务的凭据或额度吗？ | 可冲 L2/L3 | 只能 L1（读源码画链路） |
| 运行门槛可接受吗？（GPU / 浏览器 / DB / 私有服务 / 内网） | 可 L2 | 降 L1，或换一个可跑的主对象 |
| 许可证允许本地实验吗？ | 可 L1-L3 | **只做 L1 阅读**，且文中不讨论商用 |
| 时间预算够吗？（L2 约 1-2h，L3 约半天） | 按目标等级执行 | 降级并告知用户 |

**结论写进选题卡**：目标等级 + 预估耗时 + 预估费用。等级变化要主动汇报，不静默降级。

## 二、安全边界（硬约束，违反即停止实验）

1. **隔离**：实验目录固定在 `$CONTENT_DIR/agent-workshop/20261121-<slug>/sandbox/`（或系统临时目录），不放进仓库，不 `git add`，结束后清理或保留在内容目录。
2. **先读再装**：装依赖前读 `package.json` / `pyproject.toml` / `Makefile` / Dockerfile，标出 `postinstall`、`prepare`、`curl | bash`、镜像拉取等隐式动作。能 `npm install --ignore-scripts` / `pip install --no-deps` 就先走保守路径。
3. **凭据**：只通过环境变量注入；不写入 `.env` 以外的落盘文件（`.env` 放 sandbox 且不提交）；不截进图；文章里不出现任何 key、token、内网地址、账号名。
4. **数据**：不连接生产数据库、不读取个人/客户数据；需要样本时自造最小样例。
5. **写操作**：只读仓库内容；不 star/fork/create issue/提 PR；不触发付费额度之外的重试风暴。
6. **上限**：提前设好请求数/时长上限（如单任务 ≤ 20 次模型调用、总时长 ≤ 30 分钟），触顶即停并如实记录「预算耗尽」。
7. **未知二进制**：来源不明的可执行文件一律不跑。

## 三、最小实践范式

### 3.1 L2 通用（架构类 / 工具类）

```
1. 记录环境：OS、语言版本、包管理器、模型与接口、硬件
2. 按官方文档走最短路径：安装 → 配置 → 跑官方最小示例
3. 用自造的一个真实小任务替换示例输入（避免只复述 README）
4. 记录：输入、输出、耗时、调用次数/token、报错与绕过方式
5. 尝试一个边界：缺工具时的行为 / 超长输入 / 无网络 / 错误 key
```

边界实验比「跑通了」更有信息量：它决定了文章里「代价 / 边界」那一列能写什么。

### 3.2 Skill 类专用（成本最低，强烈推荐 L2）

适合验证「技能包到底怎么被触发」：

```
1. 在 sandbox 里写一个最小 skill：frontmatter（name/description）+ 一段可验证的行为
2. 用真实请求测试：
   - 正例：描述命中，skill 被加载并生效
   - 反例：描述不该命中的请求，确认不误触发
   - 擦边：同义表达、中英文混杂，记录是否触发
3. 记录触发/不触发/误触发三类结果，以及加载后输出差异
4. 结论只能写到这个范围：描述措辞如何影响触发，不延伸成「能力上限」
```

### 3.3 Harness / 基准类（L3 需用户同意预算）

```
1. 固定 harness 版本（commit/tag）与任务子集（如 10 题，注明抽样方式）
2. 固定模型、温度、最大步数/预算
3. 记录原始输出与结果文件路径
4. 报三个数：通过率、平均耗时、平均成本
5. 明确不做的事：不跨 harness 比、不用 1-2 题下结论、不把子集成绩说成榜单成绩
```

拿不到预算时走 **L1 + 公开结果**：读 harness 源码说明「它怎么判分、哪里可能被刷分」，引用官方榜单并标注口径。

## 四、`practice-log.md` 固定格式

```markdown
## 环境
- OS / 语言版本 / 关键依赖版本 / 模型与接口 / 硬件
## 目标
- 本次要验证的假设（一句话）
## 步骤
1. <命令>
   → <结果摘要，长输出只留关键 5-10 行>
2. ...
## 结果
- 结论：成立 / 不成立 / 部分成立
- 耗时：<>｜请求数：<>｜token 估算：<>｜费用估算：<>
- 可复现：是 / 否（阻塞点：<>）
## 失败点与坑
- <依赖冲突 / 权限 / 限流 / 工具调用不被支持 / 文档与实现不一致>
## 可写进文章的事实
- 【L2】<一句，带数字>
- 【L1】<一句，标注来自哪个文件/函数>
```

**规则**：正文只能引用「可写进文章的事实」里的条目；每条都要能落回上面的步骤或来源。

## 五、失败也是素材（但要说清是哪种失败）

| 失败类型 | 能不能写 | 怎么写 |
|----------|----------|--------|
| 环境/依赖问题 | 能 | 写清版本与报错，给绕过方法 |
| 文档与实现不一致 | 能，价值高 | 给出文档原话 + 实际行为 + 版本号 |
| 能力边界（不支持某工具/超长上下文崩） | 能，价值最高 | 给输入条件与现象，不下「不可用」的绝对结论 |
| 自己没 key / 没 GPU | 能，但降级 | 明确写「因缺 <条件> 未完成，以下为 L1/公开数据」 |
| 时间不够 | 能 | 汇报里说明，不假装跑过 |
| 安全边界阻止 | 能 | 说明因安全未执行，结论留待验证 |

## 六、反模式

- 只跑官方 hello world，然后把 README 的定位复述成「实测结论」
- 没有记录环境与版本，别人无法复现
- 用 1-2 个样本得出通过率，或把子集成绩写成榜单成绩
- 跨 harness / 跨模型预算比较分数
- 把作者自述性能、发布会 PPT 数字转成「我实测」
- 实验产物、日志、`.env` 留在仓库或提交进 git
- 截图里带 key、内网域名、账号信息
- 触发上限后继续重试烧钱，或隐瞒预算耗尽
- 拿「跑不通」当能力结论，却不区分是环境问题还是产品问题
