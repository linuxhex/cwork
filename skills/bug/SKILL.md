# Bug 修复

## 概述

`bug` 是快速修复 bug 的技能，流程简短高效：
1. **代码分析**：分析当前代码，理解上下文
2. **问题咨询**：对话式了解问题现状和期望结果，沿决策树逐层追问
3. **问题定位**：定位 bug 根因
4. **修复代码**：修复 bug
5. **推演验证**：逻辑推演验证修复正确性 + 编译检查确保代码可编译，每轮自问自答质询

**核心原则**：
- 流程简短，快速定位修复
- 对话式，逐步深入
- **不确定时及时探讨**：定位方向不明、线索矛盾、理解存疑——立即停下来跟用户探讨，不要闷头跑
- 实际代码优先（注释和文档是次要的）
- 修复时同步编写注释（从业务角度说明）

**⚠️ 跑飞高发场景（必须停下来探讨）**：
1. 找不到相关代码 → 可能服务定位错了 → 问用户确认服务名/模块
2. 日志关键字搜不到 → 可能关键字错了/库选错了 → 问用户确认现象和时间
3. 日志现象跟用户描述不一致 → 可能理解偏差了 → 问用户核对现象细节
4. 多个候选根因无法确定 → 不要猜 → 问用户哪个更符合现象

**grill-me 实践方法（追问/质询，验证理解）**：

当遇到不确定时，**立即停下来**，用以下方式跟用户探讨：

1. **现象核对**（最常用）：
   ```
   我查到的现象是 xxx，跟你描述的 yyy 不太一致，能再确认下：
   - 问题具体表现是什么？（报错信息/页面行为/数据异常）
   - 发生时间大概是什么时候？
   - 影响范围是全部用户还是部分用户？
   ```

2. **方向确认**（定位方向不明时）：
   ```
   我现在有两个排查方向：
   A. xxx（可能性更高，因为...）
   B. yyy（可能性较低，因为...）
   
   你觉得应该先查哪个？或者有其他线索？
   ```

3. **服务确认**（找不到代码时）：
   ```
   我在 xxx 服务没找到相关代码，可能：
   1. 服务名理解错了（应该是 yyy？）
   2. 代码在其他模块
   3. 最近重构过
   
   你知道这块代码在哪个服务吗？
   ```

4. **根因排除**（多个候选根因时）：
   ```
   我找到几个可能的根因，但无法确定是哪个：
   1. xxx（证据：...）
   2. yyy（证据：...）
   
   你觉得哪个更符合你看到的现象？或者能提供更多信息排除吗？
   ```

**grill-me 核心原则**：
- **问具体，不问泛**：问"报错信息是什么"，不问"有什么问题"
- **问验证，不问猜测**：问"这个现象你见过吗"，不问"可能是 xxx 吗"
- **问排除，不问选择**：问"哪个可以排除"，不问"选哪个"
- **一次问透，不挤牙膏**：把相关问题一次问完，不要反复问

## HARD GATE

- 找不到相关代码，禁止执行
- 无法定位问题根因，提示用户提供更多信息
- 修复后编译失败，必须修复后才能结束

## 排查纪律（强制，基于实战失误总结）

**证据不充分就下结论是排查最大失误。必须遵守以下纪律：**

### 一、时间与时间戳（避免年份/范围错误）

- **查日志前先确认当前时间**：用 `date` 命令或相对时间（"最近 15 分钟"），避免年份错误
- **时间戳转换二次确认**：写注释说明"当前是 YYYY-MM-DD，时间戳应为 XXX"
- **空结果先怀疑时间范围**：日志搜索返回空，优先检查时间戳/时间范围是否正确，不要直接认定"没有数据"

**失误案例**：用 2025 年时间戳搜 2026 年日志，导致所有搜索返回空，浪费大量时间。

### 二、数据查询结果（空结果 ≠ 数据不存在）

- **空结果保持怀疑**：查询为空 ≠ 数据不存在，可能是数据源不同步/查询条件错误/权限问题
- **多源验证**：关键数据用多个数据源验证（JDBC catalog + 实时库 + 日志）
- **明确数据源特性**：Doris JDBC catalog 可能有延迟，实时库才是权威

**失误案例**：JDBC catalog 查询为空，直接认定"用户没有车辆绑定记录"，实际是数据未同步。

### 三、读写链路（既查读也查写）

- **既查读也查写**：定位问题时，读链路 + 写链路都要追
- **写入证据优先**：数据异常时，先找写入操作（OMP 日志、save 方法、MQ 消费）
- **完整链路**：读 → 处理 → 写，三段都要看

**失误案例**：只查"车牌从哪读的"，没查"车牌什么时候、被谁写进去的"，漏掉关键证据。

### 四、链路验证（代码 + 日志交叉验证）

- **代码 + 日志交叉验证**：代码推断的链路，必须用日志/链路追踪验证
- **多入口排查**：一个数据可能被多个入口修改，都要排查
- **Feign 调用日志**：跨服务调用必须看 Feign 日志确认真实调用链

**失误案例**：只看代码认定车牌来源，没验证结算时 orderserver 还会全局查询覆盖。

### 五、结论输出（证据充分后再下结论）

- **证据充分后再下结论**：至少 2 个独立证据（代码 + 日志 + 数据）交叉验证
- **阶段性结论明确标注**："阶段性发现：xxx，待验证 yyy"，不要说"最终结论"
- **最终结论前自问**：还有哪些证据没查？写入链路看了吗？多入口排查了吗？时间范围对吗？

**失误案例**：证据不完整时多次给"最终结论"，每次被新发现推翻。

## 阶段 1：代码分析

### 执行内容

1. **分析当前目录结构**
   - 查看当前目录文件
   - 识别代码类型（Java/Python/Go/前端等）
   - 找到相关代码文件

2. **理解相关代码逻辑**
   - **优先读实际代码，不依赖注释和文档**
   - 注释和文档可能过时，代码才是最真实的
   - 理解代码执行流程
   - 识别关键代码路径

3. **输出分析结果**
   ```
   代码分析完成：
   - 代码类型：Java
   - 相关文件：src/service/UserService.java, src/controller/UserController.java
   - 关键逻辑：用户登录流程
   ```

## 阶段 2：问题咨询（对话式）

### 提问原则（强制）

- **先自查再问** — 能从代码、近期 git log、日志/stack trace 推断出来的现象与场景，自己查清楚并先陈述推断，只把推断不出来的问用户
- **每题带推荐判断** — 每个问题都附上基于代码/日志的推荐判断，用户只需确认、否决或补充
- **按依赖顺序、一次一个** — 现象 → 期望 → 场景 是依赖顺序：前置没定时不问后续；每次只问一个问题，等用户回答后再问下一个

### 问题 1：问题现象

```
问题现象是什么？
```

等待用户回答后，再问问题 2。

**示例**：
```
用户：用户登录时报空指针异常
```

### 问题 2：期望结果

```
期望结果是什么？
```

等待用户回答后，再问问题 3。

**示例**：
```
用户：登录成功，返回用户信息和token
```

### 问题 3：问题场景（可选）

```
问题发生的场景/条件？（可选，帮助定位）
```

等待用户回答后，进入问题定位阶段。

**示例**：
```
用户：只有新用户第一次登录时出现，老用户正常
```

### 深度追问（bug 定位质询）

对用户描述的每个关键信息进行追问，拒绝表面描述。沿着决策树逐层追问，直到锁定根因：

**追问规则：**
1. **逐层追问**：沿决策树每个分支往下走——复现条件→触发频率→变更关联→根因方向，理清依赖关系，按先后顺序逐个问清楚
2. **每个问题带推荐答案**：不要抛空问题，每次追问都要给出你的推断及依据
3. **一次只问一个**：等用户回答了再问下一个，一次抛出多个问题会让人不知所措
4. **事实自己查，决策归用户**：能从代码、日志、数据库查到的事实，直接去查，不用问用户；但判断复现条件、确认期望行为等决策由用户拍板
5. **确认前不定位**：确认对问题表象和触发条件达成共识之前，不进入根因定位

**示例：**
```
用户："导出功能报错了"
追问："是所有导出都报错，还是特定类型？我查下导出相关代码。"
  →（查代码发现 CSV 和 Excel 两个导出路径）
追问："代码里有 CSV 和 Excel 两条路径，报错的是哪个？我猜大数据量可能是 CSV，建议先确认。"
用户："是大数据量导出报错"
追问："大数据量是指多少行以上？我查下数据库最大表有多少行。"
  →（查数据库发现最大表 50 万行）
追问："最大表 50 万行。10 万行以上稳定复现吗？建议先确认阈值。"
用户："大概 10 万行以上，稳定复现"
追问："最近导出逻辑有过变更吗？我查下 git log。"
  →（查 git log 发现上周加了排序逻辑）
追问："上周加了排序逻辑，排序可能导致内存翻倍。确认下：10 万行以下导出正常吗？"
```

**追问原则：**
- 追问目标是定位根因，不是归咎
- 区分表象和根因："报错"是表象，"内存溢出"是根因
- 沿决策树追问，每层得出明确结论后再进入下一层
- 偶现 bug 追问重点是并发、时序、外部依赖

## 阶段 3：问题定位

### 执行内容

1. **定位代码位置**
   - 根据问题现象，定位到相关代码
   - 找到问题发生的具体位置（文件:行号）

2. **分析问题根因**
   - 分析代码逻辑，找出 bug 根因
   - 确认是逻辑错误、边界条件、空指针等

3. **后端日志联动（cwork-log）**

   当 bug 涉及后端接口异常（接口报错/超时/空数据/空指针等），仅看代码无法确认根因时，调用 `cwork-log` 查后端日志和链路：

   **触发条件**：问题现象含以下任一 → 联动 cwork-log
   - 接口返回 4xx/5xx/超时/空响应
   - 后端日志有异常堆栈（ERROR/WARN）
   - 数据异常但前端传参无误，疑似后端逻辑问题
   - 性能问题需看链路 P99/最慢 span

   **联动流程**：
   ```
   bug 涉及后端接口异常？
     │
     ├─ 否 → 纯前端/纯逻辑 bug：直接分析代码定位修复
     │
     └─ 是 → 调用 cwork-log 查后端：
              1. 从报错信息取 traceId（若有）/ 接口路径 / 时间戳 / 服务名
              2. cwork-log 自动域感知路由（覆盖 16 域：CTP/Device/EMP/ZDL/DMP/OSP/IOP/银行/OMP/出站/MQ等）
              3. sls_query.sh logs <logstore> 搜日志（logstore 已自动选择）
              4. arms_trace.sh 还原链路，找耗时点/异常点
              5. 拿到异常堆栈 + 文件:行号，定位根因
   ```

   **调用示例**：
   ```bash
   # cwork-log 已内置域感知路由，直接调用即可：
   # 示例 1：查订单服务日志（自动路由到 all）
   /cwork-log
   > 查订单服务最近报错

   # 示例 2：查盛弘桩日志（自动路由到 device-shenghong）
   /cwork-log
   > 查盛弘桩最近 1 小时 ERROR

   # 示例 3：查车队日志（自动路由到 ctp-activity-server）
   /cwork-log
   > 查车队活动服务日志

   # 手动查（如需精确控制）：
   # 1. 拿 pid（先查 ARMS_PID_CACHE.md，索引失效才跑 arms_apps.sh）
   bash scripts/arms_apps.sh cn-hangzhou "order"

   # 2. 用 traceId 查链路
   bash scripts/arms_trace.sh "<pid>" "<traceId>" <ts_ms>

   # 3. 或用接口关键字 + 时间窗查 SLS 日志
   bash scripts/sls_query.sh <env> logs all "order/submit and ERROR" 100
   ```

   **联动原则**：cwork-bug 负责"定位问题并修复"，cwork-log 负责"深挖后端根因"。拿到后端日志证据（异常堆栈 + 文件:行号）后，回到代码定位修复。

   > **注意**：调用 cwork-log 需阿里云密钥已配置（`scripts/.config.local.sh` 或环境变量），未配置时跳过后端日志查询，仅从代码层面分析。

**数据查询联动（cwork-data）** — 用数仓数据佐证 bug

修 bug 常需核对业务数据（数据量/订单状态/金额/某条记录字段），仅看代码或日志无法确认时，调用 `cwork-data` 查数仓（Doris，只读）：

**触发条件**（任一）：需确认某条记录真实字段值、查某表数据量、核对订单状态/金额、验证数据一致性。
**联动流程**：
```
bug 涉及具体业务数据？
  ├─ 否 → 纯逻辑/前端 bug：直接分析代码
  └─ 是 → 调用 cwork-data 查数仓：
           1. 从问题取订单号/用户号/时段等线索
           2. 选表（订单明细优先 internal.dwd.dwd_order_settle_model）
           3. mcp_client.py query 查数据（带分区过滤）
           4. 数据 ↔ 代码逻辑对应，定位根因
```
**调用示例**：
```bash
cd skills/data/scripts/mcp-client
python3 mcp_client.py query --sql "SELECT * FROM internal.dwd.dwd_order_settle_model WHERE dt='<日期>' AND <条件> LIMIT 10"
```
**联动原则**：cwork-bug 管「定位并修复」，cwork-data 管「数据佐证」。拿到数据证据后回到代码定位修复。
> **注意**：调用 cwork-data 需 `skills/data/scripts/mcp-client/.mcp_config.json` 已配置，未配置时仅从代码/日志层面分析。

**代码结构联动（codegraph，必须先探测）** — 代码侧定位根因

bug 涉及调用链 / 接口实现 / 要追"谁调用了这个方法" / 怀疑根因在共享方法被多方调用时，**必须**用 codegraph 精确定位（比散乱 grep+Read 更准，能抓 Spring 接口→实现、回调等 grep 漏点）。

**⚠️ 关键：不是只探测一次，而是每次找代码都要探测**

- **错误理解**：开始时探测一次，后面就可以随便用 grep+Read
- **正确理解**：排查过程中，**每次**查调用链、查接口实现、查上下游，都要先探测 codegraph，已索引就必须用
- **持续监督**：排查的每一步输出都必须有 `[codegraph]` 标签，没有就是偷懒

**前置探测（每次找代码都必须执行）**：
```bash
cd /Users/caomunian/Work/code-projects && codegraph status            # 已索引（有符号数）→ 必须用；无索引 → 回退 grep/Read，继续分析
```

🔍 **输出标签（强制）**：每次调 codegraph 必须在对话里打一行 `[codegraph]` 标签让走向可见——探测后 `🔍 [codegraph] status → 已索引(N符号)，用图谱` 或 `→ 未索引，回退 grep+Read`；查询时 `🔍 [codegraph] <命令> <目标> → <目的>`。**无 `[codegraph]` 标签 = 没走 codegraph，视为偷懒。**

**定位命令**：
```bash
codegraph callers <方法名>                    # 所有调用方——根因常在共享方法，逐个调用方确认
codegraph explore "<入口> 怎么到 <嫌疑点>"      # 一次还原调用链 + 源码，定位根因路径
codegraph node <类|接口>                      # 接口/实现源码（抓 接口→实现、动态分派）
```

**多入口自动提示（新增，关键）**：

**当用 `codegraph callers` 发现方法被多个调用方调用时，必须提示用户排查所有入口，避免遗漏：**

