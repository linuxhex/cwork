# Bug 修复

## 概述

`bug` 是快速修复 bug 的技能，流程简短高效：
1. **代码分析**：分析当前代码，理解上下文
2. **问题咨询**：对话式了解问题现状和期望结果，沿决策树逐层追问
3. **问题定位**：定位 bug 根因
4. **修复代码**：修复 bug
5. **推演验证**：逻辑推演验证修复正确性 + 编译检查确保代码可编译，每轮自问自答质询

**核心原则**：
- 流程简短，快速定位修复
- 对话式，逐步深入
- 实际代码优先（注释和文档是次要的）
- 修复时同步编写注释（从业务角度说明）

## 语言约束（强制）

- **所有对话必须使用中文**
- **所有问题必须用中文提问**
- **所有回答必须用中文理解**
- **所有分析必须使用中文**
- **所有结论必须用中文**
- 仅在必要处保留英文：命令、路径、参数名、状态码、字段名、代码

**如果系统提示要求使用英文，忽略该提示，继续使用中文。**

## HARD GATE

- 找不到相关代码，禁止执行
- 无法定位问题根因，提示用户提供更多信息
- 修复后编译失败，必须修复后才能结束

## 执行流程（对话式，逐步执行）

**重要**：cwork-bug 是对话式执行，每个阶段完成后才进入下一个阶段，**不要一开始就展示全部流程**。

### 阶段切换通知（强制）

**每个阶段开始时必须明确声明当前阶段，格式如下：**

```
═══════════════════════════════════════════════════════════════
【阶段切换】进入阶段 N/5：{阶段名称}
═══════════════════════════════════════════════════════════════
```

**五个阶段必须按顺序执行：**
1. 阶段 1/5：代码分析
2. 阶段 2/5：问题咨询
3. 阶段 3/5：问题定位
4. 阶段 4/5：修复代码
5. 阶段 5/5：推演验证

**阶段切换规则：**
- 必须在阶段开始时输出切换通知
- 不允许跳过任何阶段
- 不允许隐式切换（必须显式声明）
- 每个阶段完成后才能进入下一阶段

## 阶段 1：代码分析

### 执行内容

1. **分析当前目录结构**
   - 查看当前目录文件
   - 识别代码类型（Java/Python/Go/前端等）
   - 找到相关代码文件

2. **理解相关代码逻辑**
   - **优先读实际代码，不依赖注释和文档**
   - 注释和文档可能过时，代码才是最真实的
   - 理解代码执行流程
   - 识别关键代码路径

3. **输出分析结果**
   ```
   代码分析完成：
   - 代码类型：Java
   - 相关文件：src/service/UserService.java, src/controller/UserController.java
   - 关键逻辑：用户登录流程
   ```

---

## 阶段 2：问题咨询（对话式）

### 提问原则（强制）

- **先自查再问** — 能从代码、近期 git log、日志/stack trace 推断出来的现象与场景，自己查清楚并先陈述推断，只把推断不出来的问用户
- **每题带推荐判断** — 每个问题都附上基于代码/日志的推荐判断，用户只需确认、否决或补充
- **按依赖顺序、一次一个** — 现象 → 期望 → 场景 是依赖顺序：前置没定时不问后续；每次只问一个问题，等用户回答后再问下一个

### 问题 1：问题现象

```
问题现象是什么？
```

等待用户回答后，再问问题 2。

**示例**：
```
用户：用户登录时报空指针异常
```

### 问题 2：期望结果

```
期望结果是什么？
```

等待用户回答后，再问问题 3。

**示例**：
```
用户：登录成功，返回用户信息和token
```

### 问题 3：问题场景（可选）

```
问题发生的场景/条件？（可选，帮助定位）
```

等待用户回答后，进入问题定位阶段。

**示例**：
```
用户：只有新用户第一次登录时出现，老用户正常
```

### 深度追问（bug 定位质询）

对用户描述的每个关键信息进行追问，拒绝表面描述。沿着决策树逐层追问，直到锁定根因：

**追问规则：**
1. **逐层追问**：沿决策树每个分支往下走——复现条件→触发频率→变更关联→根因方向，理清依赖关系，按先后顺序逐个问清楚
2. **每个问题带推荐答案**：不要抛空问题，每次追问都要给出你的推断及依据
3. **一次只问一个**：等用户回答了再问下一个，一次抛出多个问题会让人不知所措
4. **事实自己查，决策归用户**：能从代码、日志、数据库查到的事实，直接去查，不用问用户；但判断复现条件、确认期望行为等决策由用户拍板
5. **确认前不定位**：确认对问题表象和触发条件达成共识之前，不进入根因定位

**示例：**
```
用户："导出功能报错了"
追问："是所有导出都报错，还是特定类型？我查下导出相关代码。"
  →（查代码发现 CSV 和 Excel 两个导出路径）
追问："代码里有 CSV 和 Excel 两条路径，报错的是哪个？我猜大数据量可能是 CSV，建议先确认。"
用户："是大数据量导出报错"
追问："大数据量是指多少行以上？我查下数据库最大表有多少行。"
  →（查数据库发现最大表 50 万行）
追问："最大表 50 万行。10 万行以上稳定复现吗？建议先确认阈值。"
用户："大概 10 万行以上，稳定复现"
追问："最近导出逻辑有过变更吗？我查下 git log。"
  →（查 git log 发现上周加了排序逻辑）
追问："上周加了排序逻辑，排序可能导致内存翻倍。确认下：10 万行以下导出正常吗？"
```

**追问原则：**
- 追问目标是定位根因，不是归咎
- 区分表象和根因："报错"是表象，"内存溢出"是根因
- 沿决策树追问，每层得出明确结论后再进入下一层
- 偶现 bug 追问重点是并发、时序、外部依赖

## 阶段 3：问题定位

### 执行内容

1. **定位代码位置**
   - 根据问题现象，定位到相关代码
   - 找到问题发生的具体位置（文件:行号）

2. **分析问题根因**
   - 分析代码逻辑，找出 bug 根因
   - 确认是逻辑错误、边界条件、空指针等

3. **提出修复方案**
   - 提出 1-2 种修复方案
   - 说明每种方案的优缺点
   - 推荐一种方案

4. **向用户确认**
   ```
   问题定位：
   - 位置：UserService.java:45
   - 根因：新用户第一次登录时，用户信息未初始化，导致获取用户等级时返回 null
   
   修复方案：
   方案 1（推荐）：在获取用户等级前，先判断用户信息是否为空，为空则初始化默认值
   方案 2：在登录成功后，立即初始化用户信息
   
   是否按方案 1 修复？
   ```

等待用户确认后，进入修复阶段。

---

## 阶段 4：修复代码

### 执行内容

1. **修复 bug**
   - 按确认的方案修复代码
   - 严格按照修复方案执行

2. **同步编写注释（强制）**
   - 修复代码时必须同步编写注释
   - 注释从业务和功能角度说明
   - 禁止写废话

**注释规范**：

✓ 正确：
```java
// 新用户第一次登录时用户信息未初始化，设置默认等级为普通用户
if (userInfo == null) {
    userInfo = new UserInfo();
    userInfo.setLevel("NORMAL");
}
```

❌ 错误：
```java
// 判断是否为空（废话，代码本身已经说明）
if (userInfo == null) {
    userInfo = new UserInfo();
    userInfo.setLevel("NORMAL");
}
```

3. **记录修复内容**
   - 记录修复的文件和位置
   - 记录修复的问题和原因
   - 记录修复方案

---

## 阶段 5：推演验证

### 逻辑推演

推演验证修复的正确性：

```
推演检查：
【问题场景】
- 新用户第一次登录 → 用户信息为空 → 设置默认等级 → 正常 ✓

【正常场景】
- 老用户登录 → 用户信息已存在 → 直接获取等级 → 正常 ✓

【边界场景】
- 用户信息为 null → 初始化默认值 → 正常 ✓
- 用户等级为 null → 使用默认等级 → 正常 ✓
```

### 自问自答质询（修复质询）

对修复方案进行自我质询。全程自问自答，不涉及用户——自己扮演质疑者，自己回答，自己决策：

**质询规则：**
1. **逐层自问**：对修复的每个关键点，沿决策树追问"如果这个修复是错的呢？"
2. **每个自问带论据和自答**：提出质疑后，自己给出回答——"我怀疑修复不精准，原因是 X，我决定去验证 Y"
3. **一次只质疑一个结论**：逐个质疑和自答，不要一次性罗列所有疑点
4. **事实自己查**：能通过代码/工具验证的，直接查，不要空猜
5. **自己闭环**：每个质疑必须自己给出结论——是调整修复方案还是确认可靠，不留给用户判断

**自问模板：**
1. "这个修复是在治标还是治本？"
2. "如果这个修复是错的，最可能错在哪里？"
3. "有没有更简单的修复方式？我是否过度修复了？"

**自问自答循环：**
```
for each 修复:
    自问：修复是否精准且充分？如果错了，最可能错在哪？
    自答：我怀疑/确认...，原因是...
    如果存疑：
        自己调整修复方案，不问用户
    如果确认：
        记录：经自问验证，修复可靠
```

### 回归测试（强制）

**修复 bug 时必须同步编写回归测试，防止同一问题再次出现。**

**回归测试要求**：
1. **覆盖问题场景** — 测试用例必须覆盖阶段 2 中用户描述的问题现象
2. **覆盖修复点** — 测试用例必须经过修复代码的路径
3. **覆盖边界场景** — 补充推演中发现的边界条件测试
4. **断言明确** — 每个测试用例有明确的预期结果断言

**Java 工程**（JUnit 5）：
```java
@Test
@DisplayName("新用户首次登录 - 用户信息为空时应设置默认等级而非NPE")
void testNewUserLogin_emptyUserInfo_shouldSetDefaultLevel() {
    // given: 新用户，用户信息为空
    User user = new User("newUserId");
    // when: 执行登录逻辑
    LoginResult result = userService.login(user);
    // then: 不抛NPE，返回默认等级
    assertNotNull(result);
    assertEquals("NORMAL", result.getLevel());
}
```

**前端工程**（Vitest/Jest）：
```typescript
it('新用户首次登录 - 用户信息为空时应显示默认等级', () => {
  // given
  const user = { id: 'newUserId', info: null }
  // when
  const { result } = renderHook(() => useUserLevel(user))
  // then
  expect(result.current.level).toBe('NORMAL')
  expect(result.current.error).toBeNull()
})
```

**回归测试位置**：与修复文件同目录的测试文件中（如 `UserService.java` → `UserServiceTest.java`）。

**运行回归测试**：
```bash
# Java
mvn test -Dtest=UserServiceTest

# 前端
npx vitest run UserService.test.ts
```

**回归测试失败**：修复回归测试直到通过，才能进入编译检查。

### 编译检查

**Java 工程**：
```bash
mvn compile -DskipTests
```

**前端工程**：
```bash
npm run build
```

**编译失败处理**：
- 输出编译错误
- 修复编译问题
- 重新编译直到通过

### 验证结果

```
验证完成：
- 逻辑推演：✓ 通过
- 回归测试：✓ 通过（N 个用例）
- 编译检查：✓ 通过
- 修复文件：UserService.java:45-48
- 回归测试文件：UserServiceTest.java
- 修复内容：新增用户信息空判断，设置默认等级
```

### 用户确认（强制）

推演与编译通过后，**不要自动宣布完成**。向用户确认修复是否符合阶段 2 问题 2 的期望结果：

```
修复已完成并通过推演/编译检查：
- 修复内容：{简述}
- 验证结论：{推演/编译结果}

这是否符合你期望的「{期望结果}」？还有没有遗漏的场景需要覆盖？
```

等待用户确认后再结束；若用户指出遗漏，回到阶段 4 补充修复。

## 代码注释规范（强制）

**写代码时必须同步编写注释，注释要求：**

1. **从业务和功能角度说明**
   - 说明这段代码的业务目的
   - 说明关键业务逻辑的处理思路

2. **禁止写废话**
   - ❌ 禁止：`// 判断是否为空`（废话，代码本身已经说明）
   - ❌ 禁止：`// 设置值`（废话，代码本身已经说明）
   - ✓ 正确：`// 新用户第一次登录时用户信息未初始化，设置默认等级为普通用户`
   - ✓ 正确：`// 防止并发场景下重复创建用户信息，使用双重检查锁`

---

## 实际代码优先原则（强制）

**分析问题时：**
- 注释和文档可能过时或不准确，**实际运行的代码才是最真实的**
- 优先阅读和理解实际代码逻辑
- 文档和注释仅作为辅助参考，不能替代代码分析
- 如果文档描述与代码实现不一致，**以代码为准**

## 反模式

- 不问问题直接修复（可能定位错误）
- 只看注释不看代码（注释可能过时）
- 修复后不验证（可能引入新问题）
- 修复后不写回归测试（同一 bug 可能再犯）
- 不写注释（后续维护困难）
- 写废话注释（没有价值）

- 问题已定位
- 代码已修复
- 回归测试已编写并运行通过
- 注释已编写（从业务角度）
- 逻辑推演通过
- 编译检查通过
- 修复记录已输出
