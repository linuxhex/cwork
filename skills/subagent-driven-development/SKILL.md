# 子代理驱动开发

## 概述

通过为每个工程分派一个独立的子代理来执行计划，主代理负责协调和契约验证。

**核心原则：** 每个工程一个独立子代理 + 主代理协调 = 高质量、快速迭代

## 语言约束（强制）

- **所有对话必须使用中文**
- **所有分析必须使用中文**
- **所有结论必须用中文**
- 仅在必要处保留英文：命令、路径、参数名、状态码、字段名、代码

## HARD GATE

- workflow-state 不是 executing-plans，禁止执行
- 未经用户明确同意，绝不在 main/master 分支上开始实现
- 并行分派多个子代理时，确保它们操作不同工程目录

## 多工程并行架构

```
┌─────────────────────────────────────────────────────────────┐
│                     主代理（协调者）                          │
│  - 加载所有工程计划                                            │
│  - 维护跨工程契约清单                                          │
│  - 协调子代理执行                                              │
│  - 验证契约一致性                                              │
└─────────────────────────────────────────────────────────────┘
         │                    │                    │
         ▼                    ▼                    ▼
┌─────────────────┐  ┌─────────────────┐  ┌─────────────────┐
│ 子代理-A         │  │ 子代理-B         │  │ 子代理-C         │
│ 主工程           │  │ user-service     │  │ order-service   │
│                 │  │                 │  │                 │
│ - 执行主工程任务  │  │ - 执行本工程任务  │  │ - 执行本工程任务  │
│ - 写主工程文档    │  │ - 写本工程文档    │  │ - 写本工程文档    │
│ - 汇报执行结果    │  │ - 汇报执行结果    │  │ - 汇报执行结果    │
└─────────────────┘  └─────────────────┘  └─────────────────┘
```

## 执行流程

### 第 1 步：加载所有计划

主代理读取：
- 主工程计划：`docs/requirements/{requirement_key}/plan.md`
- 依赖工程计划：`docs/requirements/{requirement_key}/{service_name}/plan.md`

提取：
- 每个工程的任务列表
- 跨工程调用关系
- 契约定义（请求/响应结构）

### 第 2 步：构建执行顺序

根据依赖关系确定执行顺序：

```
执行计划：
  第 1 层: [user-service 任务, order-service 任务] — 并行
  第 2 层: [主工程任务] — 依赖第 1 层完成
```

### 第 3 步：分派子代理

**依赖工程子代理：**

```
Agent tool (general-purpose):
  description: "执行 user-service 工程"
  prompt: |
    你正在执行 user-service 工程的实现任务。
    
    ## 工程目录
    /path/to/user-service
    
    ## 任务列表
    [从 plan.md 提取的完整任务文本]
    
    ## 上下文
    - 主工程将调用本工程的 /user/data 接口
    - 需要返回用户基础信息和消费记录
    
    ## 你的工作
    1. 严格按照任务列表执行
    2. 每完成一个任务，更新 changes.md
    3. 完成后汇报执行结果
    
    ## 输出文件
    - docs/requirements/{requirement_key}/user-service/changes.md
    
    ## 汇报格式
    - 状态：DONE | DONE_WITH_CONCERNS | BLOCKED
    - 完成的任务列表
    - 修改的文件列表
    - 发现的问题（如有）
```

**主工程子代理：**

等待所有依赖工程完成后分派：

```
Agent tool (general-purpose):
  description: "执行主工程"
  prompt: |
    你正在执行主工程的实现任务。
    
    ## 工程目录
    /path/to/main-service
    
    ## 任务列表
    [从 plan.md 提取的完整任务文本]
    
    ## 依赖工程信息
    - user-service 已完成，提供 /user/data 接口
    - order-service 已完成，提供 /order/list 接口
    
    ## 你的工作
    1. 严格按照任务列表执行
    2. 集成依赖工程接口
    3. 每完成一个任务，更新 changes.md
    4. 完成后汇报执行结果
```

### 第 4 步：契约验证

主代理验证跨工程契约：

```
验证清单：
  ✓ 主工程调用的 /user/data 接口在 user-service 中存在
  ✓ 请求字段 userId 类型一致（String）
  ✓ 响应字段 userData 结构匹配
  ✓ 错误码定义一致
```

发现不一致时：
1. 记录问题到 `changes.md`
2. 通知对应子代理修复
3. 重新验证

## 处理子代理状态

**DONE：** 进入下一个工程或契约验证。

**DONE_WITH_CONCERNS：** 阅读疑虑，判断是否影响正确性。影响则修复后继续。

**BLOCKED：** 评估阻塞原因：
1. 如果是上下文问题，提供更多上下文并重新分派
2. 如果任务太大，拆分为更小的部分
3. 如果计划本身有问题，上报给用户

**NEEDS_CONTEXT：** 提供缺失的上下文并重新分派。

## 红线

**绝不：**
- 未经用户明确同意就在 main/master 分支上开始实现
- 并行分派操作同一工程目录的子代理（会冲突）
- 让子代理读取计划文件（应提供完整文本）
- 忽视子代理的问题
- 在契约验证失败时继续执行

## 输出

每个工程生成：
- `docs/requirements/{requirement_key}/{service_name}/changes.md`

主代理生成：
- 契约验证报告（追加到主工程 changes.md）
