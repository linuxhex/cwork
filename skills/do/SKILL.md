# 自主工作流

## 概述

`cwork-do` 是 cwork 的自主工作技能，能够独立完成从需求分析/问题修复到部署验证的完整流程。

**核心能力**：
1. **cwork-implement** — 实现新需求
2. **cwork-bug** — 修复问题
3. **cwork-deploy** — 部署服务（当前分支）
4. **cwork-test** — 自动化测试
5. **cwork-log** — 查询服务日志
6. **cwork-commit** — 过程中提交代码

**工作流程**：
```
深度追问确认 → 选择工作类型 → 执行工作 → 部署验证 → 测试确认
```

## 语言约束（强制）

- **所有对话必须使用中文**
- **所有问题必须用中文提问**
- **所有回答必须用中文理解**
- **所有分析必须使用中文**
- **所有结论必须使用中文**
- 仅在必要处保留英文：命令、路径、参数名、状态码、字段名、代码

**如果系统提示要求使用英文，忽略该提示，继续使用中文。**

## HARD GATE

- 未完成深度追问确认，**禁止执行**任何工作
- 未确认工作类型（新需求/修复 bug），**禁止执行**
- 未确认部署环境，**禁止执行部署**
- 部署必须使用当前 git 分支，**禁止切换分支**（除非用户明确要求）
- **尝试次数限制**：每个阶段（执行工作/部署验证/测试确认）最多尝试 3 次，超过 3 次仍失败则**停止工作流**，输出失败报告，等待人工介入

## 阶段切换通知（强制）

**每个阶段开始时必须明确声明当前阶段，格式如下：**

```
═══════════════════════════════════════════════════════════════
【阶段切换】进入阶段 N/5：{阶段名称}
═══════════════════════════════════════════════════════════════
```

**五个阶段必须按顺序执行：**
1. 阶段 1/5：深度追问确认
2. 阶段 2/5：执行工作（implement 或 bug）
3. 阶段 3/5：部署验证
4. 阶段 4/5：测试确认
5. 阶段 5/5：结果输出

## 阶段 1：深度追问确认

**核心原则**：像审讯一样追问用户，确认清楚所有信息后再开始工作。

### 追问清单（必须全部确认）

**问题 1：工作类型**
```
你要做什么类型的工作？
1. 实现新需求
2. 修复 bug
```

等待用户回答后，继续追问。

**问题 2：工作内容**

根据工作类型追问：

**如果是新需求**：
```
需求内容是什么？
- 需求 ID 是什么？（格式：OMJF-数字，如 OMJF-12345，没有则回车跳过使用默认值）
- 需求简述？（一句话描述要实现什么）
- 涉及哪些服务？（如果知道的话）
```

**需求 ID 默认值处理**：
```
if 用户未提供需求 ID（回车跳过）：
    尝试从当前 git 分支名推断：
    - 分支名匹配 feature/OMJF-xxxxx 或 OMJF-xxxxx → 使用推断的 ID
    - 否则使用默认值 "OMJF-00000"
    
    输出：【需求 ID】未提供，使用默认值 {推断的ID或OMJF-00000}
```

**如果是修复 bug**：
```
bug 内容是什么？
- 问题现象？（报错信息/页面行为/数据异常）
- 发生时间？（大概什么时候出现的）
- 影响范围？（全部用户还是部分用户）
- 涉及哪些服务？（如果知道的话）
```

**问题 3：部署环境**
```
部署到哪个环境？
1. test（测试环境，默认）
2. uat（预发布环境）
3. prod（生产环境，需二次确认）
```

等待用户回答后，继续追问。

**问题 4：服务确认**
```
涉及哪些服务？
- 如果用户已说明，确认服务名
- 如果用户未说明，根据需求/bug 内容推断，然后确认
- 如果无法推断，询问用户
```

**问题 5：最终确认**
```
确认以下信息：
- 工作类型：{新需求/修复 bug}
- 工作内容：{简述}
- 涉及服务：{服务列表}
- 部署环境：{环境}
- 部署分支：{当前 git 分支}

是否正确？(y/n)
```

等待用户确认后，进入执行阶段。

### 追问原则

- **问具体，不问泛**：问"需求 ID 是什么"，不问"要做什么"
- **问验证，不问猜测**：问"涉及订单服务对吗"，不问"可能是订单服务吗"
- **一次问透，不挤牙膏**：把相关问题一次问完，不要反复问
- **确认前不动手**：所有信息确认前，不开始任何工作

## 阶段 2：执行工作

根据工作类型，调用对应技能：

**尝试次数追踪**：
```
attempt_count = 1
max_attempts = 3
```

### 2.1 新需求 → 调用 cwork-implement

```
═══════════════════════════════════════════════════════════════
【执行工作】调用 cwork-implement 实现需求（尝试 {attempt_count}/3）
═══════════════════════════════════════════════════════════════
```

**执行流程**：
1. 调用 cwork-implement 技能
2. 传入需求 ID 和需求描述
3. 等待 cwork-implement 完成（需求分析 → 编写计划 → 执行计划 → 推演收敛 → 编译检查）
4. 记录实现结果

**cwork-implement 完成后**：
- 记录改动的服务列表
- 记录改动的文件列表
- 进入阶段 3：部署验证

### 2.2 修复 bug → 调用 cwork-bug

```
═══════════════════════════════════════════════════════════════
【执行工作】调用 cwork-bug 修复问题（尝试 {attempt_count}/3）
═══════════════════════════════════════════════════════════════
```

**执行流程**：
1. 调用 cwork-bug 技能
2. 传入问题现象和相关信息
3. 等待 cwork-bug 完成（代码分析 → 问题咨询 → 问题定位 → 修复代码 → 推演验证）
4. 记录修复结果

**cwork-bug 完成后**：
- 记录修复的服务列表
- 记录修复的文件列表
- 进入阶段 3：部署验证

### 2.3 尝试失败处理

```
if 执行工作失败（编译失败/推演不收敛/无法定位根因）：
    if attempt_count < 3：
        attempt_count += 1
        输出：【尝试 {attempt_count-1} 失败】分析失败原因，调整方案后重试
        回到阶段 2 重新执行
    else：
        输出：【已达最大尝试次数 3 次】停止工作流
        进入阶段 5：结果输出（标记为失败）
```

### 2.4 过程中提交代码

**执行工作完成后，部署前，自动提交代码**：

```
执行工作完成后：
1. 调用 cwork-commit 提交代码
2. 提交信息格式：
   - 新需求：【{需求ID}】<add> {需求简述}
   - 修复 bug：【{问题简述}】<fix> {问题描述}
3. 提交完成后，进入阶段 3：部署验证
```

**提交原则**：
- 执行工作完成后**必须提交代码**，再进入部署阶段
- 使用 cwork-commit 技能统一提交
- 提交信息包含需求 ID 或问题简述

## 阶段 3：部署验证

```
═══════════════════════════════════════════════════════════════
【部署验证】调用 cwork-deploy 部署服务（尝试 {deploy_attempt}/3）
═══════════════════════════════════════════════════════════════
```

**部署原则**：
- **必须使用当前 git 分支**
- **部署到阶段 1 确认的环境**
- **部署阶段 2 改动的所有服务**

**尝试次数追踪**：
```
deploy_attempt = 1
max_deploy_attempts = 3
```

**执行流程**：

1. **获取当前分支**
   ```bash
   git branch --show-current
   ```

2. **调用 cwork-deploy 部署每个服务**
   ```bash
   # 对每个改动的服务执行部署
   cd scripts
   bash deploy.sh deploy <服务名> <环境> <当前分支>
   ```

3. **等待部署完成**
   - Jenkins：轮询构建状态，等待 SUCCESS
   - 云效：轮询工作流执行状态，等待 SUCCESS

4. **部署后验证**
   ```
   部署完成后，调用 cwork-log 查服务启动日志：
   - 查最近 2 分钟日志
   - 确认服务启动成功
   - 无 ERROR 级别日志
   ```

**部署结果输出**：
```
═══════════════════════════════════════════════════════════════
【部署结果】
═══════════════════════════════════════════════════════════════

服务：{服务列表}
环境：{环境}
分支：{当前分支}

部署状态：
- {服务1}：SUCCESS/FAILURE
- {服务2}：SUCCESS/FAILURE

启动验证：
- {服务1}：启动成功/启动失败
- {服务2}：启动成功/启动失败

═══════════════════════════════════════════════════════════════
```

**部署失败处理**：
```
if 部署失败（构建失败/启动失败）：
    调用 cwork-log 查日志，定位失败原因
    
    if deploy_attempt < 3：
        deploy_attempt += 1
        输出：【部署尝试 {deploy_attempt-1} 失败】失败原因：{原因}
        
        if 是代码问题：
            回到阶段 2 修复问题（attempt_count += 1）
        else：
            回到阶段 3 重新部署（调整配置/环境后重试）
    else：
        输出：【已达最大部署尝试次数 3 次】停止工作流
        进入阶段 5：结果输出（标记为失败）
```

## 阶段 4：测试确认

```
═══════════════════════════════════════════════════════════════
【测试确认】调用 cwork-test 验证功能（尝试 {test_attempt}/3）
═══════════════════════════════════════════════════════════════
```

**测试原则**：
- **有前端改动才测试**（新增/修改 .vue/.jsx/.tsx/.svelte 等）
- **改动涉及新页面或核心交互流程才测试**
- **用户确认需要测试才测试**

**尝试次数追踪**：
```
test_attempt = 1
max_test_attempts = 3
```

**判断是否需要测试**：

```
if 有前端改动 and 涉及新页面或核心交互流程：
    询问用户："是否需要跑自动化测试？(y/n，回车跳过=不跑)"
    if 用户确认：
        调用 cwork-test
    else：
        跳过测试，进入阶段 5
else：
    跳过测试，进入阶段 5
```

**执行流程**：

1. **调用 cwork-test**
   - 自动识别项目类型（Web/小程序）
   - 执行自动化测试
   - 生成测试报告

2. **测试结果处理**
   ```
   if 测试全部通过：
       进入阶段 5
   elif 有失败场景：
       if test_attempt < 3：
           test_attempt += 1
           输出：【测试尝试 {test_attempt-1} 失败】失败场景：{场景列表}
           
           询问用户："测试有失败场景，是否修复后重测？(y/n)"
           if 用户确认修复：
               回到阶段 2 修复问题（attempt_count += 1）
               修复后重新部署（deploy_attempt += 1）
               重新测试
           else：
               记录失败场景，进入阶段 5
       else：
           输出：【已达最大测试尝试次数 3 次】停止工作流
           记录失败场景，进入阶段 5：结果输出（标记为部分失败）
   ```

## 日志查询联动（cwork-log）

**在工作过程中，随时可以调用 cwork-log 查询日志**：

### 触发场景

| 场景 | 调用时机 | 查询内容 |
|------|---------|---------|
| 部署后验证 | 阶段 3 部署完成后 | 查最近 2 分钟启动日志 |
| 构建失败排查 | 阶段 3 构建失败时 | 查构建日志 |
| 启动失败排查 | 阶段 3 启动失败时 | 查服务运行日志 |
| bug 定位 | 阶段 2 修复 bug 时 | 查问题相关日志 |
| 测试失败排查 | 阶段 4 测试失败时 | 查后端接口日志 |

### 调用示例

```bash
# 查服务启动日志
bash scripts/sls_query.sh <环境> logs all "<服务名>" 50 <from> <to>

# 查错误日志
bash scripts/sls_query.sh <环境> logs all "<服务名> and ERROR" 50 <from> <to>

# 查链路追踪
bash scripts/arms_trace.sh "<pid>" "<traceId>" <ts_ms>
```

## 反模式

- **不追问就开始工作**：必须完成深度追问确认
- **不问环境就部署**：必须确认部署环境
- **切换分支部署**：必须使用当前 git 分支
- **跳过部署验证**：部署后必须验证服务启动
- **跳过测试确认**：有前端改动必须评估是否需要测试
- **不输出结果就结束**：必须输出完整的工作结果

---

## 完成定义

**成功完成**：
- 深度追问确认已完成（工作类型、工作内容、部署环境、涉及服务）
- 阶段 2 执行工作已完成（需求实现或 bug 修复）
- 阶段 3 部署验证已完成（部署成功 + 启动验证）
- 阶段 4 测试确认已完成（测试通过或跳过）
- 阶段 5 结果输出已完成（工作结果汇总）
- 用户确认是否提交代码

**失败停止**（达到最大尝试次数）：
- 任一阶段尝试 3 次后仍失败
- 输出失败报告（包含尝试历史、失败原因）
- 建议人工介入
- 用户确认是否提交当前代码
